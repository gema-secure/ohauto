# 答辩三问 —— 三个问题为什么出现 / 根源解法 / 替代方案（2026-09-28）

> **用途**：作品简介 §二 的三个问题，评委最可能的追问就是
> "为什么会这样？你能根治吗？根治不了怎么办？"。本文逐一作答，
> 实测结论与推断分开标注，不混。

## 〇、解决方案一览（对三问的正面回答）

**总方案一句话**：把测试系统建成一条**「探索 → 生成 → 校验 → 执行 → 归因 → 自愈 → 沉淀」
的证据闭环**，三个问题各由闭环上的一环机制保证，而不是靠某一处聪明。

| 问题 | 解决方案（机制） | 怎么工作 | 实测证据 |
|---|---|---|---|
| 一：定位依据不足 | **四源融合定位**（N 源融合内核） | 静态源码声明、运行时控件树、截图视觉定位、OCR 四路各自独立产出证据；融合契约统一为 `Claim(kind,value,scope)` + 声明/观察角色；三条规则裁决：双确认=confirmed、声明✅观察❌=**missing（疑似缺陷）**、声明❌观察✅=undeclared。规则只认角色不认来源名，**加第四源（OCR）只写了一个适配器**——机制的可扩展性被实测验证 | etsclock 控件树 0 节点、OCR 读到表盘文字（Canvas 盲区实测）；视觉与控件树一致率 94.7%/95.0%、IoU 0.842；三类确定性缺陷成因（条件渲染/显式隐藏/越屏）真机探针全齐 |
| 二：失败缺乏归因 | **多源取证 + 分类判据 + 自愈闭环** | ① 失败即取证：截图、连续多棵控件树（防"晚到"误判）、faultlogger、设备状态打包；② 归因分类各带置信度与证据链（CRASH=1.0 靠 faultlogger 硬日志、NO_WINDOW=0.95、布局异常 0 误报）；③ 判定"定位失效"且同一位置**连续失败达阈值**→ 基于历史控件树重新生成定位器 → **换代（generation 0→1）**→ 重执行；④ 全程落账本，可复核 | 真机链路实测：计数 0→1→6 递增、换代触发、用例失败转通过；离线评测归因 40/40、自愈 10/10（可挂 CI） |
| 三：用例可信度不足 | **可失败性机械校验 + 断言从事实提取** | ① 每步校验"能不能失败、失败原因指不指向应用"，等待/断言计实质动作，不满足者在导出前拦截（`NO_SUBSTANCE` 总闸，机械规则不靠模型自觉）；② 断言不从模型想象生成，从探索状态图与真实控件树提取页面基准；③ 通过校验的用例导出 hypium 脚本真机执行，形成生成-验证闭环 | 空壳用例被系统性拦截（此前 L3"全过的 2 条都是空壳"成为反例证据）；hypium 导出真机 2/2 通过；`generate_cases()` 按状态图每条边派生、首尾相接可重放 |

**三环为何是一个系统**：定位融合给探索提供"看得全的界面"（问题一的产出直接
改善问题三的断言依据）；执行失败交给归因（问题二的产出是问题一 missing 判据的
运行时验证）；自愈换代产生的新定位器回写账本沉淀为回归资产（挑战 #6）。
**每一环的输出是另一环的输入——这就是"机制保证"而非"单点聪明"的含义。**

## 问题一：控件定位依据不足（id 覆盖率 5.62%）

### 为什么会出现（三层根因）

| 层 | 根因 | 依据 |
|---|---|---|
| 开发惯例层 | **id 是可选属性**。ArkUI 的 `id()`/`testTag()` 不写不报错、IDE 不提示、评审不检查；官方示例代码大多也不写。id 主要是给自动化测试用的，而开发阶段没有测试驱动的习惯 → 没人写 | 实测：7 应用 800 节点，id 覆盖率 5.62% |
| 框架结构层 | **可交互容器不承载文案**。真机实测：可点控件自身 id/text/descr 全空，文案在子节点 `text_deep`。即使有 id 的应用，按"控件自身字段"定位也会失败 | 实测 |
| 渲染路径层 | **Canvas 自绘完全绕过语义树**。控件树本质是 ArkUI 组件树的快照；用 Canvas 直接画的应用（时钟、图表、游戏）不创建组件节点，信息**从未进入**控件树——不是丢失，是根本不存在 | 实测：etsclock 可交互节点数为 0，OCR 却读到表盘文字 |

一句话：**控件树是为渲染和无障碍设计的，不是为测试设计的**。测试自动化在
生态里是二等公民，工具只能在"事后"消费一个不为它准备的信息结构。

### 根源解法（分"该谁做"）

- **生态侧根治（我们做不了，但要说得出来）**：开发侧强制语义标注——
  lint 规则要求可交互组件必须带 `testTag`/`id`，DevEco 内置检查；
  Android 生态 resource-id 覆盖率高正是拜 lint 与测试驱动惯例所赐。
- **工具侧根治（本作品的答案）**：**放弃"单一通道"假设，多源交叉**。
  既然信息不在一个地方是生态事实，测试工具的根治之道就是融合：
  静态源码挖声明（static_arkts）+ 控件树 + 截图视觉 + OCR。
  静态分析等价于"上游信息的事后补收"——源码里写了 id/结构，不管运行时
  给不给，都能用上。
- **诚实的上限**：融合能覆盖到多少没有理论保证；无源码、纯图形、无文字的
  控件（如纯图标按钮）仍是盲区。

### 根源解决不了时的替代方案（按实测取舍）

| 方案 | 实测结论 | 局限 |
|---|---|---|
| OCR 第四源 | etsclock 上控件树读不到 `14:54:11`，OCR 读到——**纯 Canvas 唯一通道** | 无文字的图形元素读不到 |
| 视觉定位（截图+模型） | 与控件树标注一致率 94.7%，IoU 0.842 | 一致率≠绝对准确率；依赖模型可用性 |
| 坐标/图像 diff 回归 | 可用但不推荐：主题、分辨率一变即失效 | 只能当辅助证据 |
| **插桩**（往被测应用塞 testTag / hook ArkUI） | 最彻底，但破坏"零部署"优势，且**对系统应用/无源码应用不可行** | 仅适用自研应用 → 工具必须双模式：插桩模式 + 免部署模式 |

## 问题二：测试失败缺乏归因

### 为什么会出现

1. **失败信号天然贫乏**：框架只给"step failed"（断言不满足/控件未找到/超时），
   不给"为什么"。真正的原因分散在 hilog、faultlogger、截图、控件树、执行轨迹
   五个地方，失败时刻没人把它们拼起来。
2. **成因空间本身有歧义**：同一个现象"控件找不到"，可能是应用缺陷（条件渲染）、
   设备状态（系统弹窗遮挡）、脚本缺陷（定位器过时）。**单靠失败瞬间的一份快照
   在原理上就不足以判定**——需要时间维度（之前在不在？）和跨源证据。
   实测佐证：单快照判据会把"页面晚到"误判成缺陷（diagnose 已修，守卫
   `len(trees)>=2`）。
3. **判据要验证区分度，而多数工具没做**：在正常样本上也命中的判据等于没有判据。
   崩溃判据我们用 `kill -11`（落 faultlogger，置信 1.0）vs `kill -9`（不落日志，
   只有 0.35 弱证据）实测过——判据强弱是测出来的，不是设计出来的。

### 根源解法

- **失败即取证（failure context capture）**：失败瞬间自动打包多源证据——
  截图 + 最近 N 棵控件树（时序）+ 崩溃日志 + 设备状态。先解决"信息全"，
  再谈"判定准"。
- **归因必须带置信度和证据链**：每类归因可复核（如 CRASH conf=1.0 背后是
  faultlogger 硬日志）。不可复核的归因永远不会被信任——这是信任层面的根治。
- **每条判据都验正反例**：正例（注入故障）与反例（正常样本 0 误报）双向验证。
- **诚实的上限**：故障诊断存在原理性盲区（信息不足时不可判定）。
  根治的目标不是"100% 归因"，而是**高置信分类 + 不确定时如实输出未知**。
  假装全知是更严重的缺陷。

### 替代方案

| 方案 | 说明 | 取舍 |
|---|---|---|
| 人机协同归因 | 机器给 Top-N 假设+证据，人裁决 | 工业界现状；把"自动判定"降级为"辅助诊断"，仍大幅省人力 |
| 重放与差分 | 重跑失败用例、改变前置条件（清状态/加等待/重试），用行为区分 flaky 与真缺陷 | 不依赖判据设计，代价是多轮执行 |
| 历史库比对 | 同一控件/页面历史上失败过吗、怎么恢复的 | 正是自愈账本（连续失败计数+换代）的思路 |
| LLM 假设生成 | 把证据包交给模型出假设 | 必须"人工复核"标注——实测模型把 OpenHarmony 说成 Android |

## 问题三：生成用例可信度不足（空壳用例）

### 为什么会出现

1. **生成目标错位**：LLM 的训练目标是"生成看起来合理的代码"，不是
   "验证一个属性"。没有明确的验证目标，模型自然产出执行流而非检验流。
2. **生成与验证脱节**：模型看不到执行结果，无从知道自己的用例"能不能失败"。
3. **度量层根因（最隐蔽）**：如果用"步骤通过率"评价用例好坏，空壳用例
   永远 100%——**指标本身在奖励空壳**。实测教训：L3 评测全过的 2 条用例
   都是空壳，"可执行 ≠ 做了事"。
4. 与问题一连锁：模型不知道界面上真实有什么，断言只能凭空编。

### 根源解法

- **把"可失败性"做成机械校验**（不靠模型自觉）：每步判定"这步能不能失败、
  失败原因指不指向应用"；等待/断言计实质动作，纯点击凑数不算。
  已实现：`RejectReason.NO_SUBSTANCE` + 用例级 `validate_case` 总闸。
- **断言从事实中提取，不从想象中生成**：从探索状态图和真实控件树提取
  页面基准状态（该有什么、点了会怎样），断言以此为准——断言有出处。
- **生成-执行-反馈闭环**：让模型看到执行结果与归因，迭代修正；
  用例经过真机验证才计入可信数字。
- **度量改革（我们尚未做，如实承认）**：用"缺陷检出力"替代通过率——
  注入已知缺陷，看用例能不能抓到（mutation testing 思路）。
  这是空壳问题的终极度量答案，赛前可做离线版。

### 替代方案

| 方案 | 实测依据 | 取舍 |
|---|---|---|
| 剧本模板生成：结构由模板保证，模型只填参数 | `ok=True` 是 ScriptedProvider 的能力，不是模型能力——**牺牲自由度换可信度的实证** | 覆盖面受模板限制 |
| 探索→沉淀：从状态图每条边自动派生用例 | `generate_cases()` 并集覆盖全部边，首尾相接可重放 | 确定可靠，但"智能"含量低 |
| 人工记录回放 | 传统方案 | 可信但覆盖受限于人工探索 |
| 多模型互评（他证） | 补充手段 | 可靠性不如机械规则 |

## 三问的合并答辩句

> 这三个问题的共同根源是：**OpenHarmony 的 UI 测试基础设施目前是"事后补"的
> ——控件树不为测试而设计，失败信号不打包，生成用例没闭环。生态侧的根治
> （强制语义标注、原生归因接口、验证驱动生成）不在我们手里；我们手里能做
> 的根治，是把每一条都从"单点依赖"改成"机制保证"：定位靠多源融合而不是
> 祈祷有 id，归因靠证据链+置信度而不是猜，用例靠可失败性校验而不是
> 看起来能跑。每条机制都有实测正反例，做不到的地方我们如实标注，
> 并给出降级方案而不是沉默。
