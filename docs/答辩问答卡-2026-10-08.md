## 一、数字口径类

### Q1 「95% 是准确率吗？」

**答**：不是，是双通道一致性——视觉给出的框和控件树给出的框是否重合（IoU@0.5）。
标注源自控件树，所以衡量的是"两个通道看不看得到同一个东西"，不是绝对准确率。

**追问**：不调模型时 75.0%（纯静态候选下限）；调模型后 95.0%（19/20，首批 20 项）。
跨 13 个应用扩到 46 项后合计 45/46 = 97.8%；最难的靶标是设置页 81.8%，如实呈现。

**复现**：`python tools/eval_vision_offline.py --dry`（75.0%，免 key）；主结果需 key。

### Q2 「1383 项测试、91% 覆盖率，怎么来的？」

**答**：一条命令的常驻门禁，不是一次性数字：`python tools/quality_gate.py`。

**展开**：1383 项单测全绿（0 失败 / 0 error）；覆盖率 TOTAL 91%（7958 语句 / 747 未覆盖）；
静态检查 0 error。每加一个修复就补钉子测试，所以这个数是**只涨不跌**的棘轮。

### Q3 「id 覆盖率 5.6% 是什么意思？」

**答**：真机 7 份控件树 / 800 节点里，带 id 的只占 5.62%——控件树单通道在生态里天然不够用，这就是我们做多源融合的出发点。

**追问**：两个分母别混——全节点口径 5.62%（45/800）；可交互控件口径 42.3%（22/52）；
**55.8% 的可交互控件没有任何语义标识**（无 id、无文案、无描述）。

**复现**：`python tools/profile_locators.py datasets/real_samples_20260919`

### Q4 「NL 生成用例 92.3% 怎么算的？空壳问题解决了吗？」

**答**：26 条描述（24 正样本 = 19 真机树自动派生 + 5 人工多步 + 2 固定负样本），
L2 静态可执行 24/26 = 92.3%，**两轮复跑完全一致**；24 条里**空壳 0 条**。

**追问**：空壳问题是用"两道机械闸"解的，不靠模型自觉——「登录」被空壳闸拦（NO_SUBSTANCE），
「搜索订单」被测试点闸拦（NO_TEST_POINT）。负样本被拦下才算对，这是可失败性校验的证据。

**复现**：`python tools/eval_nl_generation_real.py --execute ...`（需 key + 真机；命令见 B8 评测文档 §三）

### Q5 「L3 真机执行两轮数字不一样，哪个是真的？」

**答**：都真。两轮同 key、同设备、命令逐字相同：用例级 23/24 = 95.8% 与 22/24 = 91.7%，
步骤级 99.4% 与 98.8%——L2 稳、L3 波动 1 条，波动挂在哪条已查清（见 Q9/Q10）。

**追问**：19 条自动派生样本**两轮全部通过**；挂的都在人工补充的"断言显示值"类样本上。
这也是我们主动披露的局限：断言全打在显示值上，这个数是**下限偏低**。

### Q6 「B6 延迟达标吗？」

**答**：拆两行讲。宿主侧（引擎自身开销）P50 = 10ms，阈值 200ms，达标且余量 20 倍；
端到端 P50 = 1388ms，未达标——但瓶颈是设备侧 `dumpLayout` 一次往返约 1030ms 的**平台固有成本**，占 99%。

**追问**：我们的优化方向不是加速单次，是**少取树**：合并往返 + 只读步骤复用，
同一条 10 步用例真机实测取树 12→9 次、墙钟 **−26%**（21.5s→15.9s）。
剩下 9 次里大头是 waitIdle 签名轮询，语义上不能缓存——不能省的那种浪费。

**复现**：`python tools/measure_locate_latency.py --rounds 20 --label 桌面`（需真机）

### Q7 「四源融合，四个源真的都能用吗？」

**答**：5 个源适配器都在代码里，契约驱动，加新源只写一个适配器不改融合器。
要如实披露的边界：系统应用上静态源不可用（拿不到源码），所以有源码应用 4 源可全开，系统应用实测在线 2–3 源。

**追问**：每条证据带角色（declaration/observation）和三规则裁决：
双确认=confirmed、声明✅观察❌=missing（疑似缺陷）、声明❌观察✅=undeclared。
降级必须 ok=False + 原因，不静默。

**复现**：`python tools/trifusion.py --help`；实测报告 `tools/_out/fusion_vision_settings.md` 等

### Q8 「在几台设备上验证过？」

**答**：物理真机 1 台（DAYU200 / OpenHarmony 5.0.3.135 / 720×1280），
另有 4 个模拟器实例做跨形态（Mate X7 折叠开合、MateBook、MatePad、Pura）——都是 DevEco 模拟器，不是真机，口径分开报。

**追问**：跨形态实测：设置页 open vs close 检出缺失 77 / 溢出 4（KPI 检出 ≥2 类达标）；
折叠态长稳 2h55m / 250 周期 / 1366 步零人工干预。

## 二、现场案例类（这三个案例是今晚真机刚验完的，最有说服力）

### Q9 「你们有没有失败过？失败说明了什么？」

**答**：有，而且我们能把每条失败归因到根。最典型的一条：计算器"清零后断言显示为 0"，
两轮都挂、同一条同一步——真机实测 `result` 控件**视觉上是 0、控件树里是空串**。

**展开**：逐键实测（`uitest dumpLayout` 读数）：初始 `''`、按 1 后 `'1'`、清零后 `''`。
计算器把 0 渲染出来但不写进可访问性树——**应用侧的可访问性缺口**，不是我们生成错了（模型写的断言语义正确），
也不是执行引擎错了。这正是"树盲区靠多模态兜底"主叙事的真机证据。

**一句话**：这条失败恰恰证明了产品为什么需要多模态。

### Q10 「生成有波动怎么办？」

**答**：波动真实存在，我们不当没看见。第二轮比第一轮多挂 1 条：模型自己给"点击 /"加了断言
`expression == "/"`，而计算器忽略前导运算符（冷启动按 / 后 expression 仍是 `''`，`/→2` 才是 `'2'`）——模型对应用行为的判断错了，属生成质量波动，同一描述第一轮没加这条断言就 6/6 全过。

**一句话**：机制（校验、拦截、执行）两轮一致；波动在模型的判断里，用样本量和大数兜，不粉饰单轮数字。

### Q11 「自愈不是玄学？举个真机例子。」

**答**：真机降级链四场景全 PASS。场景 C：计算器按键"7"的 id 被改掉，且按键在树里**连文案都没有**、
同类型兄弟 18 个——树内线索全灭，系统**如实报"并列候选 18 个"而不是瞎猜一个**；
接上视觉通道后（同一场景开 `--vision`），第 1 代自愈经视觉定人 `via=vision`，换代后直连命中 `id_exact`。

**展开**：设计的要点是"任何'猜一个'都是错的"——线索全灭时宁可如实失败，
把失败变成换代触发条件，换通道解决而不是加判据硬凑。

**复现**：`python tools/verify_locator_degrade.py [--vision]`（需真机）

## 三、产品 / 机制类

### Q12 「演示怎么跑？一条命令。」

**答**：`python tools/demo_full_chain.py --real`——探索 → 生成 → 校验 → 执行 → 归因 → 自愈 → 沉淀八步一键整链；
离线版去掉 `--real`。设备不在场时如实报失败退出，不崩栈。

### Q13 「跟现有方案（坐标录制回放 / Appium 类）的区别？」

**答**：三点。① 不依赖 id：真机实测 55.8% 的可交互控件无任何语义标识，单通道方案在真实生态里先饿死；
② 失败有归因：失败即打包截图/多棵树/faultlogger 五源证据，给"为什么"，不只给"step failed"；
③ 会自愈：控件丢失 → 连续失败计数 → 换代重生成定位器 → 树内全灭换视觉，闭环真机验证过。

### Q14 「需要往被测应用里插桩吗？」

**答**：不需要，零部署——不装 HAP、不 hook 框架、不改被测应用一行代码，
所以系统应用和无源码应用都能测。插桩模式作为"最彻底"的选项评估过，但它放弃零部署优势，只在自研场景可选。

### Q15 「加一个新信息源要改多少？」

**答**：只写一个 `source_xxx()` 适配器。融合规则只认 `Claim(kind, value, scope)` 的声明/观察角色，不认源的名字——
OCR 作为第四源接入时只加了一个适配器，这是机制可扩展性的实测验证，不是宣称。

### Q16 「你们项目的局限是什么？」

**答**：四条，主动报。① B6 端到端延迟受设备侧 dumpLayout 固有成本限制，真机上做不到 200ms；
② B8 样本单应用单设备、两轮稳定性，断言目标集中在"显示值"，数字下限偏低；
③ 无源码 + 纯图形 + 无文字的控件（纯图标按钮）仍是融合盲区；
④ 语义结论（如页面意图）必须人工复核——实测模型曾把 OpenHarmony 页面说成 Android。

**一句话**：每条局限都带实测依据和应对方向，不是话术。
