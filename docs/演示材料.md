## 二、为什么演示材料是「截图 + 叠加」而不是录屏

这是**实测定的，不是偷懒**：

| 事实 | 数据 |
|---|---|
| 真机截图速率 | `uitest screenCap` 单次约 **1.26 秒**（≈ **0.8 fps**） |
| 设备是否有录屏命令 | **没有** —— OpenHarmony 不含 `screenrecorder`（那是 HarmonyOS 商业版的系统应用） |
| 壳内是否有 ffmpeg / 图像库 | 无 |

→ **连续截图合成视频帧率太低，真机录屏这条路在本设备上不成立。**

而且「截图 + 叠加」**比视频更能说明问题**：视频只能看出"界面变了"，
叠加图能看出"**系统把哪些像素认成了什么控件**"—— 这才是多模态能力的证据。

## 三、画廊怎么读（三个关键证据都在这）

打开 `docs/demo/gallery.html`，7 个真机样本每个一张卡片：
**左边是真机截图 + 控件框叠加，右边是该样本的识别统计**。

| 证据 | 数字 | 说明 |
|---|---|---|
| **id 覆盖率为 0 的页面** | `com.ohos.settings`：**12 个可交互控件 / 0 个 id** | 纯控件树**无法稳定定位**这些控件，必须靠文案与视觉通道补 —— 页面会打出黄色告警条 |
| **纯 Canvas 应用** | `etsclock`：**0 个可交互节点** | 控件树里一个可交互控件都没有，**视觉通道是唯一出路** |
| 样本总量 | 7 个应用 / **744 个可见节点** | 截图与控件树**同一坐标系**，所以叠加是精确的，不是示意图 |

**怎么讲**：先用画笔把框点出来（"这些蓝框是布局通道认出来的可交互控件"），
再切到那两个特殊样本（"这页 12 个可交互控件 id 全是空的，控件树到此为止；
而这页干脆一个可交互节点都没有 —— 这就是我们为什么必须做视觉通道"）。

| 场景 | 用哪块 |

## 六、答辩会被追问的两处（**如实讲，别粉饰**）

| 追问 | 怎么答 |
|---|---|
| 「L3 用例级只有 40%，能力这么差？」 | 40% 是全过的**比例**，而全过的 2 条**都是空壳用例**（3/3、1/1）；真引用控件的 3 条 0/3 整全过。→ 这恰恰是系统的**自我纠错能力**：我们不只看「生成成功」，还把「生成了但没做事」单独量出来，并已派活补校验 |
| 「自愈演示能现场跑吗？」 | 归因侧完全可跑（结论带 `locator_id`、`wire_locator_sink` 五项自测全绿）；**换代触发**卡在 A 的幂等代次修复上，派活已发、方案与验收已定。修完当场可演 |
