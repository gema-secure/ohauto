## ⚠️ 四个必须知道的坑（否则会以为失败）

### 坑 1：启动模拟器必须由「长期存活的后台任务」持有

`Emulator.exe -start` 是**前台常驻进程**，机器不死它不退出。三个实测结论：

1. 用 `subprocess.run(timeout=300)` 等它 → 撑满 300s 超时，
   **并把已经跑起来的模拟器一起杀掉**（表现为「刚看到设备在线，回头就没了，无报错」）
2. 用 `DETACHED_PROCESS` 启动 → 模拟器**无报错静默退出**，
   日志只留一行 `Windows Hypervisor Platform accelerator is operational`
3. 调用方进程退出 → 模拟器跟着死（它依附调用者会话）

**正确姿势**（让后台任务持有它）：

```bash
"<DevEco>\tools\emulator\Emulator.exe" -start "Mate X7" > _out\emu.log 2>&1
```

冷启动约 **40–60 秒**后设备出现在 `hdc list targets`（`127.0.0.1:5555`）。

### 坑 2：折叠态生效的判据是「屏幕电源状态」，不是「分辨率」

Mate X7 是**双屏**设备，两块屏分辨率恒定：

```
screen[0] = 2416x2210（内屏）    screen[1] = 1080x2444（外屏）
```

`foldedState` 只改它们的 **`powerStatus`**：

| 折叠态 | screen[0] | screen[1] |
|---|---|---|
| `open` / `half-open` | `POWER_STATUS_ON` | `POWER_STATUS_OFF` |
| `close` | `POWER_STATUS_OFF` | `POWER_STATUS_ON` |

**只看分辨率永远得出「没变化」的错结论。** 取状态：

```bash
hdc shell hidumper -s RenderService -a screen
```

> 另外 `-list -details` 的 `isRunning` **永远是 `false`**，别拿它判断死活。
> 判断依据只有 `hdc list targets` + `hdc shell echo`。

### 坑 3：折叠态切换后**不能立刻**抓控件树（2026-09-18 实测踩到）

`-foldedState` 返回成功 ≠ 界面已经重绘完。实测**约 1/3 概率**会在切换后
立刻 dump 到一份**空树**（只有 1 个根节点、没有子节点）——
如果直接拿去比对，会得出「89 个元素全部缺失」的**假差异**，
比报错更危险（看起来像被测应用崩了）。

**对策**（已固化进 `tools/crossform_run.py` 的 `capture_online`）：

```python
# 重试 4 次，每次退避等待；并校验元素数下限
for attempt in range(1, retries + 1):
    time.sleep(_FOLD_SETTLE_SEC if attempt == 1
               else _FOLD_SETTLE_SEC * attempt)   # 3s / 6s / 9s / 12s
    ...
    if sum(1 for _ in root.walk()) >= min_elements:   # 默认 3
        return capture
raise RuntimeError('...不是被测应用的缺陷，是采集侧没就绪')
```

> 💡 判据用「元素数 ≥ 3」而不是「≥ 1」：只有根节点 = 空树，
> 但真实界面**不可能**只有 1–2 个元素。这个下限是廉价而有效的哨兵。

### 坑 4：用完记得 `stop` 释放内存（实例占约 4 GB）

```bash
python tools\emulator_cli.py stop "Mate X7"
```

返回 `Stop emulator Mate X7 successfully` 后，再自检确认已释放：

```bash
python tools\emulator_cli.py status | grep "Mate X7"
# 期望：- Mate X7   type=foldable   running=false
```

> 后台任务持有的那个常驻进程不会自己退出 —— 即使 `stop` 成功、
> 设备已下线，那个 shell 仍显示 running。**这是正常的**，
> 它是「持有者」而不是「模拟器本身」；确认 `running=false`
> + `hdc list targets` 为空即可放心。

## ★ 重要修正：下哪个镜像

原始建议是「下 `foldable`，挑最小版」。**实测后这两条都不对**：

### 修正 1：折叠设备的镜像归在 `phone` 类目下

Mate X7 的 `deviceType` 是 `foldable`，但它的 `imageDir` 写的是：

```
system-image/HarmonyOS-7.0.0/phone_all_x86/
                             ^^^^^ 不是 foldable
```

要给它下镜像，`-deviceType` 必须传 **`phone`**。按字面传 `foldable` 会下错。

**判断依据**：读实例的 `imageDir`（`lists.json` 或 `-list -details`），
**不要按 `deviceType` 猜**。

### 修正 2：已有实例锁死版本，不能用「最小版」

4 个实例**全部绑定 `HarmonyOS 7.0.0`**，而最小版是 `5.0.1(13)` ——
下最小版**现有实例用不了**，得重建实例。

| 方案 | 代价 |
|---|---|
| 按实例版本下 `7.0.0`（**当前选择**） | 镜像最大、最吃内存；但现有实例直接用 |
| 下小版本 + 重建实例 | 镜像小、省内存；但要多一步 `-create` |

所以本次是**显式指定版本**下的：

```bash
python tools\emulator_cli.py install phone --os-version "HarmonyOS 7.0.0(26.0.0)"
```

> ⚠️ 工具里 `install` 的**默认策略是 `smallest`（最小版）**，
> 这个默认值对「已有 4 个 7.0.0 实例」的场景是错的 —— 所以显式传了版本。

### 修正 3：`-install` 是交互式的，不喂 stdin 会静默失败

`-install` 会追问 `Please read carefully and confirm whether agree to the above agreement? (y/N)`。

**如果不喂输入，它会把 EOF 当成「拒绝」，直接中止 —— 且 rc=0、不报错。**
现象就是「命令瞬间返回、镜像没下」。工具已修（固定喂 `y\n`）。

## 第 6 步：★ 跨形态差异比对（跨形态测试的最终产出）

前面几步都只是「把数据拿到手」，这一步才是跨形态测试真正要交的东西。

```bash
cd ohauto

# ① 模拟器实例跑（**需模拟器在线**；采 open/close 两态并比对）
python tools\crossform_run.py --device "Mate X7" ^
    --baseline open --target close --stem matex7_real

# ② 离线跑（不需要设备 —— 用靶子应用验判据）
python tools\crossform_run.py --offline --offline-page static_fixed ^
    --baseline close --target open --out _out\crossform\target --stem target

# ③ 只按 id 匹配（对照实验，看裸 id 策略漏多少）
python tools\crossform_run.py --offline --offline-page static_fixed ^
    --baseline close --target open --only-id --out _out\crossform\onlyid --stem onlyid
```

**退出码约定**（可直接接 CI 当门禁）：

| 退出码 | 含义 |
|---:|---|
| `0` | 无高严重度差异 |
| `2` | **检出了高严重度差异**（`MISSING` / `UNREACHABLE`） |

> ⚠️ 判据用的是引擎自己的 `has_high()`，**不要另写一份「哪些类型算高危」的清单** ——
> 两份定义迟早漂移，会导致「报告标红但 CI 放行」。

**产物**（每次跑测出 4 个文件，都在 `--out` 目录下）：

| 文件 | 用途 |
|---|---|
| `crossform.md` | 人读的差异报告（周会 / 评审直接贴） |
| `crossform.html` | 带样式的版本（浏览器打开，自带 CSS 无外部依赖） |
| `crossform.json` | 机器读（接 CI / 二次分析 / 趋势） |
| `run.json` | 本次运行的元信息（含 `has_high`，供门禁读） |

### 判据速查（报告里每一类都会写明判据，这里给个索引）

| 判据 | 含义 | 默认严重度 |
|---|---|---|
| `MISSING` | 同一身份的元素在目标形态**找不到** | 高 |
| `OUT_OF_SCREEN` | bounds **超出屏幕边界**（按裁切像素分级） | 中 |
| `UNREACHABLE` | 中心点在挖孔区，或**被裁切后可见区不足原面积 1%** | 高 |
| `OVERFLOW` | bounds 超出**父容器** bounds | 中 |

**元素身份三级降级**（跨形态比对的命门 —— 坐标必然变，不能用坐标认元素）：

```
id:xxx  →  tp:type|text  →  hp:type@父容器类型链
```

> 💡 `hp:` 这一级是兜底：当 id 和文本都拿不到（或 id 带实例号不稳定）时，
> 用「元素类型 + 它在父容器链里的位置」来认。模拟器实例实测它**确实在起作用**
> （桌面那 11 处缺失里有 4 处是靠 `hp:` 认出来的）。
