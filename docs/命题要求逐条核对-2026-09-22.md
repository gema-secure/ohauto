## 三、两个缺口的严重性排序

### ❌ 基础 #5 —— 最该先补（它是**基础目标**，且**可补**）

命题原话：「至少基于一个 OpenHarmony 示例应用完成验证，**覆盖不少于 3 个页面或核心流程**」。

**现状**：唯一做过端到端真机验证的应用是**计算器，而它只有一页**。
探索出的 3 个 state 是「同一页点了不同按钮」的内容签名差异 —— **不能算 3 个页面**。

**这正是上一轮暴露的 `pages` vs `pages_structural` 口径问题的另一个侧面**：
真机计算器实测 `pages_structural = 1`。

**补法**（设备回来后半天内可完成）：
1. 换**多页面应用**（设备自带的「设置」有 183 节点、多级页面；「备忘录」151 节点）
2. 跑一次完整链路：探索 → 状态图 → 生成用例 → 导出 → 执行 → 报告
3. 报告里给出 `pages_structural ≥ 3` 的证据 + 状态图截图

### ❌ 挑战 #1 —— 最影响**叙事**（命题的名字就是这个）

命题标题是《**多模态**智能测试用例生成系统》，挑战目标第一条就是
「支持多模态大模型理解应用截图和布局结构」。

**现状**：视觉通道写完了、抽象层也留了（`VisionProvider` / `HybridLocator` /
`TieredVisionLocator`），**但没有任何一次真实调用**。答辩时问「多模态体现在哪」，
现在只能答「架构上支持」——**这在评审那里是撑不住的**。

**补法**（需要一个 key）：
1. 配一个 OpenAI 兼容的视觉模型（**便宜的小模型就够，验证用**）
2. 跑「真机截图 → 页面意图描述 → bbox 定位」，报准确率
3. 这一下同时救回 **挑战 #1 + 挑战 #2 + KPI 的视觉三项**

## 五、一句话总结

> **命题要的是「多模态 + 智能 + 能孵化成 Agent」，我们交出来的是「一个工程极其规范的
> 单通道 UI 自动化框架」。**
>
> 差距不在代码质量（905 项测试、87% 覆盖率、5 关门禁都说明质量没问题），
> 而在**能力覆盖**：命题的 13 条里，**有 2 条是零证据，5 条是半证据**。
>
> 最讽刺的一点：**命题名字里的「多模态」，是我们做得最少的部分。**
