# 给 A：视觉线索漏拼子树文案 —— 实测与修改建议

> **提出方**：C（集成与质量）｜ **日期**：2026-09-22
> **涉及模块**：`ohauto/vision.py`（任务卡 A1 / A2 / A4）—— **本文件只提建议，未改代码**
> **证据工装**：`tools/eval_vision_offline.py`（零依赖，可离线复现，不需要设备）

---

## 一、结论（一句话）

`TieredVisionLocator._hints()` 只把节点**自身**的 `text` 送给匹配与模型，
而真机上**可交互容器自身文案恒为空** —— 于是 L1 静态匹配**永远命中 0 条**，
每条定位请求都被迫打到最贵的 L3 全屏，**A4 的「三层成本递增」实际退化成单层**。

**但只补文案不解决问题**（实测：10% → 10%），必须**同时**把 L1 的判定
从「必须唯一命中」改成「取最紧的匹配」。两步都做，L1 免调模型率可达
**70%（保守，零错误）或 100%（激进）**。

---

## 二、实测证据

### 2.1 线索里根本没有文案

```
TieredVisionLocator._hints() 产出 28 条线索，前 3 条：
   {'type': 'List',     'id': '', 'text': '', 'descr': ''}
   {'type': 'ListItem', 'id': '', 'text': '', 'descr': ''}
   {'type': 'ListItem', 'id': '', 'text': '', 'descr': ''}
```

28 条线索**无一带文案**。等于拿 28 个空壳去做关键词匹配、也拿空壳去问模型。

### 2.2 L1 命中 0 条

```
_static_candidates(hints, '蓝牙') = 0        ← 现状
若把 text 退到 text_deep        = 4
```

### 2.3 根因：真机上「可交互性在容器、文案在子节点」

真机实测（`app_settings`，28 个可交互控件）：

```
Flex (clickable=true, text='')          ← 可交互目标是这一层
 ├ Text (text='蓝牙')                    ← 文案在子节点
 └ Text (text='已关闭')
```

`LayoutNode.text_deep` 就是为这个形态加的（`layout.py` 里有完整说明），
但 `vision.py` 的两处 `_hints()` 和两处 blob 构造**都没有用它**。

### 2.4 ⚠️ 关键：只补文案不省模型调用（同一批 20 项实测）

`TieredVisionLocator` 的 L1 只在 `len(static) == 1` 时才免调模型。
补上 `text_deep` 后**容器节点也会命中**（容器的 deep 文案包含子项文案），
多条命中 → 照样走 L2。实测四种路线：

| 路线 | L1 免调模型 | 其中答案正确 | 备注 |
|---|---|---|---|
| A 现状（仅自身文案，须唯一） | **10.0%** | — | 现状（2/20） |
| B 补 `deep`，仍须唯一 | **10.0%** | — | **补文案是必要条件，不是充分条件** |
| C 补 `deep` + 剔容器，须唯一 | **20.0%** | — | 提升有限 |
| E 补 `deep` + 取最紧匹配 + **文案须与指令完全相等** | **70.0%** | **14/14 = 100%** | 保守，零错误 |
| D 补 `deep` + 取最紧匹配 | **100.0%** | 19/20 | 激进 |

> D 路线的唯一错例是 `app_settings` 的「蓝牙」—— 而该条的 ground truth
> 已被证明**无效**（控件树说那儿有蓝牙，画面上实际是「移动网络」，
> 见验证报告 §6.1）。**剔除该条后 D 是 19/19 全对。**

## 三、修改建议（6 处）

### 3.1 补文案（4 处）

**① `TieredVisionLocator._hints()`**

```python
     for n in flatten(root, only_visible=True, only_interactive=True):
-        out.append({'type': n.type, 'id': n.id, 'text': n.text,
+        out.append({'type': n.type, 'id': n.id, 'text': n.text,
+                    'deep': n.text_deep,
                     'descr': n.descr, 'hint': n.hint,
                     'bounds': n.rect.to_dict()})
```

**② `HybridLocator._hints()`** —— 同上（两处代码目前是重复的，可顺手抽成一个
模块级函数，但**不要**在这次改动里加抽象层，先让行为对齐）。

**③ `TieredVisionLocator._static_candidates()`**

```python

             blob = ' '.join(str(h.get(k, '')) for k in
-                            ('type', 'id', 'text', 'descr', 'hint')).lower()
+                            ('type', 'id', 'text', 'deep',
+                             'descr', 'hint')).lower()
```

**④ `HybridLocator.locate()` 的树通道 blob**

```python
         for n in flatten(root, only_visible=True):
-            blob = ' '.join([n.type, n.id, n.text, n.descr, n.hint] +
+            blob = ' '.join([n.type, n.id, n.text, n.text_deep,
+                             n.descr, n.hint] +
                             [str(v) for v in n.attributes.values()]).lower()
```

**⑤ `OpenAICompatibleProvider._build_context()`** —— 让模型也拿到文案

```python
         for h in hints[:self.max_hints]:
-            lines.append('  - type=%s id=%s text=%r bounds=%s' % (
-                h.get('type', ''), h.get('id', ''), h.get('text', ''),
-                h.get('bounds', '')))
+            lines.append('  - type=%s id=%s text=%r deep=%r bounds=%s' % (
+                h.get('type', ''), h.get('id', ''), h.get('text', ''),
```

> 这一处是 **L2/L3 的收益点**：现在模型拿到的上下文是「28 个空壳」，
+ 补上之后它才知道每个候选框里写的是什么。`deep` 截断到 60 字符 ——
+ 容器节点的 deep 可能很长（拼接了整组文案），不截会吃掉 token 预算。

### 3.2 改 L1 判定（1 处，这才是省调用的那一刀）

**⑥ `TieredVisionLocator.locate()` 的 L1 分支**

```python
         static = self._static_candidates(hints, instruction)
-        if len(static) == 1:
-            h = static[0]
+        # 补 deep 之后容器也会命中（deep 拼接了子项文案），「必须唯一」
+        # 就基本永不成立了。改为取**最紧的那个**：容器的 rect 一定比
+        # 它吞掉的行大，所以面积最小的那个就是真正的目标行。
+        # 实测（20 项）：取最紧 → 免调模型 100%、答案 19/20；
+        # 若要求「最紧者文案与指令完全相等」才返回 → 70%、14/14 全对。
+        if static:
+            h = min(static, key=lambda x: Rect.parse(x.get('bounds')).area)
             r = Rect.parse(h.get('bounds'))
-            self._log('L1 静态唯一命中（未调模型）')
+            exact = str(h.get('deep', '')).strip().lower() == \
+                instruction.strip().lower()
+            self._log(f'L1 取最紧命中（未调模型，exact={exact}）')
             result = VisualTarget(
                 label=str(h.get('text') or h.get('id') or h.get('type')),
                 rect=r, confidence=0.65, source='tree')
             self._cache[key] = result
             return result
-        if static:
-            self._log(f'L1 静态命中 {len(static)} 项，歧义 → 升级 L2')
```

**保守 / 激进二选一**：
- **保守（推荐先上）**：加 `if not exact: 升级 L2` 的条件
  → 免调模型 70%，**14/14 全对，零风险**
- **激进**：如上面代码，直接返回
  → 免调模型 100%，19/20（唯一错例的标注本身无效）

建议先上保守版，跑一段时间看误命中率，再决定是否放开。

## 五、边界说明

1. **本文件只提建议，C 未改动 `ohauto/vision.py` 任何一行**
   （`git log` / 文件 mtime 可核：`vision.py` 最后修改时间 09-22 13:23，
   属上午 A/B 合并，C 的会话 19:25 之后才开始）。
2. 建议 ③④⑤ 一起改：只改 ③ 不改 ④，会让 `HybridLocator` 的树通道与
   `TieredVisionLocator` 的 L1 **判定口径不一致**，同一目标在两处得到不同结论。
3. ⑥ 的「取最紧」依赖「容器的 rect 一定大于它吞掉的行」这个事实。
   在本批真机样本上成立（容器 rect 与内层行 rect 相差 6~600px 不等），
   但**换应用后建议复测** —— `--dry` 就是这个复测工具。
4. 补 `deep` 会给线索字典多一个键。若有下游代码按固定键集迭代
   （`HybridLocator._hints` 的消费方），要确认不会 KeyError。
