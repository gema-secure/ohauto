## 二、★ `pages` 口径：定 `pages_structural`（KPI 用这个）

**结论：KPI「发现页面数」用 `pages_structural`。** 你倾向它是对的，我采纳。

三条理由：

1. **本体例的「页面」粒度就是结构签名**。B1 里定的双签名分工是：
   内容签名管「这页我访问过没有」（精确去重），结构签名管「这是不是同一个页面」
   （页面粒度）。报告里的「页面数」属于后者。
2. **用内容签名会让数字虚高，而且虚高得恰好违背 B1 的设计初衷。**
   真机计算器点 5 次 → 6 个 state、实际 1 页，这就是「内容签名太敏感」这个已知特性
   跑到了报告的页数上。我在 B1 里专门警告过它，现在得自己认下来。
3. **答辩叙事上更站得住**：`pages_structural=1 / pages=6` 这个对照本身就是
   「为什么必须要双签名」的现场证据，比一个虚高的「发现 6 页」有用得多。

**这事的责任在我**：`CoverageReport` 的 docstring 写「按结构签名归并页面」、
实现却是 `pages=len(graph.states)`（内容签名）—— **文档和实现脱节**，
和你在缺陷 1 里踩的「按面积排」是同一类错误：**说的话和写的事不一致**。
已订正：

```
pages             探索覆盖了多少种界面状态（内容签名去重）
pages_structural  界面上有多少个不同的页面（结构签名归并）   ← KPI 用这个
```

## 三、C-2（缺快照判错类别）：确认是真 bug，已修

**你观察到的现象和我定位到的根因完全对得上，而且根因就差一行。**

```python
def _page_expectation(rec, trees):
    ...
    for root in trees:            # ← 快照为空时，这个循环一次都不执行
        ...
        return 'match'
    return 'mismatch'             # ← 于是直接落到这里
```

空列表上「遍历没命中就判 mismatch」= 什么都没核过却给出了否定结论。
于是「落点与 expected_page 不符 → 用例缺陷」这条判据被凭空触发，
`CASE_DEFECT @ 0.80` 压过 `LOCATOR @ 0.6`，类别整体跑偏 —— 正如你在真机上看到的。

**修法**：

```python
usable = [r for r in trees if r is not None]
if not usable:
    return 'unknown'          # 核不了落点，就别假装核过了
```

**修后行为**：缺快照时仍为 `LOCATOR`，只是置信度从 0.85 降到 0.6（弱结论）。

> 这里有个我认为值得记下来的区分：**「判得不确定」和「判错方向」是两码事。**
> 前者只是数字变小，后者会把结论交给错误的人去修（应用缺陷 vs 用例缺陷，
> 一个要改代码、一个要改用例）。你指出这一点的价值比「置信度掉了一档」大得多。
