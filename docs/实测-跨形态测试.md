### ⚠️ 下镜像时的两条实测修正（原方案是错的）

**① 折叠设备的镜像归在 `phone` 类目下，不是 `foldable`。**

**判断依据是实例的 `imageDir`，不是 `deviceType` 字面。**

**② 已有实例锁死版本，不能用「最小版」。**

4 个实例全绑 `HarmonyOS 7.0.0`，而最小版是 `5.0.1(13)` —— 下了也用不上。
所以本次**显式指定** `--os-version "HarmonyOS 7.0.0(26.0.0)"`。

**③ `-install` 是交互式的**，不喂 stdin 会拿到 EOF 静默中止（rc=0 不报错）。
工具已修（固定喂 `y\n`）。

**④ 不能用 `-imageList` 判断下载是否在进行** —— `.zip` 解压注册前它一直报
`downloaded=false`。**要看目录里 `.zip` 大小是否在涨。**

**答辩口径**：说「`FoldStatus` 已接入，架构支持折叠态；已验证 X 种形态」，

### 动作 3：设计 `switch_form(profile)` 的契约（W2 冻结前必须定）

契约总表里 `switch_form(profile) -> None` 是 C 对 B 的承诺，且 **W2（9/29）就冻结**。

```python

{
  'name': 'Mate X7_unfolded',   # 档案名（重名的补了类别前缀，保证全局唯一）
  'device': 'Mate X7',           # 设备型号
  'kind': 'foldable',            # phone / foldable / foldable_folded /
                                 # wide_fold(_folded) / triple_fold(_double/_folded)
                                 # tablet / pc / tv / wearable / car
  'width': 2210, 'height': 2416, # 分辨率 px
  'density': 500,                # dpi
  'diagonal': 8.0,               # 屏幕对角线 inch
  'corner_radius': [26.25, 23.1],# 圆角半径（可能多角不同）
  'cutouts': [[2092, 28, 70, 70]],   # 挖孔包围盒 (x,y,w,h)，无孔为 []
  'status_bar_h': 0, 'nav_bar_h': 0, # ⚠️ 静态配置无此项，须 hidumper 实测填充
  'fold_status': 'EXPANDED',     # EXPANDED / FOLDED / DOUBLE；直板机 None
  'source': 'product_config',    # 数据来源，便于追溯
  'caveats': [],                 # 有值 = 该形态数据需实测复核
  # 派生字段（to_dict 自动加，不用手填）
  'safe_area': [0, 0, 2210, 2416],
  'is_folded': False,
  'has_measured_safe_area': False,
}
```

**关键约定（必须写进契约）**：
- `switch_form()` **返回后调用方必须重新 `dumpLayout`**，任何缓存坐标一律失效
- 切换失败要**明确抛异常**，不能静默降级（否则跨形态用例会拿旧形态的坐标乱点）
- 形态档案用 **dataclass**（`FormProfile`）而非裸 dict，方便校验 ✅ 已实现
- **`caveats` 非空的形态，其上得出的结论必须先实测验证**（当前只有 Mate XT
  的折叠态与双屏态命中这条 —— 配置里给了它一个孔坐标，但三个形态共用，
  物理上未必对）
- **`has_measured_safe_area=False` 时 `safe_area` 等于整屏**，语义是"还没测"
  不是"没有安全区"——消费方必须先判断这个标志位，否则会把安全区当 0 用

### 动作 4：差异报告的判据要能"硬"判

四类差异里最容易写虚的是「不可达」。建议给出**客观判据**：

| 差异类型 | 客观判据（不靠感觉） |
|---|---|
| 元素缺失 | 同一选择器（id/text）在形态 B 的控件树里**找不到** |
| 越界 | 元素 `bounds` 超出 `screen_size`（拿 `driver.screen_size()` 比） |
| **不可达** | 元素 bounds **与安全区/挖孔区域相交**，或其中心点在屏幕外 → 点击必然失败 |
| **溢出** | 元素 bounds **超出父容器 bounds**（控件的 containment 破坏） |

「越界」和「不可达」要分开：前者是渲染超出屏幕，后者是**能看见但点不到**
（被挖孔/圆角/折痕挡住），这在折叠屏上很常见，也是最容易出真 bug 的地方。

**四类判据**（客观、不靠感觉）：

| 判据 | 含义 | 默认严重度 |
|---|---|---|
| `MISSING` | 同一身份的元素在目标形态**找不到** | 高 |
| `OUT_OF_SCREEN` | bounds **超出屏幕边界**（按裁切像素分级） | 中 |
| `UNREACHABLE` | 中心点在挖孔区，或**被裁切后可见区不足原面积 1%** | 高 |
| `OVERFLOW` | bounds 超出**父容器** bounds | 中 |

**元素身份三级降级**（跨形态比对的命门 —— 坐标必然变，不能用坐标认元素）：
`id:xxx` → `tp:type|text` → `hp:type@父容器类型链`

**真机实测结果**（Mate X7 模拟器，桌面 `SCBDesktop`，`open` → `close`）：

```

缺失 11 / 越界 0 / 不可达 0 / 溢出 1
```

展开态横铺 x∈[721,1491]，外屏宽仅 1080 → 重排）。1 处溢出 =
`LiveMetaBallBaseVm`（**折叠态新出现**的智慧语音悬浮球，已标
`is_new_in_target=True`）。

**离线靶子应用** `static_fixed`（按外屏 1080×2444 设计、坐标系切形态
纹丝不动）复现真实世界最常见错误：`close`→`open` 时
**越界 2 处**，退出码 2（可直接接 CI 当门禁）。
