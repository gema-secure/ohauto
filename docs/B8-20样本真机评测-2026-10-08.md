> 结论一句话：**规划原文要求的「20 条描述生成后逐条执行」这一轮补齐了** ——
> 24 条正样本 + 2 条固定负样本，L2 静态可执行率 **92.3%**（**两轮复跑完全一致**），
> 可执行的 24 条**空壳用例 0 条**；L3 真机执行**用例级 23/24 与 22/24**（两轮）、
> **步骤级 176/177 与 170/172**（两轮，见 §四之二）。
> 两轮挂掉的两条**都属于「断言/期望落在控件树之外」**：一条是**计算器没把「0」写进控件树**
> （真机实测，见 §五），另一条是模型自己加了一条「前导运算符进表达式」的断言（见 §四之二）。

## 一、为什么之前只有 3 条

10-08 早先那轮（`tools/_out/nl_eval_mp3/nl_eval.json`）总数只有 **3 条**：

| 来源 | 条数 | 说明 |
|---|---|---|
| 工具从真机树自动派生 | **1** | 入口页只有 1 个「可交互且带文案/id」的控件 |
| 固定负样本 | 2 | 故意混入，期望被拦下 |

分母是 3 时，`executable_rate` 既不可比，也容易被读成「已按规划验过」。
**根因不是模型，是样本集**：入口页派生的描述数上不去。

## 二、这一轮怎么补到 20+

| 来源 | 条数 | 怎么来的 |
|---|---|---|
| 真机树自动派生 | **19** | 换到可交互控件更多的应用 `ohos.samples.distributedcalc`（144 节点 / 20 可交互 / 21 带 id） |
| 人工补充（`--prompts`） | **5** | `tools/b8_prompts_calc.txt`：多步描述（7+8=15、9*3=27、C 清零、1.2.5、连续运算），只用该树真实存在的 id |
| 固定负样本 | 2 | 期望被拦下 |
| **合计** | **26**（正样本 24） | ≥ 规划要求的 20 |

⚠️ **口径必须说清的三条**：
1. 19 条是**自动派生**、5 条是**人工补充**（每行一条，出处写在文件里）——
   引用数字时要说明这个配比，不能笼统说「20 条都是自动生成的」；
2. L2 的分母是 **26**（含 2 条负样本），负样本**被拦下才算对**；
3. L3 只在 L2 通过的那 24 条上跑，**不并进 L2**（真机状态会波动）。

不会产出一个「分母只有 3」的漂亮百分比。

## 四之二、第二轮（稳定性复跑：同 key、同设备、命令逐字相同，只换 `--out`）

| 指标 | 第一轮 | 第二轮 | 结论 |
|---|---|---|---|
| L2 可执行 | 24/26 = **92.3%** | 24/26 = **92.3%** | **两轮完全一致** |
| 其中真引用控件/断言 | 24/24（空壳 0） | 24/24（空壳 0） | 一致 |
| 负样本拦截 | 空壳闸 1 + 测试点闸 1 | 空壳闸 1 + 测试点闸 1 | 一致 |
| L3 用例级 | **23/24 = 95.8%** | **22/24 = 91.7%** | 波动 **1 条** |
| L3 步骤级 | **176/177 = 99.4%** | **170/172 = 98.8%** | 波动 1 步 |
| L2 生成耗时 | 392.4s | 441.2s | — |

**L2 稳、L3 波动 ±1 条**，而且两轮各自挂在哪条已经查清：

| 轮次 | 挂的用例 | 挂在哪 |
|---|---|---|
| 第一轮 | 「点击 C 清零，然后断言显示为 0」 | `assert text(result) == "0"` —— **控件树盲区**（见 §五） |
| 第二轮 | 同上（同一条、同一步） | 同因，**可复现** |
| 第二轮 | 「点击 id 为 / 的控件」 | 模型这一轮**自己加了一条断言** `assert text(expression) == "/"` —— 期望本身不成立 |

真机实测（冷启动后逐个按键，同台 DAYU200；`uitest dumpLayout` 读数）：

| 操作 | `expression.text` | `result.text` |
|---|---|---|
| 冷启动 | `''` | `''` |
| 冷启动 → 按 `/` | **`''`**（前导运算符被忽略） | `''` |
| 冷启动 → `/` → `2` | `'2'` | `'2'` |
| 按 `7` | `'7'` | `'7'` |
| 按 `7` → `/` | `'7/'` | `'7'` |
| 按 `C` 清零 | `''` | **`''`**（视觉是 0，树里是空串） |

→ 两条失败**同属一类：断言/期望落在控件树之外**，但成因要分开讲：

① 「C 清零」是**应用侧可访问性缺口** —— 值在视觉上有、控件树里没有（多模态兜底该上场的地方）；
② 「/」是**模型对应用行为的判断错了** —— 计算器本就不把前导运算符写进表达式，
   属模型波动/生成质量类，**不是机制问题**（同一描述第一轮没加这条断言，就过了 6/6）。

> 口径：对外引用 L3 时必须**两轮并列**（`23/24` 与 `22/24`），
> 不能只报第一轮 —— 单轮数字会被读成稳定值。

## 五、第一轮唯一失败的那一步：不是 bug，是控件树盲区（真机实测）

失败用例来自**人工补充**的第 22 条「点击 C 清零，然后断言显示为 0」
（第二轮同一条同一步照样挂 —— 这一条是**可复现**的失败）。
模型生成的用例本身是对的：

```
start → waitFor(id=result) → tap(id=1) → waitIdle → tap(id=C) → waitIdle
      → assert text(id=result) equals "0"   ← 这一步挂
```

真机上直接量 `id=result` 这个控件（`uitest dumpLayout`，同一台 DAYU200）：

| 界面状态 | `result.text` | `result.text_deep` |
|---|---|---|
| 初始（视觉上是 0） | `''` | `''` |
| 按下 `1` 之后 | `'1'` | `'1'` |
| 按 `C` 清零之后 | `''` | `''` |

**结论**：计算器把「0」渲染出来但不写进可访问性树 —— 视觉是 0、控件树是空串。
所以「断言显示为 0」在这台设备上**用控件树通道永远无法通过**，
它只能靠视觉 / OCR 通道判。这既不是生成质量问题（模型写的是语义正确的断言），
也不是执行引擎问题，而是**应用侧的可访问性缺口** ——
恰好是本项目「树盲区靠多模态兜底」这条主叙事的又一份真机证据。

> 对评测口径的影响：这 1 条是**人工补充**样本，19 条自动派生样本 **全部用例级通过**。
> 引用时不要把这条说成「生成质量 96%」——它是「断言目标选在了控件树读不到的值上」。

## 六、局限（不许含糊）

1. **单应用、单设备**：`ohos.samples.distributedcalc` + DAYU200 一台。
   稳定性只做了**两轮**（见 §四之二）：L2 两轮一致、L3 波动 1 条 ——
   要报"稳定值"还得再多跑几轮（每轮约 12 分钟，成本在生成 24 条用例）。
2. **19 + 5 的配比**：自动派生的 19 条清一色是「点击 id 为 X 的控件」（单击），
   多步能力实际由人工补的 5 条承载 —— 这是本轮样本集的结构性偏斜。
3. **负样本只有 2 条**，且是固定两条；「语义映射到现有控件」的那类半执行负样本
   （如早先的「搜索订单」）**本轮没有**。
4. **断言类失败集中在"显示值"上**：两轮挂掉的 2 条都在断言计算器的显示值
   （`result` / `expression`）——这类目标在控件树里**本来就不稳定**。
   样本集里没有覆盖"断言页面结构（控件存在/跳转）"这类更稳的目标，
   所以 95.8% / 91.7% 这个数**下限偏低**，不是模型不能写稳断言。
5. 本轮用的 key 是临时提供的一把，**按项目约定跑完即轮换**；
   报告只记 base_url 与模型名，key 不落盘（`sk-*` 还会被兜底打码）。

## 七、与本轮代码改动的关系

本轮同时补上的两处（都在 `tools/eval_nl_generation_real.py`）：

- `--require-samples N` + `sample_gate()`：正样本不足直接停（防「分母 3 的百分比」流出）；
- `build_descriptions_from_pages()`：多页模式按页并集派生描述（入口页 1 条 → 三页 6 条）；
- `load_prompts_file()`：`--prompts` 跳过 `#` 注释行（注释被当成描述会直接污染 KPI）。

钉子：`tests/test_c_b8_samples.py`（16 项）。
