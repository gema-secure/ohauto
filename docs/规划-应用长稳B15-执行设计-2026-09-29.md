# B15 · 应用长稳执行设计（2026-09-29）

> **回答一个问题**：引擎在**真实大程序**上连续跑 2 小时，稳不稳？
> 7+8 循环（B11）证明的是引擎通道不劣化；B15 证明的是引擎在
> **真实大树的持续压力**下不劣化——两者证据并列，不互相替代。

## 二、混合套件编排（不是单一用例循环）

每个**周期**（约 4-6 分钟）按固定顺序执行，2 小时 ≈ 20-30 个周期：

```
周期 =
  A. 探索爆发        Explorer 在靶应用上探索（Budget：2 页 / 每页 3 动作）
                     —— 每周期重新探索，覆盖面随周期累积
  B. 核心流导航      重放一条固定的设置导航用例（进入子页 → 返回 → 换页）
  C. 压测分片        连续滑动/翻转 ×10（stress_cases 分片）
  D. 形态切换        （仅模拟器版）open ↔ close 切换一次，验证布局重建
  E. 稳定等待        waitIdle + 采样点（遥测在此打点）
```

设计理由：
- A 保证「每周期都有新东西」（探索覆盖面随时间增长，页面指纹去重防绕圈）；
- B 提供可比性（固定用例的耗时趋势是漂移检测的基准线）；
- C 提供输入压力（连续注入是句柄/事件的泄漏源）；
- D 仅模拟器版——折叠重建是鸿蒙特色压力，真机版无此步。

**用例从哪来**：首轮探索的 `graph.json` → `generate_cases` 生成导航用例 →
人工审阅后冻结为 B15 固定套件（**不每轮重新生成**——固定套件才有可比性）。

## 三、遥测采样器（需新建：`tools/stability_telemetry.py`）

独立进程与跑测并行，每 60 秒采一轮，写 `telemetry.jsonl`：

| 通道 | 采集方式 | 派生判据 |
|---|---|---|
| 设备内存（被测应用 PSS） | `hidumper --mem <pid>`（pidof 定位） | 斜率：后半程均值 / 前半程均值，涨幅 ≥30% 且持续上扬 → 报泄漏嫌疑 |
| 设备负载 | `cat /proc/loadavg` | 趋势参考 |
| 设备存活 | `list targets` 含目标 | 断连即记事件 |
| 宿主进程内存 | `tasklist /FI "PID eq <pid>"`（解析内存列） | 同 PSS 判据 |
| 引擎计数 | 读 partial 报告（轮数/失败/重试/恢复） | 与延迟趋势联动 |

设计约束：
- 采样失败**记 None + 警告**，绝不编造（「缺样本 ≠ 正常」）；
- 判据阈值首轮跑完**校准后冻结**——第一轮的产出就是阈值依据（与
  stability_trend 的 15% 阈值同一方法论：先测再定）；
- 零依赖，复用 preflight/hdc 既有封装。

## 四、判据（全部满足才达标）

1. 连续 ≥2h 无异常退出（同 B11）；
2. 固定导航用例（B 项）耗时半程漂移 < ±15%（stability_trend 口径）；
3. 探索爆发（A 项）每周期均产出**新的**覆盖增量或如实报告已饱和；
4. 被测应用 PSS 斜率无持续上扬（阈值首轮校准后冻结）；
5. 全程零人工干预；
6. 每条失败步骤都有归因结论（引擎失败 vs 应用行为，两行并列）。

## 五、风险与处置

| 风险 | 处置 |
|---|---|
| 模拟器应用弹窗/首启向导卡住前台 | 周期 A 的探索自带弹窗识别；连续 2 周期无法采集 → 截图留证后跳过该应用 |
| 真机系统应用版本差异导致用例失效 | note_stability 的教训——**先探后写**：用例从当次探索产物生成，不手写 |
| 遥测与跑测抢 hdc | 采样间隔 60s，单次 <2s，占空比 ~3%，实测确认不影响跑测延迟 |
| 宿主被杀（B11 教训） | `-u` 无缓冲 + 每周期增量落盘 + 跑时别关终端（SOP 已固化） |
| 模拟器 4GB 内存与其它工作冲突 | 跑 B15 时停其它重活；爆内存先保真机侧工作 |

## 七、与既有证据的关系

- B11（7+8，2h）：引擎通道不劣化 ✅ 已达标——B15 不重复它；
- B12（跨形态）：布局重建差异 ✅ 已达标——B15 把折叠切换放进**长时程**；
- B15 补的是最后一块：**真实大应用 × 长时程 × 资源曲线**——
  「大一点的程序怎么办」的完整答案由此闭环。
