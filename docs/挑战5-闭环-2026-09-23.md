# 挑战 #5 闭环：失败步 → 归因 → 报告

> **命题对应**：挑战 #5「崩溃 / 卡死 / 白屏 / 无响应 / 布局异常」
> **编写**：C（队长 · 集成与质量）｜ **日期**：2026-09-23
> **一句话**：把 `diagnose_failed_step()` 接进了 **runner 的失败分支** ——
> 在此之前归因引擎虽然就绪，却**一次都没在生产链路里被调用过**，
> 所以「崩溃 ✅ / 白屏 ✅」拿不出证据链。现在失败步自动归因，结论随报告落盘。

## 二、改了什么

### 2.1 `runner.py`：失败分支接归因

| 项 | 内容 |
|---|---|
| 新参数 | `diagnose_failures=False`（默认关）/ `diagnoser=None` / `diagnose_signals=False` / `diagnose_locator_sink=None` |
| 接入点 | `Runner.run_case()` 里 `not sr.ok` 时调 `_diagnose_step()`，结论写进 `StepResult.verdict` |
| 失败降级 | **归因是旁路**：`_diagnose_step` 吞掉一切异常，记进 `diagnose_errors`，返回 None |
| 输出 | verbose 模式下失败步紧跟一行「归因: [定位失败] 置信度 0.60 …」 |

**为什么默认关**：既有 1007 项测试与真机批量的行为必须一字不变。
开关打开后才有额外行为 —— 迁移是显式的，不是悄悄发生的。

**为什么 `diagnose_signals` 是独立开关**：传了 `hdc` 才会调 `collect_signals()`，
那是**每步失败一次设备往返**（采崩溃日志 + 截图 + 控件树）。默认只做
**离线归因**（用产物目录里已有的控件树快照），真机批量时才按需打开。

**两个 sink 为什么不能合并**（容易写错的地方）：

```python
Runner.locator_sink(spec, reason)            # 执行器递「DSL 原始规格」
diagnose_locator_sink(locator_id, reason)    # 归因递「定位器 id」
```

直接复用会把**规格当成 id** 传出去，在 A 的健康度台账里塞假账。所以分成两个参数。

### 2.2 `StepResult`：承载结论

新增字段 `verdict`（+ `diagnosed` / `verdict_cn` 两个便捷属性）。

`to_dict()` 里 **有 verdict 才输出这个键** —— 让消费方能区分
「没做归因」与「归因结论为空」，这两件事在报告里必须看得出差别。

### 2.3 `report.py`：结论要看得见

markdown 与 html 都新增「**失败步归因**」一节（结论 + 置信度 + 建议 + 证据）。
没有 verdict 时**不输出这一节**，不留空标题。

> 报告里为什么要专门占一节：归因的价值在**证据**和**建议**，
> 表格里一行放不下；而藏在产物 JSON 里的结论，在没人翻文件的批处理里等于没做。

### 2.4 `signals.py`：补第 5 类「布局异常」

详见 §三 —— 判据的选择是**用真机数据定的**，不是拍脑袋。

## 三、布局异常的判据为什么是「越出屏幕」

任务卡列的 5 类里，布局异常最难判 —— 直觉上会选「子控件越出父容器」。
**真机数据把这条否了。** 用 `--scan-fixtures` 在 7 个真机样本上对比三种候选判据：

| 样本 | 节点数 | 越出父容器 | 子比父大 | **越出屏幕** |
|---|---|---|---|---|
| app_note | 151 | 11 | 8 | **0** |
| app_photos | 49 | 0 | 0 | **0** |
| app_settings | 183 | 13 | 9 | **0** |
| etsclock | 77 | 11 | 8 | **0** |
| s_etsclock | 103 | 11 | 8 | **0** |
| sample_calc | 144 | 12 | 8 | **0** |
| sample_music | 93 | 11 | 8 | **0** |
| **合计** | — | **69** | **49** | **0** |

**结论**：前两条在**每一个正常页面上都命中** —— 没有区分度，等于「永远报警」。
一条永远报警的判据比没有判据更糟，它会把真正的异常淹掉。

为什么前两条在真机上是常态（两种原因都实测到了）：

1. **滚动列表的坐标系不同**：`app_settings` 里 `ListItem [42,72][678,122]`
   越出父 `List [42,156][678,207]` 达 84px —— 子节点**整个在父容器上方**。
   这是列表内容坐标 vs 可视区坐标的差异，不是布局写坏。
   （真机上 `List` 的 `scrollable` 字段是 `False`，所以「排除可滚动父容器」这条
   过滤**在真机上根本不起作用**。）
2. **整体偏移 ≠ 溢出**：`sample_calc` 里 `Text(expression)` 与父 `Row`
   **高度完全相同**（都 185px），只是整体偏移 10px —— 渲染取整/描边，不是缺陷。

所以判据定为：**可见且面积 > 0 的控件越出屏幕边界**
（屏幕边界取根节点 bounds，不额外查设备）。

### 误报与漏报的验证

| 验证 | 方法 | 结果 |
|---|---|---|
| **误报**（关键） | 7 个真机样本 + 真机设置首页（169 节点） | **0/8** |
| **能报**（正例） | 单测构造越屏控件（右/下/左三边） | 全部报出，evidence 带数量与坐标 |
| **不是"全排除所以恒为 0"** | 诊断脚本统计被排除量 | 真机页面**确实有 19 个越界节点、8 个超阈值** —— 它们面积全为 0（`Row`，看不见），属**正确排除**而不是判据失效 |

⚠️ **诚实留白**：目前**没有**在真机上见过真实发生的「布局异常」，
所以「能不能报真问题」只有单测的正例支撑，**没有真机正例**。
这条在答辩时应如实说。

### 4.3 真机正例：受控异常注入（★ 这一段是「能报」的证据）

之前所有验证都只证明了「**正常页面不乱报**」；「**真出现异常时能不能报**」一直没有真机证据，
因为异常在真机上不可控。本工装把可控的两类做成注入：

```bash
# 崩溃判据依赖设备时间窗口，先校时（RTC 跳到 2017 会让窗口判据失效）
python tools/sync_device_time.py --target <device-serial>
python tools/verify_signals_injection_real.py
```

真实输出（2026-09-23，DAYU200 / `ohos.samples.distributedmusicplayer`）：

```
场景 1/2：CRASH —— kill -11 杀被测应用（SIGSEGV，会产生 faultlog）
  [基线] CRASH 异常 0 条（期望 0）
  [注入] kill -11 8033
  [落盘] 系统新增崩溃日志：['cppcrash-ohos.samples.distributedmusicplayer-20010020-20260923220803']（等了 2.0s）
  [判定] 注入后应报 CRASH
         ✅ CRASH conf=1.0 — 崩溃日志 cppcrash-…-20260923220803: module=… pid=8033 reason=Signal:SIGSEGV
         ✅ CRASH conf=0.9 — 进程 ohos.samples.distributedmusicplayer 已不在 pidof 输出中
  [基线复核] 注入前 0 条 → 注入后 [('CRASH', 1.0), ('CRASH', 0.9)]

场景 2/2：NO_WINDOW —— 息屏（锁屏不进无障碍树）
  [基线] NO_WINDOW 异常 0 条（期望 0）
  [注入] power-shell suspend（息屏 → 锁屏）
  [判定] ✅ NO_WINDOW conf=0.95 — 控件树仅 1 个节点（且 bounds 全为 [0,0][0,0]），
         DeviceGuard.has_window() 同样判定无窗口 —— 锁屏或无前台窗口
  [恢复] ensure_awake = True
```

**两个关键设计决定，都是踩过才定下来的**：

1. **注入用 `kill -11`（SIGSEGV）而不是 `kill -9`** —— 实测 `kill -9`（SIGKILL）
   **不会**让 `faultlogger` 落日志，判据只能给 **0.35** 的「进程消失」弱证据；
   `kill -11` 会被系统当作真实崩溃捕获，落一份 `cppcrash-<bundle>-<uid>-<时间戳>`，
   判据走到 **1.0** 那条路。**要验「真崩溃能不能被认出来」，就别用那个连日志都不产生的信号。**
2. **基线窗口只回看 5 秒 + 注入后轮询等落盘** —— 第一版工装两处都错了：
   `collect_signals` 默认回看 **600s**，把上一次实验留下的崩溃日志算进了基线
   （基线直接报 1 条 CRASH，「注入前无异常」这个前提失效）；固定 `sleep 3s`
   又读到「还没写出来」的空目录（注入后反而 0 条）。
   改成「短窗口基线 + 轮询等新日志出现」后两个场景才稳定。

> **这两个坑值得记住**：验证工装自己出错时，产生的**假阴性/假阳性比被测代码的 bug 更难发现** ——
> 因为它看起来"跑通了"，只是结论反了。

**真机造不出来的三类，工装会打印声明而不是假装跑过**：白屏、无响应、布局异常。

### 4.4 闭环接线：`locator_id` 送达归因（★ 挑战 #5 → 挑战 #6 的桥）

在此之前归因只能说「⚠️ 这次**没能回写**定位器自愈 —— 记录里缺 `locator_id`」，
读者看不出该去修哪个定位器。接线办法是给 `Runner` 加一个**只读**钩子：

| 新增 | 作用 |
|---|---|
| `Runner(locator_id_resolver=...)` | 集成层注入 `spec -> locator_id` 反查；runner **不认识** `LocatorManager`（那是 A 的模块） |
| `tools/wire_locator_sink.make_locator_id_resolver(lm)` | 反查实现（用 A 的公开接口 `all_health()` + `spec()`） |

⚠️ **只补 id、不回写**：回写仍只有 `_report_locator_failure` 一条路。
两条路都回写会把同一次失败**计两遍**，把 A 刚修好的幂等又破坏掉
（表现为自愈阈值被提前触发）。

实测（`python tools/wire_locator_sink.py`）：

```
失败步 kind           : LOCATE
StepResult.locator_id : L001_username
verdict.locator_id    : L001_username
归因结论              : [定位失败] 置信度 0.60 — 按**定位失败**处理：回写
                        record_locator_failure(locator_id, reason) 给 A 的定位器自愈
                        （locator_id=L001_username，由 A 的 LocatorManager 生成，我们原样回写）
A 侧连续失败          : 0 -> 1
```

**⚠️ 但这一跑又暴露了下一环断点（A 侧）**：

```
又失败 5 次后连续失败 : 1（期望接近 6）
```

原因：A 的幂等键是 `(locate 代次, locator_id)`（`locator.py:547`），
代次**只在 `locate()` 时推进**；而执行器走 `matcher`/`layout`、**从不调 `locate()`**
→ 代次恒为 0 → 第一次之后的回写全被判成「同一次定位的重复记账」而丢弃
→ **连续失败停在 1 → 自愈阈值达不到 → 自愈永远不会触发**。

这是 A 的幂等设计与「执行器不经 LocatorManager」这个架构现实之间的冲突。
**归属 `locator.py::_count_failure`（A 的文件）**，建议修法：
让代次可由执行器显式推进，或幂等键改用「执行尝试序号」。
（注意：**这不是本次接线的问题** —— id 已正确送达、回写也确实被调用了。）
