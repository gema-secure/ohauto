## 一、★ 缺陷 1：页面标题取到状态栏（已修）

### 现象

真机跑探索，**6 个页面的标题全是同一句**：

```
· S1 「没有 SIM 卡」  content_key=d91703041b
· S2 「没有 SIM 卡」  content_key=c9e514d294
· S3 「没有 SIM 卡」  content_key=f736d7a2b6
· S4 「没有 SIM 卡」  ...
· S5 「没有 SIM 卡」  ...
· S6 「没有 SIM 卡」  ...
```

`content_key` 六个都不一样（说明**双签名工作正常**，页面确实被区分了），
但标题全一样 —— 报告里完全分不出谁是谁。

### 根因

`explorer.py` 的 `_page_title()` 原实现：

```python
cands.append((n.rect.top, -n.rect.area, n.text))
if cands:
    cands.sort()          # ← 按 top 升序 = 取「最靠上的」
    return cands[0][2]
```

**真机上「最靠上的文本」永远是状态栏** —— 实测状态栏在 `top≈32` 且带文本
（`没有 SIM 卡` 在 `[43,32][170,50]`）。模拟设备的状态栏文本不同，所以自测没暴露。

### 修法（已实施）

**排除状态栏区域后，仍旧取「最靠上的」** —— 标题栏本就固定在页顶，判据没错，只是漏了排除。

```python
STATUS_BAR_MAX_TOP = 72      # 真机 SystemUi_StatusBar 的实测高度 [0,0,720,72]
...
if n.rect.top < self.STATUS_BAR_MAX_TOP:
    continue                 # 剔掉状态栏
cands.append((n.rect.top, -n.rect.area, n.text))
cands.sort()
```

> ⚠️ **中间踩过的坑，值得你知道**：我一度改成「**面积优先**」，
> 结果真机计算器上正文提示「按 = 出结果」的面积是标题「计算器」的 **30 倍**，
> 把标题挤掉了 —— 是我自己写的测试挡下来的。
> 教训：**这个函数里「靠上」比「字大」可靠**，因为标题栏的位置是稳定的，字号不是。

**真机复验（修复后）**：

```
states=3 结构页数=3 覆盖=10.0%
    S1 「计算器」      ← 正确
    S2 「软件更新」     ← 正确
    S3 「计算器」      ← 正确
```

配了 3 条单测（`tests/test_c_explorer_fixes.py`），按**真机形态**构造
（状态栏在最上方带文本 —— 这是关键前提）。

## 二、★ 缺陷 2：`coverage.pages` 与 docstring 口径不符（**请你定夺**）

### 现象

真机计算器是**单页**应用（按钮不跳页，只有显示区文字在变），但探索报告说：

```
发现页面数      6
```

### 根因

`CoverageReport` 的 docstring 写的是：

> 覆盖度：已访可交互 / 全部可交互（**按结构签名归并页面**）

但实现是：

```python
pages=len(self.graph.states),      # ← states 按**内容签名**去重
```

而 `StateGraph.states` 的键是 `signature.content_key`。于是
**「点一下、正文文字变了」就会被算成一个新页面** ——
这正是你在 B1 设计里警告过的「内容签名太敏感」，
只是它现在出现在**报告的页数**上，而不是探索逻辑里。

实测：计算器点 5 次 → 6 个 state，实际 1 页。

### 我的处理（**只加不改**，口径留给你定）

没有动 `pages` 的语义（怕动到你已有的报告/测试数字），而是**追加**一个字段：

```python
@dataclass
class CoverageReport:
    pages: int = 0
    pages_structural: int = 0      # ★ 新增：len(structural_index)，按结构签名归并
```

`to_dict()` 两个都出。两个数一起看：

| 字段 | 含义 |
|---|---|
| `pages` | 探索覆盖了多少种界面**状态**（内容签名） |
| `pages_structural` | 界面上有多少个**不同的页面**（结构签名） |

### 需要你定的

**KPI 里「发现页面数」该用哪个？** 我倾向 `pages_structural`（它才符合你在 B1
里定的「页面」粒度，也符合这个类原本的 docstring）。但最终口径你定 ——
你定了我就把 smoke 脚本和文档统一过去。

## 三·补、依赖约定的口径澄清（你 C-1 那个问题的**根子**）

你 C-1 问「pyyaml 算不算必须」。我上一份回执答了「落盘保持 YAML」——
但你之所以会问，**根子在这条**：

> `分发说明` 第 67-70 行：「**不要 `pip install` 任何东西**……
> `requirements.txt` 里只有开发期的可选工具。」

照字面读，`requirements.txt` 里躺着 pyyaml **本身就自相矛盾** —— 你不知道该听哪句。

### 准确口径：核心能力零第三方依赖（不是「不许 pip install」）

| 层 | 内容 | 规则 |
|---|---|---|
| **核心能力** | `hdc` / `layout` / `matcher` / `driver` / `runner` / `report` / `sim` / `explorer` / `generator` / `diagnose` | **零第三方**。引一个进来才算违规 |
| **DSL 序列化后端** | `pyyaml` | 写可退化 JSON；**读 YAML 必须有它** |
| **工具链** | `coverage`、`pyyaml` | CI 与本地装，**不进设备侧、不进分发产物** |

**所以**：`requirements.txt` 里可以有东西、CI 会装它
（`.github/workflows/quality-gate.yml:63` 就是 `pip install -r requirements.txt`）——
**这不违反约定**；**在核心模块里 `import` 第三方包才违反**。

### 这条为什么不能干脆取消

不是随手定的偏执，是从《项目规划》高地 7 的验收标准推出来的：

```
高地 7 验收：「任何人 clone 后按 README 三步能跑起来」   ← 工程规范 10 分的硬指标
        ↓ 要做到这点
代码包必须自包含（clean-room 能跑）
        ↓ 所以
核心能力零第三方依赖 —— 标准库够用
```

`分发说明` 第 60-61 行自己就写明：「这个命令在**解压后的干净副本上实测通过** ——
代码包是自包含的」。

> **原表述「不要 pip install 任何东西」是手段被绝对化的产物**：
> 原始目标（可复现）→ 推导约束（核心零依赖）→ 转述成（啥都别装）。
> 每转一手掉一层条件，最后和 CI 自己的 `pip install` 打起来了 ——
> **你就是被这个失真卡住的，不是被项目规划卡住的。**
> 完整分析见 `docs/口径澄清-依赖约定-2026-09-22.md`。
