### 1.3 问题三「三个 KPI 是自证式的」—— ✅ **确认（前两条）/ ✅ 确认（第三条口径）**

（输出格式即 `期望={CATEGORY_CN[want]}`），用规则表复述规则表。**同义反复成立。**

**(b) 可执行率 17/20** ✅ **确认**：`tests/test_generator.py:110` 的
`_StageAwareProvider` 是**剧本 provider** ——

```python
def complete(self, prompt: str) -> str:
    if '拆成测试点清单' in prompt:
        return self.plan_reply        # ← _plan_reply() 返回预置文本
```

它按 prompt 内容分派**预置回复**，不是真模型。所以「17/20」证明的是
「解析器能处理我预先设计的输入」。**同义反复成立。**

**(c) 50 步成功率 ≥95%** ✅ **确认口径问题**（这一条评审分析得最漂亮）：

```python
# runner.py:530-533
@property
def independent_success_rate(self) -> float:
    return round((self.total - self.independent_failed) / self.total, 4)
```

配合 `runner.py:885-900` 的级联判据（失败类别与首个失败相同 → 标记 cascade
→ 剔出分母），**50 步全部因同一原因失败 → independent_failed=1 → 0.98 → 判定通过**。
而现实中绝大多数失败恰好都是同一类（LOCATE）。

**这不是 bug（逻辑自洽），是口径设计问题**：一个测量「引擎健壮性」的指标，
在用例彻底挂掉时会给出最漂亮的分数。评审这个判断我完全同意。

```
可改用固定 waitFor，或去掉该步。已实现的 action: start/wait/…
```

## 五、我最同意评审的一点（也是我要补充的一点）

评审说：

> 最需要正视的不是缺口数量，而是**三个自证式 KPI** 和一个**没闭上的闭环** ——
> 前者会让你们在答辩时被一句话问穿，后者会让核心主张失去支撑。

**我同意，并认为这两件事是同一件事的两面**：

```
闭环没闭上  →  只能用剧本 provider / 手写快照自测
            →  自测出来的数字支撑不了「闭环成立」
            →  于是 KPI 只能是自证式的
```

所以**第一刀应该切在闭环上，而不是 KPI 上**：
把 `diagnose()` 与 `collect_signals()` 接进 `Runner.run_case` 的失败分支
（评审建议 2，改动量比重接 `LocatorManager` 小得多）。接上之后：

- 报告里会出现真实 `Verdict` 版面 → **闭环叙事成立**
- 同时立刻拿到**真实失败快照样本上的分类命中率** → **归因 KPI 的口径问题自动解决**

一刀解决两个问题。这比先改 KPI 的数字口径更有价值 —— 后者只是把自证改成「自证得更谦虚」。
