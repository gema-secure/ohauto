## 二、「只用 Python 够不够」—— 分维度回答

**一句话**：**编排、AI/ML、图像处理留在 Python 是对的**；但有两件事确实该切出去：
**ArkTS 源码分析**（归 Node）和**设备侧深度能力**（归 ArkTS，做成可选）。

| 维度 | Python 现状 | 别的语言更强吗 | 判断 |
|---|---|---|---|
| 编排 / AI / ML / 提示词 | ✅ 就是最强生态 | — | **保持 Python** |
| 图像处理 / 报告生成 | ✅ 够用 | C++ 更快但没必要 | **保持** |
| **ArkTS 源码 / HAP 静态分析** | ❌ 生态不在这（ohpm、hvigor、arkanalyzer 全在 Node） | **Node/TS 明显更强** | ✅ **已切出去**（见 §三） |
| **设备侧能力** | ⚠️ 只能走 `hdc` 命令行，单次操作一次进程启动 | **ArkTS 强很多**：`waitForComponent`、Toast、性能数据、Socket 长连接 | 短板 —— 但**零部署**是我们的核心优势，做成**可选增强**而不是替代 |
| 实时性 / 高频操作 | ⚠️ 实测真机截图 **0.8 fps**（单次 1.26s） | 设备端 / C++ | 压测与「录屏」场景受限 |
| 前端可视化 | HTML 报告已有（静态） | JS 可做交互式 | 可增强（ui-viewer 思路） |
| 并发 / 多设备 | ⚠️ GIL | Go/Rust | 当前单设备，**不急** |

> ⚠️ **实测数据**：真机 `uitest screenCap` 单次约 **1.26 秒**（≈0.8 fps），
> 所以「连续截图合成视频当录屏」在 DAYU200 上**帧率太低**；
> 且 OpenHarmony **没有** `screenrecorder`（那是 HarmonyOS 商业版的系统应用）。
> **结论：真机录屏这条路在本设备上不成立**，演示材料应走「分步截图 + 说明」而非视频。

## 三、已落地：ArkTS 静态分析（Node + Python 双语）

这是本次「多技术栈各用一段」的第一个实例：

```
Node（tools/static_arkts/analyze.mjs，零依赖，只用内置 fs/path）
    ↓ JSON
Python（tools/static_arkts/bridge.py，负责「用起来」）
```

**为什么切给 Node**：ArkTS 生态工具链（ohpm / hvigor，以及 HmTest 用的 arkanalyzer）
都在 Node 侧，Python 做这件事是逆生态的。

**能给出什么**（实测 `ohauto-hypium-test` 工程）：

```
页面路由 : ['pages/Index', 'pages/WidgetCard']
abilities: ['EntryAbility', 'TestAbility']
控件     : 1 个（已排除测试代码）→ HelloWorld
```

**与运行时控件树是互补的两份**：

| | 来源 | 能回答 |
|---|---|---|
| `ohauto.treesum.control_catalog` | 运行时控件树 | 「此刻界面上有什么」 |
| 本静态分析 | 源码 / 配置 | 「工程里声明了什么」（包括**还没进入的页面**） |

**降级原则**：Node 找不到 / 目录不存在 / 脚本失败 → **返回 None 并留下原因**，
绝不拖垮主流程（已实测两条降级路径）。静态分析是**增强项**，不是必选项。

```bash
python tools/static_arkts/bridge.py D:/project/ohauto-hypium-test -o _out/static_arkts.json
```

## 四、我们的差异化（相对这些项目）

调研之后更清楚我们该讲什么：

1. **双通道定位**（视觉 + 控件树）—— HapTest / hmdriver2 都只有控件树；
   我们的视觉通道在真机上 **94.7%**，且 L1 免调模型率 **70%**（几乎不花钱）。
2. **失败归因闭环**（挑战 #5）—— 失败步自动出 `Verdict`（类别+置信度+证据+建议），
   且 **CRASH / NO_WINDOW 两类已有真机受控注入的正例**。同类项目没看到这个。
3. **自然语言 → 用例六阶段**，含**红线校验与自动修复**（硬编码坐标/固定等待会被拦下并修好）。
4. **零部署**：不需要测试 HAP，宿主侧 Python + hdc 直连。
5. **跨形态**（折叠屏形态差异比对）。

## 六、一句话

**Python 不是短板，是主控层的正确选择；真正的短板是「设备侧能力」和
「ArkTS 生态」——前者用「可选增强」补（不牺牲零部署），后者已经切给 Node 了。
下一步最值钱的是把静态分析的产出接进探索器（归 B）和做一个交互式控件树查看器（归 C）。**
