# 三源融合定位 —— 调研结论与原型（2026-09-24）

> **作者**：C ｜ **命题对应**：基础 1（多模态识别可交互元素）、挑战 1（理解页面意图/入口/路径）
> **代码**：`tools/trifusion.py`（原型）＋ `tools/static_arkts/`（静态源）

---

## 一、调研：**没有人把「静态源码」当第三个源**

先查了 GitHub / AtomGit / 官方文档 / 学术论文，确认这个想法有没有人做过：

| 项目 | 源 1 | 源 2 | **静态源码** | 融合方式 |
|---|---|---|---|---|
| **Airtest + Poco**（网易，9.4k star） | 图像识别 | UI 树 | ❌ | **人工选择** —— 官方原话「哪边方便用哪边」 |
| **UiPath AI Computer Vision** | 元素检测 | OCR | ❌ | 融合成 multi-anchor descriptor（商业闭源） |
| **OmniParser**（微软） | 视觉检测 + OCR | — | ❌ | 纯视觉，明确「不依赖 HTML 或控件树」 |
| **Auto-Explorer**（NUS） | UIA | OCR / 图标模板 | ❌ | **降级链** —— 「HTML 和 UIA 失败时才用 OCR」 |
| **arkXtest / Hypium**（官方） | 控件树 | — | ❌ | 单源 |
| **HapTest / HmTest** | 控件树 | 静态（**但不与运行时交叉验证**） | ⚠️ | 静态只用于**引导探索**，不做对齐 |
| **本原型** | 视觉 | 运行时控件树 | **✅** | **交叉验证 + 差异告警** |

**两条结论**：

1. **第三条源（静态源码）没人做过** —— HapTest/HmTest 虽然也做静态分析，
   但用途是「引导探索往哪走」，**不与运行时做逐项对齐**。没人用它回答
   「这个控件**应该**在不在」。
2. **融合方式都不是交叉验证** —— 要么人工选、要么降级链（前一种失败才用后一种）。
   交叉验证是**同时看**：一致则提高置信度，**不一致本身就是信号**。

## 二、核心洞察：**差异即缺陷**

> 源码里声明了某个控件，运行时控件树里却没有 —— 这个控件丢了。

这是一类**能被自动发现的真实缺陷**，而且**两类现有方案都发现不了**：

| 方案 | 为什么发现不了 |
|---|---|
| 纯控件树（HapTest / hmdriver2 / Hypium） | 不知道「**应该有什么**」—— 它只看到此刻在的 |
| 纯视觉（OmniParser / UI-TARS） | 不知道「**声明了什么**」—— 它只看到画面上有的 |

只有把「声明」和「实际」放在一起对齐，才能问出「**少了吗**」。
这就是三源融合里第三源不可替代的价值。

## 三、原型设计

```
源 1 静态（Node）        源 2 运行时（控件树）      源 3 视觉（截图+模型）
「工程里声明了什么」      「此刻界面上有什么」      「画面上看到了什么」
      │                        │                        │
      └────────────┬───────────┴────────────┬───────────┘
                   ▼                        ▼
              逐项对齐（按 id / 文案）   交叉验证
                   └────────────┬───────────┘
                                ▼
                    融合结果 + 置信度 + **差异告警**
```

**置信度阶梯**（本原型的核心输出）：

| 命中源 | 置信度 | 含义 |
|---|---|---|
| 静态 + 运行时（+ 视觉） | **0.95** | 声明的控件确实在 |
| 仅运行时 | 0.70 | 现状基线（控件树单通道） |
| 仅视觉 | 0.65 | Canvas 类控件（控件树里没有） |
| **仅静态**（运行时没有） | **—** | 🔴 **差异告警** |

## 四、实测（真机同源数据）

**样本**：`com.example.myapplication`（我们自己的 hypium 模板工程，**有源码**）
**真机**：DAYU200 / OpenHarmony 5.0.3.135

### 4.1 真实场景：三源一致 ✅

```
源 1 静态：可用（1 项）
源 2 运行时：77 个节点
源 3 视觉：未配置视觉模型 key → **第三源未启用，本次融合降级为双源**

| 目标 | 类型 | 静态 | 运行时 | 视觉 | 置信度 | 位置 |
|---|---|---|---|---|---|---|
| `HelloWorld` | id | ✅ | ✅ | 未启用 | 0.95 | [150, 596, 571, 684] |

确认率 100.0% ｜ 差异告警 0 ｜ 运行时独有 24（系统控件，未声明）
```

**这是真实的同源对齐**：静态分析读出 `pages/Index` + 控件 `HelloWorld`，
真机运行时树里 `pagePath=pages/Index`、`id=HelloWorld` —— **两边对得上**。

### 4.2 告警机制：⚠️ **合成场景**（如实标注）

把运行时树里的 `HelloWorld` 节点**移除**（模拟控件丢失），静态声明不动：

```
确认率 0.0% ｜ **差异告警 1**

🔴 差异告警（源码声明了、运行时没有）
- **`HelloWorld`**（id）
  - 出处：`entry/src/main/ets/pages/Index.ets`
  - 判定：静态源码声明了该控件，但运行时控件树里找不到
  - 解读：很可能是真缺陷（控件丢失/改名）；也可能是条件分支或页面未加载完
```

> ⚠️ **这一段是刻意构造的**，用来演示告警机制，**不是真机上的真实缺陷**。
> 真机上目前**没有**捕获到真实的「控件丢失」案例 —— 这点必须如实说。

## 五、诚实声明（三条）

1. **视觉源未启用**：需要模型 key（`OHAUTO_VISION_*` / `OHAUTO_LLM_*`）。
   未配置时原型会**明确标注「第三源未启用」并降级为双源**，不会假装做过视觉。
2. **静态分析是正则级**（`tools/static_arkts/analyze.mjs`），不是 AST 解析 ——
   够用来做「声明了什么」的粗对齐，**不能当编译器用**。
3. **告警的合成性**：§4.2 是构造场景。**真机真实案例尚未捕获**。
4. **静态分析器的一个已修缺陷**（2026-09-24）：早先版本把所有含 `@Entry` 的 struct
   都当成页面路由，于是把 **`WidgetCard`（桌面卡片）** 也算了进去 ——
   实测该文件在 `pages/` 目录下、也有 `@Entry`，但它是
   `form_config.json` 声明的**卡片**，`main_pages.json` 里的应用内页面**只有 `pages/Index`**。
   现在按 `form_config.json` 排除卡片，`pages` 回到准确的 `['pages/Index']`。

   > 这个坑值得记：**如果不核实就照着这份清单派活**（"用静态声明的页面引导探索"），
   > 等于让探索器去追一个**根本进不去**的页面。**派活前必须先核实数据本身对不对。**

## 五之二、第二个用途：**用例健康度**（直接支撑挑战 #6）

同一套融合逻辑换个声明源就多了一个能力：把**用例引用的控件**当声明，
与运行时控件树对齐 —— **失效用例不用等真机跑挂，扫一遍就列出来**。

```bash
python tools/case_health.py --out _out/case_health.md
```

实测输出（用仓库里的真实用例 × 真机样本）：

| 用例 | 配到的样本 | 声明 | 确认 | 缺失 | 健康度 |
|---|---|---|---|---|---|
| `calculator.yaml` | sample_calc | 7 | 7 | 0 | **100%** |
| `note_stability.yaml` | app_note | 2 | 2 | 0 | **100%** |
| `login.yaml` | **（无样本）** | 7 | 0 | 7 | — |

两条真实用例都健康；`login.yaml` 是示例模板（`com.example.app` 不存在），
被正确地报成**覆盖缺口**而不是"健康" —— 这是本工具最要紧的一处设计：
**「没配到样本」和「验证通过」绝不能混为一谈**，混了就是自欺。

### 差异告警在**真实数据**上的有效性

用同一份用例跑三个不同样本（真实数据，不是合成的）：

| 组合 | 声明 | 确认 | 告警 | 说明 |
|---|---|---|---|---|
| `calculator.yaml` × **同应用**样本 | 7 | **7** | 0 | 同应用 → 全健康 |
| `calculator.yaml` × `app_settings` | 7 | 0 | **7** | 跨应用 → 全失效 |
| `calculator.yaml` × `sample_music` | 7 | 0 | **7** | 跨应用 → 全失效 |

这同时说明一件事：**用例必须记录它属于哪个应用** ——
换个应用跑就是 100% 失效，而融合器能**自动检出**这种错配。

## 五之三、多页面样本与探索覆盖率（真机实测）

为验证「静态声明能不能用于探索引导」，**先造了一个有源码的多页面应用**：
改造 `ohauto-hypium-test` 加了 2 个页面（`Second` / `Third`，含输入框、计数按钮、
回首页出口），`hvigor assembleHap` 构建（38 秒）→ `tools/sign_hap.py` 签名 →
`hdc install -r` 装机。

**静态分析读出**（`python tools/static_arkts/bridge.py`）：

```
页面路由 : ['pages/Index', 'pages/Second', 'pages/Third']     ← 3 个
源码跳转 : ['pages/Index', 'pages/Second', 'pages/Third']     ← router.pushUrl 提取
控件     : 13 个
```

**真机探索**（`python tools/explore_coverage.py`，137 秒、9 步动作）：

```
[explore] 起始页面 S1「Hello World」
[explore]   点击「进入第二页」-> S2「第二页」（新页面）
[explore]   点击「进入第三页」-> S3「第三页」（新页面）
[explore]   点击「加一」      -> S4「第三页」（新页面）
[explore]   点击「回到首页」  -> S5「Hello World」（新页面）
[explore] 探索结束：发现 8 个页面、9 条跳转
```

**探索器确实走遍了 3 个页面** —— 引导的价值在原理上成立。

### ⚠️ 但覆盖率算出来是 **267%** —— 这不是成功，是**口径不一致**

| | 口径 | 结果 |
|---|---|---|
| 静态声明的页面数（分母） | **路由**（`main_pages.json`） | **3** |
| 探索到的页面数（分子） | **内容签名**去重（`StateGraph.states`） | **8** |

同一页面因为「加一」让计数文本变了，被内容签名判成新页面 → 分子虚高。
**两个口径直接相除必然得出荒谬数字。**

**我让工具如实报出 267% 并打出警告**，而不是粉饰成一个"漂亮"的覆盖率 ——
宁可数字难看，也不能让它骗人。

### 这正好是给 B 的派活依据（有实测数据，不是想象）

`explorer.StateGraph.add_state` **只存内容签名的 hash、不保留 `page_path`**，后果：

1. **算不出真正的「页面覆盖率」** —— 用内容签名去重会把"同一页多状态"当成"多页"；
2. **列不出"具体漏了哪一页"** —— 只知道数量对不上，不知道缺谁。

`page_path` 是应用自报的路由，是**最硬的页面标识**（比内容签名、标题都硬），
而且它**已经在 `PageSignature` 里参与签名计算了**，只是没被 `PageState` 存下来 ——
改动量很小。

## 五之四、通用化：从「三源」做到「N 源」

### 先说原来哪里不通用（三个真问题）

| # | 问题 | 后果 |
|---|---|---|
| 1 | **静态源绑死 ArkTS 工程目录** | 设备上大多数应用**没有源码** → 这条直接废掉 |
| 2 | **页面 ↔ 文件靠路径字符串猜**（`stem in file.lower()`） | 换个工程结构（多 module / 非标准目录）就错 |
| 3 | **融合逻辑硬编码「静态 / 运行时 / 视觉」三条路** | 想加第四个源（OCR / 无障碍树 / 设计稿）**得改融合器本身** |

> 通用性**不来自把三条路写得更细**，而来自**契约**。

### 怎么改：契约驱动（`ohauto/fusion.py`）

抽象只有两个：

**① `Claim`** —— 一个源对「某处应该/确实存在什么」的一条主张：

```python
Claim(kind='id', value='HelloWorld', scope='pages/Index',
      confidence=0.9, evidence='entry/src/.../Index.ets')
```

任何源只要能产出 Claim 就能接进来 —— 它是不是"静态"、用什么语言写的，融合器不关心。

**② `role`** —— 源只分两类，**融合规则只认 role，不认源的名字**：

| role | 含义 | 典型源 |
|---|---|---|
| `declaration` | 「**应该**有什么」 | 源码、用例、设计稿、接口契约 |
| `observation` | 「**实际**有什么」 | 运行时控件树、视觉、OCR |

于是融合规则可以写成**与源无关**的三条 —— **这就是通用性的全部秘密**：

| 声明 | 观察 | 状态 |
|---|---|---|
| ✅ | ✅ | `confirmed` |
| ✅ | ❌ | **`missing`** 🔴 |
| ❌ | ✅ | `undeclared`（信息级） |

**加一个新源要做什么**：写一个 `source_xxx() -> SourceResult`。
**融合器一行不用改。** 现有适配器：`source_static_project` / `source_case` /
`source_runtime_tree` / `source_vision_stub`。

### 降级是一等公民

源不可用时**必须显式返回 `ok=False` + 原因**，不能静默给空列表 ——
否则「这个源没查到」和「这个源根本没运行」就分不清了，报告会骗人。

### 实测：三种场景都跑得通

| 场景 | 结果 |
|---|---|
| **有源码的应用** | 静态 + 运行时 → `HelloWorld` confirmed（1.00）；2 个未观察页面；**1 个真实缺失**（见下） |
| **没有源码的应用** | 静态源**如实报「未运行：该应用可能没有源码」**，并打出警告：**「不要把『缺源』读成『没问题』」** |
| **用例作声明源** | 7/7 confirmed（没源码的应用也能查「用例有没有失效」） |

### 顺带捕获到一个**真实**差异（不是合成场景）

场景 1 里：

```
🔴 声明了但没出现
- **btn_go_second**（id）
  - 声明方：static
  - 出处：entry/src/main/ets/pages/Index.ets
```

源码里 `Button('进入第二页').id('btn_go_second')` 明明白白声明了 id，
**但真机运行时树里找不到它** —— 印证了那个已知的真机现象：
**可点控件自身的 `id`/`text`/`descr` 常常全空**（文案在子节点上）。

这条差异的**实际意义**：说明「用 id 定位这个按钮」在真机上行不通 ——
对定位策略与用例生成有直接指导价值。**这是本项目第一次拿到真实（非构造）的差异样本。**

### 报告里的分类也是有讲究的

`missing` 不能一句「缺陷」了事，**不同 kind 含义完全不同**：

| kind | 缺失的含义 |
|---|---|
| `page` | **不是缺陷** —— 只是这次没访问到（报告里单列「未观察到的页面」） |
| `id` / `text` | 才是「声明了但运行时找不到」，可能真缺陷 |

## 五之五、第四源：OCR（接进来只写了一个适配器）

### 为什么 OCR 是**独立**的源，而不是重复控件树

控件树里的文字是**系统帮我们读出来的、与控件绑定的**文字；
OCR 读的是**画面上真实画出来的像素**。两者会分叉，而分叉有意义：

| 场景 | 控件树 | OCR | 说明 |
|---|---|---|---|
| 常规页面 | ✅ | ✅ | 两个观察源**交叉印证**（置信度更高） |
| **纯 Canvas 应用** | ❌ **一个字都没有** | ✅ | **OCR 是唯一通道** |
| 图片里的字 / 图标下的文字 | ❌ | ✅ | 同上 |
| 控件树文字与画面不一致 | 一套 | 另一套 | **冲突信号**（渲染未更新 / 被遮挡 / 文字被裁剪） |

### 铁证：`etsclock`（纯 Canvas 时钟应用）

同一个真机样本，两条通道看到的**完全不是一回事**：

| 画面上的内容 | 控件树 | 说明 |
|---|---|---|
| **`14:54:11`**（大号数字） | ❌ **读不到** | Canvas 绘制，没有对应控件 |
| **表盘刻度 1–12** | ❌ **读不到** | 同上 |
| `没有 SIM 卡` / `11%` / `02:54` | ✅ 读到 | 那是**系统状态栏**，不是应用内容 |

`etsclock` 的控件树实况：**77 个节点、0 个可交互、0 个 id**，
带文案的只有那 4 条状态栏文字 —— **应用自身的内容一个字都读不到**。

> 这正是「多模态」的立论基础：`app_settings` 那类页面是「有控件但没 id」，
> 而 `etsclock` 这类是**压根没有控件** —— 后者**只有视觉通道能看见**。

### ✅ 实测（2026-09-24，后端 rapidocr）

```
python tools/trifusion.py \
    --runtime-json datasets/real_samples_20260919/etsclock.json \
    --ocr-image   datasets/real_samples_20260919/etsclock.png
```

```
runtime  observation  ✅ 22 条主张（可见节点 77）
ocr      observation  ✅  7 条主张（rapidocr 经 venv 解释器读到 7 行）
```

**逐条比对**（这是本页最硬的证据）：

| 画面上的内容 | 控件树 | OCR | 说明 |
|---|---|---|---|
| **`14:54:11`** | ❌ **读不到** | ✅ **读到** | **应用的核心内容** —— Canvas 绘制，没有对应控件 |
| **`10` / `11` / `12`** | ❌ **读不到** | ✅ **读到** | 表盘刻度，同样是 Canvas 画的 |
| `11%` / `02:54` | ✅ 读到 | ✅ 读到 | **系统状态栏 → 两源交叉印证** |
| `没有SIM卡`（OCR） / `没有 SIM 卡`（控件树） | ✅ | ✅ | 同一个东西的两种读法（空格差异） |

结论：**「OCR 是纯 Canvas 应用的唯一通道」从推断变成了实测。**
而且交叉印证也真实发生了 —— 状态栏那两条被两个观察源同时读到。

> **顺手记一条装包教训**：`pip install winsdk` 在本机**卡了 12 分钟没完成**，
> 换 `rapidocr-onnxruntime` 用**清华镜像**（`-i https://pypi.tuna.tsinghua.edu.cn/simple`）
> **45 秒装完**。另外 `cmd | tail -N` 会把输出**全缓冲**，后台跑时看不到任何进度
> —— 直接 `> log 2>&1` 再 tail 日志才对。
>
> 也试过一条**零安装**的路：用 PowerShell 直接调 Windows 的 WinRT OCR（无需任何包）。
> 但本机安全策略**禁止从脚本调 PowerShell**（`Invoking PowerShell from Bash bypasses
> PowerShell security checks`），唯一入口又无回显 —— **无法集成进自动流程**，只能装包。

### 降级是一等公民（已实测）

本机没装 OCR 后端时，适配器**如实报**：

```
ocr   observation   未运行：未装任何 OCR 后端（试过 winsdk / pytesseract）
                     → 本次融合不含 OCR 源。装一个即可启用：
                     pip install winsdk（用 Windows 自带 OCR，无需模型）
```

**不会**静默返回空列表 —— 否则「OCR 没读到字」和「OCR 根本没跑」就分不清了。

### 后端可换

| 后端 | 依赖 | 说明 |
|---|---|---|
| `winsdk` | `pip install winsdk` | **用 Windows 自带 OCR 引擎，无需下载模型**（首选） |
| `pytesseract` | 需另装 tesseract 二进制 | 备选 |

`source_ocr(path, backend='auto')` 自动按顺序探测，都没有就降级。

### 加一个源的实际成本

```python
sources.append(fusion.source_ocr('shot.png'))   # 就这一行
```

**融合器一行没改** —— 这正是 §五之四 那套契约的目的。
`source_ocr` 与运行时源**同为 `observation` role**，
所以它天然参与「声明 vs 观察」的对齐，不需要任何特判。

## 五之六、第五源：视觉理解（VLM）

### 与 OCR 的分工 —— 刻意设计，不是重复

| | OCR（本地 rapidocr） | 视觉（云 VLM） |
|---|---|---|
| 成本 | **0**（本地算力） | 按 token |
| 离线 | ✅ | ❌ |
| 能力 | **只认字** | **认字 + 理解**（图标含义、页面意图、图表） |

**不建议用云模型替代 OCR** —— 那是花着钱做本地免费能做的事。
让 VLM 去干 OCR 干不了的：回答「这个图标是什么」「这一页是干什么的」
—— 正是**命题挑战 #1「理解页面意图」**要的东西。

所以视觉源把「问什么」做成参数（`instruction`）：默认只让它读文字（便于与其它源对齐），
问语义时换一句提问即可。

### DeepSeek 侧的正确配置（⚠️ 2026-09-24 核实，网上资料多有滞后的）

| 项 | 正确值 |
|---|---|
| **API 模型名** | **`deepseek-flash`** = **DeepSeek-V4.1-Flash**，**原生支持图像** |
| 已下线 | `deepseek-v4-flash-vision-exp`（**2026-09-10 下线**；旧名字仍被接受，**路由到 `deepseek-flash`**） |
| 不支持图片 | `deepseek-v4-pro` |
| 图片计费 | **最多 1024 input tokens / 图** |
| 需要的环境变量 | `OHAUTO_VISION_BASE_URL` / `_API_KEY` / `_MODEL`（或 `OHAUTO_LLM_*`） |

> **一条值得记的教训**：我最初搜到的资料写「只有 `deepseek-v4-flash-vision-exp` 接受图片、
> 每图 384 tokens」—— 那是 **9 月 10 日之前**的状态。**是用户指出「4.1 不也可以吗」之后
> 复查才发现的**：官方模型表已经更新，**`deepseek-flash` 才是当前能吃图的那个**，
> 且图片上限是 1024 tokens 而不是 384。
>
> **结论：凡是「当前哪个模型/接口可用」这类事实，搜索引擎给的很可能是过时快照，
> 必须多看几处来源交叉验证。**

### 复用而非重写

`source_vision()` 直接复用 `ohauto/vision.py` 的 `OpenAICompatibleProvider`
（里面已有 base64 编码、MIME 处理、结果解析），**没有另写一份 HTTP 调用**。
没配 key 时如实降级，并**在 reason 里提示该填哪个模型名**。

### 实测

| 项 | 结果 |
|---|---|
| 五源同跑 | ✅ `runtime` 22 条 + `ocr` 7 条 + `vision` 如实报「未运行」 |
| 降级提示 | ✅ 已修正为 `deepseek-flash`（原写成已下线的 exp 名字，是错的） |
| 测试 | ✅ 21 条（含**注入替身**的离线测试 —— 不联网也能测） |
