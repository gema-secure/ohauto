## 二、C-2 · 失败时留 dumpLayout 快照：**已实现**

### 改了什么

| 文件 | 改动 | 性质 |
|---|---|---|
| `ohauto/runner.py` | `StepResult` 加 `trees: List[str]` 字段；`to_dict()` 带上它 | **纯追加** |
| `ohauto/runner.py` | 新增 `Runner._capture_trees()`，在**判定失败**的那一刻抓 2 张 | 新增方法 |
| `ohauto/diagnose.py` | `from_step()` / `from_case_result()` 用 `setdefault` 自动继承 `step.trees` | **不覆盖调用方显式传值** |

### 三个设计选择（如果不同意，改起来都很小）

1. **抓两张**（失败瞬间 + 200ms 后）
   用来区分「控件自始不存在」（定位失败）和「界面还没稳定」（时序问题）——
   这正是 `diagnose._locator` / `_timing` 的判据前提。
2. **只抓失败步**
   成功步抓图会让 50 步用例凭空多出上百次 `dumpLayout`，还会挤爆 `artifact_budget`
   （产物轮转是按「失败优先」保护文件的，见 `_prune_artifacts`）。
3. **整段 try/except 包住**
   抓快照是旁路。它失败**绝不能改写原判定** —— 本来是 `LOCATE`，不能因为抓图失败
   变成「未知异常」。抓不到就留空列表，你的兼容分支照常走。

### 验证证据（`tools/verify_failure_snapshot.py`，可复跑）

同一条失败用例、同一份失败，分别按「有快照 / 无快照」归因：

```
① 运行器侧
  失败类别 : LOCATE
  快照数量 : 2      ← 0001_layout.json / 0002_layout.json 都在产物目录里落盘了

② 归因侧
  有快照   category=LOCATOR       confidence=0.85   ← 与你说的一致
           · 目标控件在 2 张控件树快照里都匹配不到
           · 落点页面与 expected_page 一致 → 页面是对的，控件不在，属于定位失败

  无快照   category=CASE_DEFECT   confidence=0.80   ← ★ 类别判错了
           · 落点页面与 expected_page 不符 → 用例缺少「先走到目标页」的步骤
           · 另一条候选判据「定位失败」置信度 0.60
```

### ★ 一个你没提到、但比置信度更严重的后果

没有快照时不只是「置信度低」—— **归因引擎会把类别判错**：
`LOCATOR` 被误判成 `CASE_DEFECT`。

根因：`_page_expectation()` 在没有快照时返回 `unknown`，而
`_case_defect()` 里「落点与 expected_page 不符」这条判据**把「没快照」当成了
「落点不符」**，于是给出「用例缺步骤」的结论。

**这条对 KPI 的影响**：归因准确率的分母里，这类样本会**稳定判错**而不是
「判对但置信度低」。你的 20/20 = 100% 是模拟数据上测的，那批数据自带快照；
真机一旦缺快照，准确率会掉得比置信度看起来的更狠。

已配 6 项单测守住（`tests/test_runner.py::TestFailureSnapshots`），
其中一条专门断言「有快照时类别必须是 `LOCATOR`」，防止哪天又静默退化。
