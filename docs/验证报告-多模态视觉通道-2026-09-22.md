> **项目**：面向 OpenHarmony 的多模态智能测试系统（a24）
> **被测对象**：`ohauto/vision.py` L3 语义层（视觉定位通道）
> **验证人**：C（兼队长 · 集成与质量）
> **日期**：2026-09-22
> **数据来源**：真机采集样本（DAYU200 / OpenHarmony 5.0.3.135 / 720×1280 / 2026-09-19）
> **工装**：`tools/eval_vision_offline.py`（零依赖，过 `static_check.py` 0 告警）

## 〇、结论摘要

| # | 结论 | 数字 |
|---|---|---|
| 1 | **视觉定位通道可用**，在真机截图上有可复现的定位能力 | 命中 **18/19 = 94.7%**（剔除 1 条无效标注，见 §6.1） |

## 一、⚠️ 方法与口径（先读这段，再看数字）

### 1.1 本报告测的是什么

评测集的标注**来自控件树自身的文案**，因此控件树通道在这个集合上是
**开卷考试**。所以：

- `IoU@0.5` / `中心命中` 衡量的是 **视觉通道与控件树通道的一致性**
  —— 即 `HybridLocator` 的交叉校验（`iou_threshold=0.3`）能否通过；
- 它**不是**视觉通道的绝对准确率。

绝对准确率必须在**控件树盲区**上测，而盲区没有自动标注（§5）。
本报告**不拿一致性数字充作绝对准确率**。

### 1.2 为什么不能拿别的数字代替

| 容易误用的数字 | 为什么不行 |
|---|---|
| 「模型能看懂图」的通用评测（如 Chartography / BabyVision） | 与本项目的**定位任务**不是同一件事 |
| 「控件树单通道 100%」 | 那是开卷成绩，且只在标注集上成立 |
| 「模拟设备上的结果」 | 真机上可交互容器**自身文案恒为空**，模拟夹具发现不了（§7.2） |

### 1.3 判定阈值

- `IoU@0.5`：通用严格口径
- `IoU@0.3`：与 `HybridLocator.iou_threshold` 保持一致
- `中心命中`：预测框中心落在标注框内，或标注框中心落在预测框内。
  **容器节点（648×57）与文字节点（48×22）天然不同尺寸，只报 IoU 会低估** ——
  实测正面案例：模型给的是文字框、标注是容器框，IoU 0.86 但中心命中。
  故本报告以 `中心命中` 为主判据。

## 二、被测对象与运行环境

| 项 | 值 |
|---|---|
| 视觉 Provider | `deepseek-flash`（= DeepSeek-V4.1-Flash，原生多模态） |
| 接入方式 | OpenAI 兼容 `/chat/completions`，`image_url` + base64 data URL |
| base_url | `https://api.deepseek.com` |
| 思考模式 | **关闭**（`{"thinking":{"type":"disabled"}}`，主测配置） |
| 采样参数 | `temperature: 0`（思考模式下该项**不生效**，见 §7.5） |
| 设备 | 润和 DAYU200，OpenHarmony 5.0.3.135，720×1280 |

**为什么关思考模式**：目标定位不需要长推理链。官方文档明写思考模式

`frequency_penalty` **设置不报错也不生效**（官方原文），等于我们在
「以为在求确定性、其实没有」的状态下评测。

## 四、结果

### 4.1 主结果（关思考模式）

| 范围 | n | 中心命中 | 平均 IoU | L1 免调模型 |
|---|---|---|---|---|
| **合计** | 20 | **90.0%** | 0.842 | 10.0% |
| 剔除无效标注后 | 19 | **94.7%** | — | — |
| `app_note` | 5 | 100.0% | 0.863 | 20.0% |
| `app_photos` | 2 | 100.0% | 1.000 | 0.0% |
| `app_settings` | 11 | 81.8% | 0.780 | 0.0% |
| `s_etsclock` | 2 | 100.0% | 0.974 | 50.0% |

> `app_settings` 的 81.8% 含 1 条**无效标注**（§6.1），修正后为 90.9%。

### 4.2 思考模式开 / 关对照（同一批 20 项）

| 指标 | 关思考 | 开思考 | 差异 |
|---|---|---|---|
| 中心命中 | 90.0% | 90.0% | 无 |
| 平均 IoU | 0.842 | 0.831 | 无显著差异 |
| **p50 延迟** | **1059ms** | 3238ms | 关掉快 **3.06×** |
| **20 条总耗时** | **34.5s** | 63.6s | 关掉省 **46%** |
| `temperature: 0` 是否生效 | **是** | **否** | 关掉才可复现 |
| 思维链计费 | 无 | 有（按**输出**计价，是输入的 4 倍） | 关掉更省 |

**两条配置在 20 项上失败的是不同条目**（开思考时「应用」对、「生物识别和密码」错；
关思考时相反）—— 说明**思考模式本身改变了模型行为**，不是随机抖动。

### 4.3 可复现性

同一配置（关思考）连续跑 3 次：

- **逐条命中/未命中完全一致**（3 次均为 18/20，失败的同样是「蓝牙」和「应用」，
  且「应用」返回的框完全相同）→ **判定结果可复现**
- 波动仅在**框的几何尺寸**：`app_note` 平均 IoU 0.863 / 0.817 / 0.817
  （同一目标一次 IoU=1.00、两次 0.77，均判为命中）→ **几何有 ±6px 级抖动**

> 结论写法建议：**「判定可复现，几何精度有轻微抖动」**。
> 不要写成「完全可复现」——IoU 会在第二轮浮动。

### 4.4 成本

| 项 | 值 |
|---|---|
| 单图 token | ≤ 1024（官方上限；720×1280 截图会缩放到约 1300×1300 量级） |
| 输入单价 | 1 元/百万 token（空闲时段）/ 2 元（高峰） |
| 输出单价 | 4 元/百万 token（空闲）/ 8 元（高峰） |
| **一轮 20 条的实际花费** | **不到 1 毛钱** |

真机上**可交互控件自身几乎没有文案**：

| 样本 | 可交互 | 人话文案可用 | 仅 id | 无任何标识 |
|---|---|---|---|---|
| `app_note` | 12 | 10 | 0 | **2** |
| `app_photos` | 3 | 3 | 0 | 0 |
| `app_settings` | 28 | 28 | 0 | 0 |
| `etsclock` | 0 | 0 | 0 | 0 |
| `s_etsclock` | 5 | 4 | 1 | 0 |
| `sample_calc` | 20 | **0** | **19** | **1** |
| `sample_music` | 5 | 1 | 0 | **4** |
| **合计** | **73** | **46** | **20** | **7** |

**盲区 = 27/73 = 37.0%** —— 这些控件人话文案不可用，控件树通道给不出

> ⚠️ 待办：这 27 个控件**只能人工标注**才能测出视觉的绝对准确率。

## 六、失败归因

### 6.1 「蓝牙（app_settings）」—— **标注无效，模型无辜**

| 项 | 内容 |
|---|---|
| 模型原话 | `[]`（三次运行稳定复现） |
| 初判 | 「模型认不出蓝牙」 |
| **实情** | 让模型念一遍整页文字（15 处）后发现：**清单里根本没有「蓝牙」，第一项是「移动网络」** |

逐行对齐控件树与画面文字：

| 控件树文案 | 控件树给的 rect | 该位置画面上的文字 | 判定 |
|---|---|---|---|
| 蓝牙 | `(42,72,678,122)` | **设置**（页面标题） | ⚠️ 不一致 |
| 蓝牙 | `(36,156,684,213)` | **移动网络** | ⚠️ 不一致 |
| 移动网络 | `(42,123,678,207)` | 移动网络 | ✅ |
| 显示与亮度 → 关于设备（11 行） | — | 全部同名 | ✅ |

**结论**：`app_settings` 的「蓝牙」那一行**在截图上不存在**。控件树里那两层
rect（内层 y=72~122 正好压在标题区、外层 y=156~213 正好是「移动网络」的位置）
是**没有画面依据的残留坐标**。

- 模型返回 `[]` 是**正确**行为
- 该条从评测集剔除 → 18/19 = **94.7%**
- 根因指向**采集流程**：`dumpLayout` 与 `screencap` 的时机可能不同（见 §7.3）

### 6.2 「应用（app_settings）」—— **真实模型错误 + 过度自信**

| 项 | 内容 |
|---|---|
| 模型原话 | `[{"label":"应用","bbox":[42,465,678,549],"confidence":0.95}]` |
| 标注 | `(42,550,678,634)` |
| 实际返回 | `(42,465,678,549)` = **上一行**（生物识别和密码） |
| 置信度 | **0.95** |

且模型自己在「念页面」任务里把「应用」定在 `(114,556,180,588)` ——
**与控件树标注一致**。也就是说：

> 同一张图、同一个目标，模型**两路输出相差 65px**，定位那一路是错的。

这条既暴露了模型的定位不稳定，也指出一个**可落地的改进方向**（§8.2）：
把「念页面」作为第二路信号与定位结果交叉校验。

## 七、发现的缺陷（按严重性排序）

### 7.1 🔴 控件树：嵌套 `List` 的内层子项坐标未叠加外层偏移

| 项 | 内容 |
|---|---|
| 现象 | `app_settings` **14 个节点越出父容器，最大 84px**（其余 6 个样本为 0） |
| 原始 bounds | `List[42,156][678,207]` → 子项 `ListItem[42,72][678,122]` |
| 逻辑矛盾（无需主观判断） | ① 子节点不在父容器内；② 该 bbox 与页面标题「设置」`[36,72][684,156]` **重叠** |
| 后果 | 按控件树坐标点「蓝牙」会落到 y≈97（标题区），真实行中心 y≈184 —— **点错控件** |
| 已核验 | 手工核对原始 JSON，确认非解析问题 |
| 处理 | 工装自动检测并把这些项剔出评测集（计入 `坐标可疑`） |

### 7.2 🔴 `ohauto/vision.py` 线索漏拼子树文案 → A4 成本分层失效

| 项 | 内容 |
|---|---|
| 位置 | `TieredVisionLocator._hints()` / `HybridLocator._hints()` 只送 `n.text`（自身） |
| 实测 | 送进模型的 **28 条线索文本全为空**（真机上可交互容器自身文案恒为空） |
| 连带 | `_static_candidates()` 对「蓝牙」命中 **0** 条 → **L1 永远免不了调模型** |
| 后果 | 18/20 条打到最贵的 L3 全屏；A4 的「三层成本递增」**实际退化成单层** |
| 另 | `HybridLocator` 树通道构造的 blob 同样不含 `text_deep`（实测对「蓝牙」判定 `False`） |

**⚠️ 这里有一个必须说清的细节：只补文案并不省模型调用。**
`TieredVisionLocator` 的 L1 只在**唯一命中**时才免调模型；补上 `text_deep` 后
**容器节点也会命中**（容器的 deep 文案包含子项文案），多条命中 → 照样升级 L2。
同一批 20 项实测四种路线（这就是给 A 的改动菜单）：

| 路线 | L1 免调模型 | 其中答案正确 | 说明 |
|---|---|---|---|
| A 现状（仅自身文案，须唯一） | 10.0% | — | 现状 |
| B 补 `deep`，仍须唯一 | 10.0% | — | **补文案单独不省调用**（必要条件，非充分） |
| C 补 `deep` + 剔容器，须唯一 | 20.0% | — | 提升有限 |
| **E 补 `deep` + 取最紧匹配 + 文案须与指令完全相等** | **70.0%** | **14/14 = 100%** | 保守，零错误 |
| **D 补 `deep` + 取最紧匹配** | **100.0%** | 19/20 | 激进；唯一错例是「蓝牙」，而该条 GT 已被证明无效（§6.1）→ **剔除后 19/19 全对** |

**修法**（详见 `docs/给A-线索漏拼子树文案-2026-09-22.md`）分两步，缺一不可：
1. 线索里补 `'deep': n.text_deep`，匹配键列表加上 `deep`；
   `HybridLocator` 的 blob 追加 `n.text_deep`；
2. **把 L1 的判定从「必须唯一」改为「取最紧的匹配」**（路线 D 或 E）
   —— 这一刀才是真正省下模型调用的地方。

### 7.3 🟠 采集流程：`dumpLayout` 与 `screencap` 时机可能不一致

控件树里存在**没有画面依据的坐标**（§6.1）→ 最可能的解释是
**两次采集之间页面发生了滚动或布局变化**。

影响面：**凡受滚动/动画影响的样本，控件树坐标都不可信** ——
而它正被当成 ground truth 使用。这比单个模型错误严重，因为它会**系统性**
污染所有后续评测。

**建议**：① 查 `tools/capture_app.py` 的采集顺序；② 采集时加
「dump 与截图一致性自检」（§8.1 的 `--read-page` 就是它的雏形）。

### 7.4 🟡 模型：会把目标定位到相邻行，且高置信度

见 §6.2。两次关思考运行**完全复现**（同一错框），属系统性错误。

### 7.5 🟡 模型：`bbox` 与自身 `label` 可能矛盾（框复用）

实测两组（见 `_out/vision_eval/vision_compare.md`）：同一轮里
**两个不同指令收到同一个框**（IoU=1.00），模型还给它们贴了不同 label。
`应用` 就是这种情况。

这类错误单看每行 IoU 看不出来（位置往往是邻行的真实位置），
工装已加常驻检查 `find_box_reuse()`，并用已有数据回验（两份报告各检出 1 组）。

## 九、局限性与未验证项（必须如实声明）

1. **不是绝对准确率**。本报告的 94.7% 是「视觉与控件树的一致性」。
   绝对准确率需在盲区（§5）上测，尚未进行。
2. **样本量小**：19 条有效评测项、4 个应用。`app_photos` 仅 2 条、
   `s_etsclock` 仅 2 条，分样本数字的置信度低。
3. **只测了定位任务**。页面意图 / 核心操作入口 / 潜在测试路径
   （命题挑战 #1 后半句）的工具已就绪但**未跑未复核**。
4. **只测了一个模型**。未做跨模型对照（`VisionProvider` 是抽象层，
   换模型只需改环境变量，但未实测）。
5. **未在盲区上评测**，因此**不能**宣称「视觉通道能覆盖那 37%」——
   只能说「控件树在那 37% 上给不出描述性定位」。
6. **几何精度有抖动**（§4.3），单条 IoU 不宜作为精细指标引用。
7. **未做真机端到端**。本报告是**离线**验证（复用 2026-09-19 的采集样本），
   不包含「视觉定位 → 真机点击 → 结果校验」的闭环 —— 那需要设备在线。
