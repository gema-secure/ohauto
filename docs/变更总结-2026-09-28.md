## 二、修改的既有代码（重点复核区）

### 2.1 `ohauto/explorer.py` —— tarpit 防粘滞（B 复核）

| 位置 | 改动 |
|---|---|
| 模块 docstring | 增补 tarpit 一条 |
| 新增段「★ Tarpit 防粘滞」 | `content_similarity(a, b)`（控件行 Jaccard）+ `TarpitPolicy`（enabled / sim_threshold=0.90 / max_family_states=4，`__post_init__` 校验） |
| `Explorer.__init__` | 新增 keyword 参数 `tarpit_policy=None`（向后兼容）；新增 `_tarpit_family` 台账与 `tarpit_hits` 公开列表 |
| 新增方法 | `_tarpit_judge(new_sig, cur_sig)`（两条拦截判据：成对相似度 / 同族封顶，返回可解释原因）、`_tarpit_note(sig)` |
| `explore()` | fresh 分支重构：**先判定、再登记**；被拦截的状态照加、边照记（note=`tarpit 不入队：<原因>`）、**不入队**；结束日志追加拦截计数 |
| `save_graph()` | 产物新增 `payload['tarpit'] = {policy, hits}` |

**设计红线**：拦截只影响「要不要入队探索」，**不影响记账** —— 状态、边、
相似度与原因全部落盘，报告查得到「为什么没探这一页」，绝不静默。
默认开启；`Explorer(driver, tarpit_policy=TarpitPolicy(enabled=False))` 完全恢复旧行为。

### 2.2 `ohauto/diagnose.py` —— 单快照空真缺陷修复（B 复核，★ 本会话唯一一处判据修改）

- **现象**：A6 扩容样例「C9 目标控件 disabled（定位形态）」被误判为
  时序问题(0.75)，而同形态的 ASSERT 版（C5）正确判为用例缺陷。
- **根因**：时序判据②「目标在失败后的快照里才出现」中，
  `present_early = any(_find_in_tree(target, r) for r in trees[:-1])` 在
  **单快照**记录下对空序列恒为 `False`，于是「目标就在唯一的快照里」
  被误读成「失败后才出现 → 界面没稳定」。
- **修法**：该判据加守卫 `len(trees) >= 2`（"晚到"至少要两张快照才说得通），
  修法处有注释写明来龙去脉。修复后该形态按「控件在树里但不可用」正确归
  **用例缺陷**。
- **回归钉**：`test_single_snapshot_cannot_claim_late_appearing`
  （断言：单快照不得判 TIMING，且判 CASE_DEFECT）。
