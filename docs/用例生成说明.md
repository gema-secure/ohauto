# 用例生成说明 —— 自然语言生成可执行用例

本文说明系统的自然语言生成用例模块：输入一句中文功能描述，输出一条可执行的
YAML 用例（Action DSL）。代码位于 `ohauto/generator.py`，最小示例见
`examples/generate_demo.py`。

生成评测的当前结论：26 条描述（24 条正样本 + 2 条固定负样本）在真机上的
静态可执行率为 92.3%（24/26），两轮复跑结果一致；可执行用例中引用真实控件
与断言的比例为 24/24。示例部分使用 ScriptedProvider（脚本化 Provider），
完全离线、可复现、不需要模型 key，用于演示链路与校验逻辑。

## 一、解决的问题

```
输入：验证登录页：输入账号密码后点击登录，应能进入首页

输出：
name: 登录页基本检查
bundle: com.demo.app
ability: EntryAbility
steps:
- start: true
- waitIdle: true
- tap:
    id: btn_login
- assert:
    exists:
      text: 登录
```

产出的 `Case.to_dict()` 可直接交给 `action.load_case()` 与 `runner.run()` 执行，
生成与执行之间不引入额外格式。

由模型直接输出脚本的失败模式集中且可预见：编造不存在的控件、使用硬编码坐标、
使用固定等待。因此生成流程设计为六阶段流水线：模型只承担拆解测试点与撰写草案
两步，可执行性由其后的确定性校验与修复代码保证。

## 二、六阶段流程

```
                ┌─────────────────────────────────────────────┐
 一句中文描述 ─→ │ ① 描述 → 测试点       (LLM)                 │
                │ ② 测试点 → DSL 草案   (LLM + 控件清单)      │
                │ ─────────── 以下为确定性代码 ───────────     │
                │ ③ 静态校验           红线扫描+DSL+控件存在性 │
                │ ④ 修复               本地启发式 → 必要时 LLM │
                │ ⑤ 再校验             （回到 ③，最多 max_repair 轮）
                │ ⑥ 干跑               只执行无副作用步骤      │
                └─────────────────────────────────────────────┘
                                    ↓
                         GenerationOutcome（成功或失败均留痕）
```

| 阶段 | 入口 | 输入 | 输出 | 代码 |
|---|---|---|---|---|
| ① 测试点 | `Generator.plan()` | 描述 | `List[TestPoint]` | `generator.py:1094` |
| ② 草案 | `Generator.draft()` | 描述 + 测试点 + 控件清单 | `Case` | `generator.py:1099` |
| ③ 校验 | `validate_case()` | `Case` + 控件树 | `List[ValidationIssue]` | `generator.py:734` |
| ④ 修复 | `repair_locally()` → LLM | `Case` + 问题清单 | 修复后的 `Case` | `generator.py:859` |
| ⑤ 再校验 | 同 ③ | | | `generator.py:1196` |
| ⑥ 干跑 | `dry_run()` | `Case` + `driver` | `DryRunResult` | `generator.py:826` |

一站式入口 `Generator.generate()` 一次执行六阶段并返回 `GenerationOutcome`
（`generator.py:1127`）；需要裸 `Case` 时使用 `generate_case()`（失败抛出
`GenerationError`）；批量场景使用 `generate_many()`（返回 `GenerationReport`）。

## 三、阶段说明

### 阶段① 描述 → 测试点

模型按六个维度分别输出测试点（`TestPointKind`，`generator.py:57`）：
功能、边界、异常、界面、性能、兼容性。提示词要求每个维度给出 0–3 条，
并明确要求不书写具体控件 id——该阶段尚未提供控件树，模型无法得知真实 id。

模型输出的维度名可能使用同义词（如"主流程"、"negative"），
`_KIND_ALIASES` 将其归一到六类，无法归类的标记为 UNKNOWN
（`generator.py:68`）。

JSON 解析失败时由 `parse_test_points_lenient()` / `fallback_test_points()`
正则兜底（`generator.py:434` / `350`），不因格式瑕疵放弃整条描述；
兜底仍无法取得测试点时，返回 `RejectReason.NO_TEST_POINT`。

### 阶段② 测试点 → DSL 草案

本阶段的关键输入是控件清单（`catalog_fn`）：提示词限定模型只能从清单中
引用控件。清单由 `control_catalog(page)` 生成（`generator.py:507`），
可替换为 `ohauto.treesum.control_catalog` 以获得更完整的清单
（见"接入真实模型与真机"一节）。

提示词包含注入防护（`generator.py:588`）：控件清单来自被测应用界面文案，
属于不可信输入——界面完全可能包含"忽略以上指令"之类的文字。清单被包入
`<app_content>` 数据区，并附声明说明区域内内容均为数据而非指令，
同时过滤 `<app_content>` 伪标签以防区域提前闭合。该边界由单元测试断言。

模型返回的 JSON 经 `parse_json_payload()` 容错解析后进入
`_case_from_payload()`；schema 不符返回 `RejectReason.SCHEMA`，
步骤为空返回 `RejectReason.EMPTY`。

### 阶段③ 静态校验

`validate_case()` 执行以下检查，每项对应一类可执行性缺陷：

| 检查 | 拦截内容 | reason |
|---|---|---|
| 红线扫描一 | `tap_xy` 及参数中的 `x` / `y` / `startX` 等坐标 | `HARDCODED_COORD` |
| 红线扫描二 | `sleep` / `wait` / `delay` / `pause` / `waitMs` 固定等待 | `HARDCODED_WAIT` |
| DSL 合法性 | 动作名不在 `LEGAL_ACTIONS` 内 | `DSL_INVALID` |
| 匹配器可解析 | `spec_to_matcher()` 抛出 `DslError` | `DSL_INVALID` |
| 控件存在性 | 引用的控件在当前树中 `filter()` 为空 | `CONTROL_MISSING` |
| 起始步骤 | 第一条不是 `{"start": true}` | `DSL_INVALID` |

起始步骤必须为 `start`：不先启动应用，用例没有确定的初始状态，
可重放性无从谈起（`generator.py:752`）。

跨页面用例的后置步骤可能引用尚未出现的控件，`validate_case()` 提供
`allow_missing_controls=True` 只执行红线与 DSL 校验，
控件存在性留给干跑阶段判定。

### 阶段④ 修复

顺序为先本地启发式修复，再考虑调用模型（`generator.py:1196`）。

`repair_locally()` 处理三类问题（`generator.py:859`）：

| 问题 | 修法 |
|---|---|
| `tap_xy` / 坐标参数 | 替换为同位置控件或同类型第 n 个控件的匹配器 |
| 固定等待 | 替换为 `waitIdle` |
| 控件 id 不存在但树中有同前缀 / 同类型控件 | 替换为该控件 |

无法本地修复的问题原样保留，由上层决定是否调用模型或判定不可执行。
调用模型的条件收紧为存在 `CONTROL_MISSING` 或 `DSL_INVALID` 等
可通过修改 DSL 解决的问题（`generator.py:1206`）；
回写使用 `build_repair_prompt()`，要求最小改动。

### 阶段⑤ 再校验

修复后重新执行 `validate_case()`，最多 `max_repair` 轮（默认 1）。
仍有 fatal 问题时带原因返回，不静默通过。

### 阶段⑥ 干跑

只执行无副作用步骤（`generator.py:826`）：

- 实际执行：`waitFor` / `waitGone` / `waitIdle` / `assert`（只读操作，
  验证等待与断言是否成立）
- 全部跳过：`tap` / `input` / `swipe` / `start` / `back` / `key`
  （`SIDE_EFFECT_ACTIONS`）

`DryRunResult` 报告 `executed` / `skipped` / `failures` 三个计数。
断言失败计入干跑失败，但 `kind` 标记为 `'assert'` 而非 `'error'`——
断言不成立与用例书写错误的修复方向不同。

## 四、最小示例（离线，不需要模型 key）

执行 `examples/generate_demo.py`：

```bash
python examples/generate_demo.py
```

该示例使用 `ScriptedProvider` 固定模型回复以保证可复现，并刻意构造
两处违规，使校验与修复阶段真实执行。输出摘录（可当场重跑）：

```
阶段① 描述 → 测试点清单
  [功能] 正常登录  期望=点击登录后进入首页
  [异常] 空密码登录  期望=给出错误提示且停留在登录页

阶段② 测试点 → DSL 草案
  1. {'start': True}
  2. {'sleep': 2}                          ← 违规：固定等待
  3. {'tap_xy': {'x': 300, 'y': 770}}      ← 违规：硬编码坐标
  4. {'assert': {'exists': {'text': '登录'}}}

阶段③ 静态校验（红线扫描 + DSL 合法性 + 控件存在性）
  [硬编码等待（违反红线）] 第 2 步：固定等待 sleep，应改用 waitFor / waitGone 等具名等待
  [硬编码坐标（违反红线）] 第 3 步：tap_xy（硬编码坐标），折叠/旋转/滚动都会使坐标失效，必须改用匹配器定位
  -> 共 2 处问题

阶段④ 本地修复（先于模型调用）
  第 2 步：固定等待 → waitIdle
  第 3 步：硬编码坐标 → 匹配器 {'id': 'btn_login'}

阶段⑤ 再校验
  剩余问题：0 处

阶段⑥ 干跑
  干跑结论: ok=True ｜ 实际执行 2 步 ｜ 跳过 2 步

一站式 API：Generator.generate()
  ok=True ｜ 可执行=True ｜ 修复过=True ｜ attempts=1
```

阶段③ 捕获两处红线违规；阶段④ 未消耗任何模型调用完成修复，
`tap_xy {'x':300,'y':770}` 被替换为 `{'id': 'btn_login'}`；
阶段⑥ `executed=2 / skipped=2`：`waitIdle` 与 `assert` 实际执行，
`tap` 与 `start` 未被触发。完整输出（含 `to_dict()` JSON）可复现，
产物落盘于 `examples/_out/generate_demo/case.yaml`。

## 五、生成侧的红线执行

| 红线 | 执行方式 |
|---|---|
| 禁止硬编码坐标 `tap_xy` | 阶段③ 扫描 → `HARDCODED_COORD`；阶段④ 替换为匹配器 |
| 禁止固定等待 | 阶段③ 扫描 → `HARDCODED_WAIT`；阶段④ 替换为 `waitIdle` |
| 控件必须真实存在 | 阶段③ `CONTROL_MISSING`（对当前控件树 `filter()`） |
| 不发明动作名 | 阶段③ 对 `LEGAL_ACTIONS` 校验 |

上述问题在阶段③ 均产出 `fatal=True` 的 issue，带原因返回，不静默放行；
可执行性由阶段④ 的修复保证——仅报告不修复不能构成拦截。

## 六、接入真实模型与真机

### 接入真实模型

```python
from ohauto.generator import Generator, default_provider

gen = Generator(provider=default_provider(),   # 按环境变量构建；未配置时抛错
                bundle='com.demo.app', page=tree)
```

环境变量（key 只经环境变量传递，代码无默认值）：
`OHAUTO_VISION_*` > `OHAUTO_LLM_*` > `OH_LLM_*`。
每组含 `BASE_URL` / `API_KEY` / `MODEL` 三项，任一组配齐即可，组内不混搭；
视觉与用例生成共用同一服务时只配置一组 `OHAUTO_LLM_*`。

### 更换控件清单实现

```python
Generator(provider=..., catalog_fn=ohauto.treesum.control_catalog)
```

签名与内置 `control_catalog(page, limit=60)` 一致，一行替换。
treesum 版本同时覆盖 id 与文案，自身无文案的容器会借子节点文案
（`deep="…"`）；在无 id 的页面上，内置清单会明显退化。

### 连接真机执行

```python
from ohauto.driver import Driver

d = Driver(bundle='com.demo.app', hdc=..., artifact_dir='...')
tree = d.refresh()
gen = Generator(provider=..., bundle='com.demo.app', page=tree)
out = gen.generate('验证登录页：…', page=tree, driver=d)   # 传入 driver 才执行阶段⑥
```

真机执行的两项前置事实：`aa start` 会复用既有实例，启动前应先 force-stop
再启动以保证回到入口页；设备息屏时 `dumpLayout` 会返回近乎空白的树且不报错，
长时间用例应使用 `runner.py` 的 `DeviceGuard.ensure_awake()` 维持亮屏。

## 七、批量生成与统计

```python
rep = gen.generate_many(descriptions, page=tree, driver=d)
print(rep.executable_rate, rep.reasons_cn())
```

`GenerationReport`（`generator.py:1016`）字段：

| 字段 | 含义 |
|---|---|
| `executable_rate` | 可执行条数 / 总条数 |
| `repaired` | 经修复后才可执行的条数（修复器贡献度） |
| `reasons_cn()` | 不可执行原因的中文分类 |
| `ok(target=0.80)` | 验收判定：可执行率是否达到目标值 |

批量生成默认开启预取（`generate_many`，`generator.py:1270`）：处理第 i 条时
并发请求第 i+1 条，避免 N 条串行等待。连续失败达到
`max_consecutive_failures`（默认 3）时终止整批并保留已产出的结果。

## 八、不可执行原因分类

`RejectReason`（`generator.py:85`），`cn` 属性为中文名称：

| reason | 中文 | 归属 |
|---|---|---|
| `PROVIDER` | 模型调用失败（超时 / 网络 / 空回复） | 环境 / 网络 |
| `SCHEMA` | 输出不符合 schema，兜底解析失败 | 模型 |
| `NO_TEST_POINT` | 第一阶段未产出可用测试点 | 模型 |
| `EMPTY` | 第二阶段产出步骤为空 | 模型 |
| `DSL_INVALID` | 步骤名或参数不是合法 DSL | 模型（可本地修复一部分） |
| `CONTROL_MISSING` | 引用的控件不在控件树中 | 模型（可本地修复一部分） |
| `HARDCODED_COORD` | 使用硬编码坐标（红线） | 模型（可本地修复） |
| `HARDCODED_WAIT` | 使用固定等待（红线） | 模型（可本地修复） |
| `DRYRUN_FAILED` | 干跑失败且修复无效 | 用例本身 |
| `UNEXPECTED` | 未预期异常（降级为单条失败，不中断整批） | 框架 |

## 九、接口索引

| 需求 | 接口 |
|---|---|
| 只拆测试点 | `Generator.plan(desc)` |
| 只取草案 | `Generator.draft(desc, point, page)` |

## 十、设计要点

模型只承担拆解测试点与撰写草案两步；可执行性由静态校验、修复与干跑三段
确定性代码保证。硬编码坐标与固定等待两条红线在生成侧被拦截并修复，
`GenerationReport` 对全部失败给出可分类的原因。
