# 执行引擎健壮性 —— 实测记录

> 面向 OpenHarmony 的多模态智能测试系统 · 实测记录
> 验收标准：**50 步连续执行成功率 ≥ 95%**

---

## 一、结论

**本项已完成并通过验收。** 真机 **50 步连续执行 100%**、**200 步长跑 100%**（近 7 分钟零重试、零设备恢复）。

但比数字更重要的是：**本轮在实现过程中挖出 4 个会让「连续执行」静默失效的设计缺陷**（第四节），其中 2 个属于「用例跑通过了但实际没测到」的假通过类型 —— 如果不做这一项，这些问题会一直潜伏到决赛演示当天。

---

## 二、这一版解决的问题

`driver.py`（前置能力）解决「**一步**怎么做对」。本版解决「**一百步连续做，还能不能做完**」。

真机连续执行会遇到三类问题，原来的单步执行器（`action.run_steps`）一个都处理不了：

| 问题 | 现象 | 原执行器行为 | 本版行为 |
|---|---|---|---|
| **偶发失败** | 控件还在动画里没渲染出来、hdc 命令偶发超时 | 直接判定用例失败 | 分类后分级重试，退避等待 |
| **设备失联** | 跑几十步后 hdc daemon 卡死、设备掉线 | 重试单步毫无意义，一路报错到底 | 触发连接级恢复（心跳→重启 hdc 服务） |
| **级联失败** | 第 5 步真挂了，第 6~50 步跟着全挂 | 上报 46 个失败，成功率被拉到 8% | 识别级联，区分「原始成功率」与「独立成功率」 |

## 四、★ 挖出并修复的 4 个设计缺陷

### 4.1 设备掉线被静默降级成「界面有点慢」

**这是本轮最有价值的发现。**

`Driver._signature()`（用于判断界面是否稳定的控件树签名）原本这样写：

```python
try:
    root = self.refresh()
    ...
except Exception:
    return f'<err:{time.time()}>'      # 一律吞掉
```

后果链条：

1. 设备掉线 → `refresh()` 抛 `DeviceNotFound`
2. `_signature` 吞掉它，返回一个带时间戳的错误串
3. `wait_idle` 发现签名每次都不同（时间戳在变），**永远判不出「稳定」，返回 False**
4. 但所有调用方（`tap` / `input` / `start` … 共 10 处）**都忽略了 `wait_idle` 的返回值**
5. 于是设备掉线被静默降级成「界面有点慢」，**用例照常报通过**

**本版的设备自愈因此永远等不到触发时机** —— 因为上层根本不知道设备出事了。

修复：异常处理分级。

```python
except DeviceNotFound:
    raise                              # 设备没了，立刻上报，让上位机接管
except Exception:
    self._sig_errors += 1
    if self._sig_errors >= self.idle_error_tolerance:   # 默认 3
        raise                          # 连续取不到签名 = 不是抖动
    return f'<err:{time.time()}>'      # 偶发抖动，本次签名作废
```

单次抖动仍然被吸收（这正是本版要做的），但连续失败必须冒泡。

### 4.2 传输层断了，重启被测应用毫无用处

原本的恢复流程是「轻量重试 → 重启 hdc 服务 → 重启应用」，一路往下兜。

实现过程中发现：**待恢复流程走到「重启应用」时，它自己也验证不了结果** —— 因为验证「界面回来了没有」同样要走 `hdc shell` 读控件树。壳都断了，重新拉起应用只是徒劳，还可能把已经崩掉的现场抹掉。

修复：**按失败类型分流**。

| 失败类型 | 真正管用的处置 | 理由 |
|---|---|---|
| `DEVICE` | 重启 hdc 服务（`kill -r`）+ 等设备重连 | 传输层问题只能在传输层解决 |
| `APP` | 重新拉起应用，把界面拉回起点 | 传输层是好的，只是应用崩了 |

另外：`APP` 类失败即便传输层健康也**必须真的重启应用**，不能走轻量路径蒙混过关 —— 单测里专门有一条盯这个。

### 4.3 锁屏会让控件树突然全空

实测（DAYU200 / OpenHarmony 5.0.3.135）：**设备默认几十秒就息屏，息屏后回到锁屏界面，而锁屏界面不进无障碍树** —— `dumpLayout` 只返回 1 个 `bounds = "[0,0][0,0]"` 的根节点。

50 步连续执行要跑几分钟，不处理这个问题就会出现「跑到一半控件树突然全空」。这个现象**看起来像引擎崩了**（或像应用崩溃），极难从报错反推 —— 实际只是屏幕黑了。

修复：新增 `DeviceGuard.ensure_awake()`，在批量执行前调用一次：

```bash
hdc shell power-shell wakeup                       # 唤醒
hdc shell power-shell timeout -o 1800000           # 把息屏超时覆盖成 30 分钟
hdc shell uitest uiInput swipe <x> <0.9h> <x> <0.35h> 600   # 必要时上滑解锁
```

配套新增 `DeviceGuard.has_window()`：用「控件树节点数是否 > 1」判断当前有没有窗口。这条判据把「**根本没有窗口**」和「**窗口在但控件没找到**」区分开了 —— 两者的处置完全不同（前者唤醒解锁，后者改定位条件）。

`examples/run_suite.py` 开跑前自动执行，无需手工处理。

### 4.4 级联基线不会重置，会掩盖第二个真缺陷

级联识别的初版逻辑是「本步失败类别 == 首个失败类别 → 判为级联」。

问题：如果第 5 步挂了、第 6 步又成功、第 7 步再挂（同样类别），第 7 步会被错误地挂到第 5 步头上 —— **那会掩盖一个真实存在的独立缺陷**。

修复：**中间只要成功过一次，就重置基线**。成功说明应用恢复了，之后的失败属于新问题。

### 5.1 真机 50 步连续执行（主验收）

```

总步数            : 50
通过              : 50
失败              : 0（其中级联 0）
独立成功率        : 100.00%   ← 验收口径（阈值 95%）
结论：达标
```

### 5.2 真机 200 步长跑

```
用例：cases/note_stability.yaml × 20 轮（每轮 10 步）
设备：润和 DAYU200 / OpenHarmony 5.0.3.135 / 720×1280
耗时：6 分 49 秒

总步数            : 200
通过              : 200
失败              : 0（其中级联 0）
独立成功率        : 100.00%
重试尝试次数      : 0
设备恢复          : 0 次自动恢复，0 次重启 hdc 服务
结论：达标
```

**读法**：200 步跑满近 7 分钟，横跨多次息屏周期（已由 `ensure_awake` 钉住屏幕），全程**零重试、零恢复**。

这有两层含义：

- **好的一面**：引擎与设备都很稳，裕度充足。本版的验收标准（≥95%）不只是「刚好达到」，而是以 5 个百分点以上的余量达成。
- **需要如实说明的一面**：本次运行**没有出现偶发失败**，所以重试与设备自愈机制在真机上**未被触发**。它们的正确性由 5.3 的注入式对照实验保证，而不是由这次真机跑分保证。

另外，最慢的 5 步全部是同一个动作（`tap id=searchInput`，约 5.7 秒）。这个耗时构成是：定位（1 次 `dumpLayout`，约 0.7s）+ 注入点击 + `wait_idle`（2~3 轮签名比对 + 350ms 间隔）。**属于设计内耗时，不是卡顿**。若后续要提速，应优先优化 `wait_idle` 的轮询节奏（例如首轮无间隔、后续指数退避），而不是减少刷新次数（刷新是坐标正确性的前提）。

### 5.3 重试机制有效性（注入式单测）

真机本次运行未出现偶发失败（设备很稳），所以重试机制没被触发。它的有效性由**注入式对照实验**证明：

| 场景 | 关重试 | 开重试 |
|---|---|---|
| 每 5 次 dumpLayout 注入一次超时（50 步） | 通过率显著下降 | 成功率回升，且**严格优于**关重试 |

`tests/test_runner.py::TestRetryBehavior::test_retry_beats_no_retry_under_periodic_faults`
断言「开重试的成功率 ≥ 关重试」且「通过步数严格更多」——**重试没救回任何步骤就会挂**。

### 5.4 验收指标口径说明

报告同时给出两种成功率，**验收以「独立成功率」为准**：

| 指标 | 定义 | 用途 |
|---|---|---|
| 原始成功率 | (总步数 − 失败步数) / 总步数 | 受级联影响，一步挂可能拉低几十个点 |
| **独立成功率** | (总步数 − **独立**失败步数) / 总步数 | **执行引擎健壮性的真实指标** |
| 重试挽救率 | 挽救步数 / 重试尝试次数 | 量化重试机制到底救回了多少 |

## 六、失败分类与重试策略

### 6.1 七类失败（同时是失败归因引擎的接口雏形）

| 类别 | 触发条件 | 最大尝试 | 退避基数 | 是否触发设备恢复 |
|---|---|---|---|---|
| `LOCATE` | 控件未找到 | 3 | 400ms | 否 |
| `TIMEOUT` | 命令/等待超时 | 3 | 800ms | 否 |
| `DEVICE` | 设备或 hdc 连接异常 | 3 | 1200ms | **是（重启 hdc 服务）** |
| `APP` | 被测应用异常 | 2 | 1500ms | **是（重新拉起应用）** |
| `ASSERT` | 断言不成立 | **1（不重试）** | — | 否 |
| `DSL` | 用例本身写错 | **1（不重试）** | — | 否 |
| `UNKNOWN` | 未归类 | 2 | 600ms | 否 |

**为什么 `ASSERT` 和 `DSL` 绝不重试**：断言失败是真失败，重试只会拖慢并掩盖问题；用例写错了重试一万次也没用。单测里有 4 条专门盯这个，包括一条针对「`断言失败：控件应存在但未找到` 同时含 ASSERT 和 LOCATE 关键词」的歧义用例 —— 判成 LOCATE 会让断言被重试三次。

### 6.2 退避

线性退避 `base × attempt` + 随机抖动（0~120ms），并有单步总时长上限（默认 30s），防止重试把一步拖到几分钟。抖动是为了避免多用例并发时重试撞在一起。

## 七、顺手解决的工程问题

### 7.1 单测从 133 秒压到 8.5 秒

本项测试第一版跑了 **133 秒**。原因是 `wait_idle` 默认每轮真睡 350ms，一个 50 步用例要睡 35 秒，而本版有 5 个 50 步级别的测试。

修复：给 `Driver` 和 `Runner` 都加 `sleep_fn` 参数（默认 `time.sleep`），单测注入空实现。

```python
Driver(..., sleep_fn=lambda s: None)
Runner(..., sleep_fn=lambda s: None)
```

**等待逻辑的正确性不依赖真实时间流逝**，所以这不损失任何覆盖率。结果：**133s → 8.5s**。

### 7.2 产物轮转

50 步连续执行每步都截图 + 存控件树，会产出上百个文件。`Runner.artifact_budget`（默认 60）按「**失败优先**」清理：失败步骤的产物必留、末尾 3 步必留，其余按时间从旧到新删。不限制会直接把磁盘撑爆。

### 7.3 模拟设备保真度补丁

本项开发中发现 `FakeHdc` 有两处不保真，都会导致「模拟环境绿灯、真机红灯」：

1. **不支持 `echo`** —— `DeviceGuard` 的心跳探测就是 `hdc shell echo xxx`，于是模拟环境里心跳永远失败。
2. **`shell('uitest uiInput ...')` 没有路由到操作注入** —— 真机上「经 `hdc.swipe()` 下发」和「直接拼 shell 命令」完全等价（`hdc.py` 内部就是这么实现的），模拟环境里后者会静默变成空操作。

两处都已修，并新增**锁屏模拟**（`FakeHdc(locked=True)` 返回单节点空树）。

> 这是本项目第三次踩「模拟器不保真」的坑（前两次：bounds 格式、`json.dumps` 序列化 坐标）。**教训统一为一条：模拟器产生的数据形态与错误形态，都必须与真机逐字对齐。**

## 八、对外接口

### 8.0 ★ 契约入口：`run(cases, device) -> RunReport`

**这一节是给 A、B 和 CI 看的，请统一走这个入口。**

系统接口契约约定对外提供 `run(cases, device) -> RunReport`，而 本版的内部实现 `Runner.run_suite(...)` 返回的是 `SuiteResult` —— **两者签名与类型都对不上**。这个不一致如果在 W2 接口冻结后才被发现，集成会直接断在类型上。

已在冻结前对齐：

```python
from ohauto import run

rep = run(cases, device)          # -> RunReport（契约声明的类型）
rep.ok                            # 契约字段：整体是否通过
rep.total / rep.passed / rep.failed
rep.errors                        # 每条：case / step / action / kind / attempts / cascade / error

rep.suite                         # 富信息：完整 SuiteResult
rep.suite.failures_by_kind()      # 失败归因分布
rep.suite.independent_success_rate
```

设计原则：**契约类型负责对外，内部类型负责细节。** `RunReport` 保证 A/B/CI 有一条稳定的调用路径；`RunReport.suite` 挂着完整的 `SuiteResult`，需要失败归因、卡顿点、重试明细的调用方不必再走一遍内部实现。

`device` 参数支持四种形态，覆盖三人的不同场景：

| 传参 | 场景 |
|---|---|
| `None` | 真机，自动定位 hdc |
| `{'sim': True}` | 模拟设备（A/B 开发自测、CI 用）<br>可细化：`screen` / `start_page` / `faults` / `locked` |
| `Hdc` / `FakeHdc` 实例 | 复用已有连接 |
| `Driver` 实例 | 复用已有驱动器（多用例共享一次应用启动） |

真机实测（走契约入口跑 `note_stability.yaml`）：

```
返回类型   : RunReport (契约要求 RunReport: True)
总步数     : 10   通过: 10   失败: 0   ok: True
kpi_ok     : True (阈值 0.95)
耗时       : 25591 ms
```

### 给信号采集模块

`CaseResult` / `StepResult` 已自带可供归因的全部结构化信息：

```python
CaseResult.failures_by_kind()   -> {'ASSERT': 2, 'LOCATE': 1}   # 失败归因分布
CaseResult.slowest(n)           -> [StepResult, ...]            # 卡顿点

StepResult.recovered            -> bool                         # 是否靠设备恢复救回
```

`SuiteResult.to_dict()` 可直接序列化进报告（`examples/run_suite.py` 已这么做，输出 json/md/html 三份）。

### 给 B（归因引擎）

`FailureKind` 是**失败归因的一级分类**，刻意设计成与归因引擎的输入对齐。B 可以在此之上做二级归因，例如：

- `LOCATE` + `visible=false` → 控件存在但不可见（需滚动）
- `LOCATE` + `hitTestBehavior` 异常 → 控件被遮挡
- `DEVICE` + `hilog` 有 hdc 相关错误 → 连接层问题
- `ASSERT` + 截图差异 → 真实 UI 回归

## 十、用例幂等性：一个反直觉的教训

`cases/note_stability.yaml` 的第一版断言了标题「全部笔记」，第 9 步失败。排查后确认是**用例写错而非引擎问题** —— 点击搜索框后，标题会被搜索栏取代而消失。

这引出一个做长跑压测时必须遵守的规则：

> **做长跑压测时，用例的幂等性比覆盖面更重要。**
> 一个不幂等的断言会在第 N 个循环里突然失败，然后被误判成「引擎不稳定」，浪费大量排查时间。

最终版用例只断言「点击搜索框前后都存在」的控件（`id=searchInput`、`text=数学公式`），并且全部选在屏幕顶部（不会被软键盘遮挡），因此可以无限循环。

## 十一、遗留与后续

1. **真机上重试机制未被触发过** —— 50 步、200 步两次运行都是零重试，`--timeout` 压到 4000ms 也没咬住失败。这说明裕度充足，但也意味着**重试机制在真机上还缺一次实战验证**。等跨形态用例引入后，大概率会自然出现。届时应重点看 `重试挽救率` 这个指标。
2. **`wait_idle` 是当前最大的耗时来源** —— 实测每步约 5.7s，其中 `wait_idle` 占 2~3 秒（2~3 轮签名比对，每轮间隔 350ms + 一次 `dumpLayout`）。后续可优化为「首轮无间隔、后续指数退避」，预计能把单步压到 3s 以内。
3. **`REPORT` 的 HTML 模板未针对本版指标体系改造** —— 当前复用原有模板，`suite` 字段在 json 里完整，但 html 的可读性一般。若 质量门禁 要用 HTML 做门禁报告，需补。
4. **重试策略尚未按「步骤类型」细分** —— 目前按失败类别统一处理。后续可考虑：`assert` 步骤的 `LOCATE` 重试次数可以更多（断言本来就该等更久），而 `tap` 步骤应该更少（点两次可能产生副作用）。
5. **产物轮转只按文件数**，未按磁盘占用。截图单张 ~280KB，60 张约 17MB，目前可接受。
