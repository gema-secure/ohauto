### ★★ 3.1 追加：L3 在真机数据上**系统性失效**（2026-09-22 下午补测）

用**真机采集的真实控件树**（设备自带计算器，144 个可见控件）做了补测，
触发方式：把靶子控件的 id 换成**完全不相干**的词（不能含旧 id，否则 L2 就接住了）。

**结果：L3 一次都没命中，直接掉到 L5 坐标兜底。**

```
场景 A · 只改 id（含旧值）      → level=id_fuzzy_text  conf=0.85  rect=[15,548][147,694] ✓
场景 B · id 换成完全不相干的词  → level=coordinate     conf=0.20  rect=[81,621][81,621] ✗
                                  ↑ 直接跳过了 L3，而且坐标退化成一个点
```

**换了页面内唯一的控件（`result`，Text）重试，结果一样。**

### 根因：L3 的「唯一最高分」判据在真机上几乎必然落空

`_lv_path_type` 的最后一道关：

```python
scored = sorted(same_type, key=score, reverse=True)
if scored and score(scored[0]) > 0:
    # 唯一最高分才认——两个同分候选说明线索不够，宁可落空走 L4
    if len(scored) == 1 or score(scored[0]) > score(scored[1]):
        return scored[0], 'path_type'
return None, ''
```

而真机上 `same_type` 这一池子**总是很大**：

| 类型 | 数量（真机计算器一页） |
|---|---|
| Row | 46 |
| Image | 24 |
| GridItem | 21 |
| **Button** | **18** |
| **Text** | **8** |

打分只用了三类证据：`control_key`（**含 id，被改掉了就不得分**）、
`parent_types`（同类型控件的父链类型序列**完全一样**）、`text`/`descr`（按钮没文案）。
于是 18 个按钮的分数**全部相等** → 判为"线索不够" → 落空。

**所以这不是个例，是系统性失效。** 你的模拟设备上能过「改 5 个 id 恢复 5/5」，
是因为模拟页面控件类型多样、同类型不重复 —— **真机上同类型控件通常成组出现**
（一排按钮、一串列表项、一列图标），父链类型序列根本区分不开。

### 建议（如果同意我可以配合改）

同分时不要直接放弃，用**一条改 id 不影响的第三证据**打破平局：

| 候选证据 | 是否受"改 id"影响 | 评价 |
|---|---|---|
| `index_in_parent`（该控件在父节点里的序号） | ✗ 不受影响 | **最推荐**，简单且稳 |
| 兄弟中同类型总数 | ✗ | 可作辅助（区分"3 个按钮"vs"18 个按钮"） |
| 相对几何位置（bounds 排序后的第 k 个） | ✗ | 可用，但页面重排就漂 |
| 父链**节点的 id** | ✓ 会被改 | 不行 |
| 控件 text | ✗（除非文案也改） | 你已经用了 |

我的验证脚本留在 `tools/verify_locator_degrade.py`（`--from-json _out/calc_tree.json`
可复跑，`--id result` 换靶子），你改完可以直接拿它对比。

> 顺带说一句：**L5 坐标兜底返回的是一个退化点**（`[81,621][81,621]`，宽高为 0，
> conf 0.20）。它确实"记失败不记成功"（你那条取舍是对的，连续失败在正常累加），
> 但如果上层不检查宽高是否为 0，会往一个点上点 —— 这个值得在上层加一道校验。

## 八、依赖约定的口径澄清（可能困扰过你）

`分发说明` 第 67-70 行写着「**不要 `pip install` 任何东西**」。你如果照字面理解，
可能会担心 `vision.py` 里能不能用 `requests`、`crop_fn` 钩子接真裁剪时能不能用 PIL。

**这条的准确口径是「核心能力零第三方依赖」，不是「不许 pip install」**：

| 层 | 内容 | 规则 |
|---|---|---|
| **核心能力** | `hdc` / `layout` / `matcher` / `driver` / `runner` / `report` / `sim` | **零第三方**。引一个进来才算违规 |
| **DSL 序列化后端** | `pyyaml` | 写可退化 JSON；**读 YAML 必须有它** |
| **工具链** | `coverage`、`pyyaml` | CI 与本地装，**不进设备侧、不进分发产物** |

**所以**：`requirements.txt` 里可以有东西、CI 会装它（`quality-gate.yml:63`）——
**这不违反约定**；**在核心模块里 `import` 第三方包才违反**。

### 这条为什么不能干脆取消

它不是随手定的偏执，而是从《项目规划》高地 7 的验收标准推出来的：

```
高地 7 验收：「任何人 clone 后按 README 三步能跑起来」   ← 工程规范 10 分的硬指标
        ↓ 要做到这点
代码包必须自包含（clean-room 能跑）
        ↓ 所以
核心能力零第三方依赖 —— 标准库够用
```

`分发说明` 第 60-61 行自己就说了：「这个命令在**解压后的干净副本上实测通过** ——
代码包是自包含的」。再加上技术路线本身（设备侧零部署、能力层全跑在宿主 PC 上），
**部署门槛越低、评委和队友复现越容易**。

> 原表述「不要 pip install 任何东西」是**手段被绝对化**的产物：
> 原始目标（可复现）→ 推导约束（核心零依赖）→ 转述成（啥都别装）。
> 每转一手掉一层条件，最后和 CI 自己的 `pip install` 打起来了。
> 完整分析见 `docs/口径澄清-依赖约定-2026-09-22.md`。
