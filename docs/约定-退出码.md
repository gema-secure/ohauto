# 约定：tools/ 脚本的退出码（三态）

> 2026-09-27 成文。此前这条约定**只存在于代码里**（`tools/preflight.py` 的注释、
> 各脚本的写法），没有文档 —— 下一个写 tools 脚本的人只能靠猜，于是出现了
> 6+ 处「倒置」（该 1 的返 2、该 2 的返 1、甚至失败返 0）。本文把它钉死。

## 三态定义

| 退出码 | 含义 | CI 应如何处理 |
|---|---|---|
| **0** | 通过（检查项全过 / 产物正常生成） | 继续 |
| **1** | **未达标**（跑完了，但结果不合格：门禁红、用例失败、采集有问题、前置资源缺失、用法错误） | **失败**，必须处理 |
| **2** | **设备不在场**（真机没插 / 模拟器环境未就绪 —— 重试或补环境后**同一命令能过**） | **跳过**（不是代码的错） |

## 判定口诀（写脚本时自问一句）

> **这个失败，把设备插上会不会消失？**
> - 会 → `2`（设备不在场）
> - 不会（缺样本、缺环境变量、参数错、检查不过、门禁红）→ `1`
> - 都没问题 → `0`

## 为什么 2 不能挪用

CI / 外层脚本把 `2` 解读为「跳过而非失败」。如果拿 2 表达别的失败
（曾经：`crossform_run.py` 发现高危差异时返 2 当「门禁红」），
真失败会被静默跳过 —— **比崩溃更糟的失败形态**。

反过来，设备连不上时也不能返 1：真机任务在无设备环境（如定时任务）
会被误报成「检查未达标」，而它其实只是「今天没插设备」。

## 两处豁免（写文档时如实声明）

1. **argparse 自身的用法错误退出码是 2**（Python 惯例，改不了）。
   调用方要区分：argparse 的 2 总伴随 stderr 上的用法文本。
   自家逻辑里的参数校验（如 `--bundle` 不带 `--ability`）**用 1**，不用 2。
2. **`tools/ocr_worker.py` 是子进程私有协议**：父进程 `fusion._ocr_via_venv`
   只判 `rc != 0` 即降级，其内部退出码不属本约定管辖。

## 新写 tools 脚本的 checklist

- [ ] `main()` 的每个 `return` 都能对上三态之一（对着上表自问那句）
- [ ] 设备探测失败统一走 `tools/preflight.py::require_device`（它返 2）
- [ ] 自家参数校验用 1（argparse 的 2 是豁免，别模仿）
- [ ] 不发明 3、4……新值；确需细分，先改本文档
- [ ] 在脚本 docstring 里写明「退出码：0=… / 1=… / 2=…」
