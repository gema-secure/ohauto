### 2.1 🔴 `locator.py:582` 报「已回滚」但没有回滚

**现象**：自愈验证未通过时，报告字符串说「已回滚」，代码没有任何回滚动作。

**代码事实**（我逐行读过的顺序）：

```python
# 566-575：原地改写 spec 的全部线索
spec.target_id = new_node.id
spec.text = new_node.text
spec.descr = new_node.descr
spec.target_type = new_node.type
spec.type_fp = type_fingerprint(new_node)
spec.control_key = control_key(new_node)
spec.parent_types = tuple(p.type for p in self._ancestors(new_node))
spec.fallback_center = new_node.rect.center
spec.generation += 1
h.repairs += 1
h.consecutive_failures = 0          # ← 还把失败计数清零了

# 578-583：验证失败分支
if verify is None:
    rep.failed[lid] = f'第 {spec.generation} 代定位器验证未通过，已回滚'
    self._log(f'{lid} 自愈验证失败')
    continue                        # ← 到此为止，没有恢复旧值
```

**后果三层**（比「消息不准」严重）：

1. **spec 已被改成错的**：所有线索指向那个验证失败的新节点，但报告说「已回滚」——
   调用方据此认为 spec 没变，继续用这个坏定位器；
2. **`generation` 已自增**：账本上多了一代，而这一代是没验证通过的；
3. **`consecutive_failures = 0`**：自愈阈值被清零 → 下次要**重新攒够**失败才触发自愈，
   等于**弄坏一次、还顺手把自愈延迟了**。

**最小复现**（构造一次「有唯一候选但验证不通过」的自愈）：

```python
# 思路：让 _pick_repair_candidate 给出候选，但 _lv_id_exact / _lv_path_type 都判不中
# 例如候选节点的 id 为空、且层级路径在新鲜树上对不上
rep = mgr.repair_locators(root, [lid])
assert rep.failed[lid].endswith('已回滚')
# 此时看 spec：target_id/text/type_fp 已被改写，generation 已 +1
```

**修法建议**：改写前先 `old = replace(spec)`（或把 8 个字段存成快照），
`continue` 前把旧值写回，并 `generation` 不自增、`consecutive_failures` 不清零。
报告文案改成「自愈失败，已回滚至第 N 代」—— 让它和真实状态一致。

**验收**：加一条单测，自愈失败后断言 `spec` 的所有线索字段与调用前**逐字段相等**。

### 2.2 🔴 `locator.py` 的失败记账不幂等（docstring 与代码不符）

**docstring（`locator.py:38-40`）**：

> 失败自动记账：locate 全链路落空时内部也会 `record_locator_failure`，
> B 的执行器按契约回写是第二重保险，**两者幂等**。

**代码（`locator.py:519-526`）**：

```python
def record_locator_failure(self, locator_id: str, reason: str) -> None:
    """契约接口：B 的执行器在定位失败时回写（幂等，内部也会自动记）。"""
    h = self._health.get(locator_id)
    if h is None:
        return
    h.attempts += 1
    h.consecutive_failures += 1      # ← 没有任何去重/幂等判断
    h.last_failure_reason = reason
```

**没有任何幂等措施**：同一次失败，`locate()` 内部记一次 + B 的执行器按契约再回写一次 →
`attempts` 和 `consecutive_failures` **各 +2**。

**后果**：`consecutive_failures` 达到阈值的**速度翻倍** →
**自愈阈值以一半的失败数触发**。自愈会提前介入（浪费一轮自愈），
更糟的是它让「健康度账本」上的失败数**不能当真实失败次数用**。

**修法建议**（两选一）：

- **方案 A（推荐，改动最小）**：给记账加一个幂等键。
  在一次 `locate()` 调用内用 `self._failure_seen_in_call`（或一个 context 标记）
  保证同一个 locator 只记一次；
- **方案 B**：把「内部自动记」去掉，明确要求**只有执行器回写**——
  但那要改 B 的契约，跨人协调，成本高。

**验收**：一条单测断言「`locate()` 落空 + 执行器回写」后
`consecutive_failures == 1`（现在是 2）。
