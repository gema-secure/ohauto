## 一、通用上下文（三人共用，喂给 AI 时先粘这一段）

### （一）项目一句话

面向 OpenHarmony 应用的智能化 UI 测试系统：让系统自动探索应用、自动生成用例、自动判断失败原因、自动沉淀回归集。

### （二）技术路线（决定了怎么写代码）

走 hdc 命令行通路，**不需要给被测应用打包测试 HAP，设备侧零部署**。核心命令只有四条：

| 命令 | 作用 |
|---|---|
| `hdc shell uitest dumpLayout` | 导出控件树（JSON） |
| `hdc shell uitest screenCap` | 截图 |
| `hdc shell uitest uiInput ...` | 注入操作（click / inputText / swipe / keyEvent） |
| `hdc shell uitest uiRecord` | 录制用户操作 |

**最关键的一点**：`uiInput` 全部基于坐标。所以整条链路是「控件树 JSON → 控件对象 → bounds 中心坐标 → 注入事件」，这个转换是项目的地基。

### （六）模拟器与真机必须保持一致（血泪教训）

**模拟器一旦和真机格式不一致，就是在替被测系统掩盖缺陷。** 已经踩过两次：

1. `sim.py` 的 `_b()` 早先返回 JSON 形态的 bounds（真机是 `"[l,t][r,b]"`），
   结果 113 个单测全绿、真机上所有坐标退化成 0、点击全落屏幕左上角。
2. C4 的模拟截图默认是纯色图（真机是正常内容页），
   结果干净场景被判成「白屏」，置信度 0.99 —— 测试全绿但结论是假的。

**因此定为硬约定**：新增任何模拟能力时，**默认值必须等于真机的典型状态**，
把「异常态」（纯色截图、故障注入、设备掉线）做成**显式选项**通过参数传入。
写测试时也要专门有一条守住「默认路径」——只测逻辑的两个分支是不够的。

### （二·补）B1 的关键设计：页面双签名

**这是 B1 最该先定下来的东西，定错了后面全白做。**

每个页面同时算两个签名：

```python
content_sig   = sha1(完整控件树 + ability + bundle + pagePath)   # 精确：id/text/结构全参与
structural_sig = sha1(每个控件的 type 序列 + ability + bundle + pagePath)  # 宽容：不含 id/text
```

| 签名 | 用途 | 为什么不能混用 |
|---|---|---|
| 内容签名 | **精确去重**：判断"这个页面我访问过没有" | 太敏感——列表新增一条数据就变成新页面 |
| 结构签名 | **返回栈回溯**：判断"返回后是否回到原页" | 太宽容——两个结构相同的不同页面会被当成同一页 |

**为什么必须要结构签名**：页面里的文案会随数据变化（列表首项、未读计数、时间戳），
如果只用内容签名，探索器会把同一个页面反复"发现"成新页面，覆盖率统计虚高、还会绕圈。
结构签名只看控件类型序列，文案怎么变都不影响。

**配套**：每个控件也可算一个 `type` 级的稳定 ID（`sha1(type)`），
用于「跨页面找同类控件」，这是降级链里「层级路径 + 类型」那一级的实现基础。

### （二·补）B2 的优先级设计（四档）

不要用「有权重」这种模糊说法，用固定档位，便于测试与解释：

```
URGENT 100   危险控件（删除/支付/注销）——默认拦截，配置放开后置顶
HIGH    80   弹窗内可交互控件；含「登录/搜索/详情/提交」关键词的控件
MEDIUM  40   普通可交互控件
NORMAL  20   其他
LOW     10   已访问过且无状态变化的控件（留作兜底）
```

排序规则：**先榨干当前页面所有未执行过的事件（按档位降序），
再跳到最近的可达未访问页面**。这个「局部穷尽 + 全局 BFS」的混合结构，
比纯 BFS 少走很多回头路，也天然避免了在页面间来回弹跳。

### （五）LLM 调用的两条工程约束（不做到会直接卡死主循环）

**1. 异步预取，不要阻塞探索主循环。**

LLM 决策一次要几秒。如果每次都同步等它，探索速度无法接受。做法：

```python
def next_event(self):
    if self.pending_event:              # 上一轮预取的结果已就绪 → 直接用
        ev, self.pending_event = self.pending_event, None
        return ev
    if not self.fetching:               # 本轮没有存货 → 发起异步请求
        self.fetching = True
        self._fetch_async()             # 完成后写入 self.pending_event
    return WaitEvent()                  # 本轮先等待，下一轮吃结果
```

配合 `sim.py` 的 `sleep_fn` 注入就能单测（无需真的调模型）。

**2. LLM 失败必须能降级，绝不中断探索。**

模型超时 / 返回不合法 / 网络断 → 退化成随机点击 + 记警告，继续探索。
连续失败超过阈值才停。**要在 prompt 里带上「已尝试过的动作列表」并注明不要重选**，
否则 LLM 会绕着同一个按钮打转出不来。

### （二·补）C3 的形态档案：从设备原生接口取，不要靠猜

> ⚠️ **2026-09-17 真机实测修正**：下面原来的命令 `-a -a` **在这台真机上报
> `arguments are illegal`**，取不到任何数据。各服务的真实子命令不同，
> **通用办法是先 `-a -h` 问它要帮助**：
> `hdc shell 'hidumper -s <服务名> -a -h'`。

形态档案的字段**不必自己推算**，设备有原生接口。经真机实测，**数据分在三个地方**：

```bash
# ① 屏幕列表：ScreenName / Type / VPR / Rotation
hdc shell 'hidumper -s DisplayManagerService -a "-s -a"'

# ② 显示信息：DisplayId / RefreshRate / VPR / 分辨率
hdc shell 'hidumper -s DisplayManagerService -a "-d -a"'

# ③ ★ 安全区（真正的来源！不是 DisplayManager）
hdc shell 'hidumper -s WindowManagerService -a -a'
```

实测真机（720×1280）拿到的数据：

| 输出字段 | 来源 | 实测值 | 对应形态档案项 |
|---|---|---|---|
| `[x y w h]` | ② `-d -a` | `[0 0 720 1280]` | **分辨率** |
| `RefreshRate` | ② | `69` | 刷新率 |
| `VPR` | ② / ① | `1.5` | **像素比** |
| `MIPI` / `REAL` | ① `-s -a` | — | 屏幕类型 |
| `SystemUi_StatusBar` | ③ | `[0,0,720,72]` | **顶部安全区 72px** |
| `SystemUi_NavigationB` | ③ | `[0,1208,720,72]` | **底部安全区 72px** |
| `SystemUi_PrivacyIndi` | ③ | `[0,0,720,32]` | 隐私指示区 32px |

> **重要修正**：安全区的真正来源是 **`WindowManagerService`**，
> 不是 DisplayManagerService（那里只有分辨率和刷新率）。

**折叠态与挖孔（`FoldStatus` / `CUTOUT INFO` / `WaterFall`）**：
直板机上**这些字段根本不存在**（实测无输出）。
所以要么用 DevEco 的 Foldable 模拟器验证，要么作为架构预留、不纳入验收。

另外两条辅助命令：

- `hdc shell hidumper -s RenderService -a screen` → 物理分辨率与渲染尺寸
  （**`driver.py:521` 已经在用这条**）
- `hdc shell hidumper -s BatteryService -a -i` → 电量与温度（**长稳 2h 测试时监控设备过温**）

> ⚠️ **注意**：单台直板机上取不到折叠形态数据，**且真机 `wm` 命令不可用**
> （实测 `wm: inaccessible or not found`，无法靠改分辨率造第二形态）。
> **C3 的第二形态只能靠 DevEco 模拟器** —— 这台机器上 DevEco 已装好。

## 七、★ 主攻方向：把资源压在这三件事上

> 本章是 2026-09-17 调研同类开源项目后的结论，**直接影响资源分配与答辩叙事**。

### （一）调研结论

同类项目已有相当成熟的能力，**"自动探索"和"AI 生成用例"这两件事我们并不领先**：

- 探索：已有开源框架实现了**页面状态图 + 一族搜索策略**（朴素 / 贪心 / 随机）、
  四档优先级、乃至 LLM 引导的决策，还带异步预取。
- 生成用例：已有产品实现了**两阶段 AI 生成**（需求 → 测试点 → 用例）。

所以**不要在这两块上追平**——借鉴成熟思路做到「够用」就收手，
把省下的时间投到下面三件事。

### （二）我们的三个真空白

| 主攻方向 | 同类项目状态 | 归属 |
|---|---|---|
| **跨形态测试** | **翻遍同类项目，没有一个做折叠/平板形态对照** | C（C3） |
| **失败归因四分类** | 同类项目都只报「失败」，**没有一个做归因** | B（B4） |
