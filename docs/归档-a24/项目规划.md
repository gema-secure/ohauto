# 项目规划：面向 OpenHarmony 的多模态智能测试系统

> 赛事定位：系统与技术创新类作品（参考中国国际大学生创新大赛 a24 命题自主创作）
> 团队：3 人 ｜ 提交截止：2026-10-31
> 现有资产：`ohauto` UI 自动化能力层（分层架构、113 个单测通过、模拟设备可离线跑通全链路）

---

## 一、作品定位

**一句话**：面向 OpenHarmony 应用的**智能化 UI 测试基础设施**——把"人工读控件树写脚本、肉眼判断是否跑通"变成"系统自己探索、自己生成用例、自己判断失败原因、自己沉淀回归集"。

**与既有方案的差异**（答辩必讲）：

| | 官方 UiTest（ArkTS 通路） | 传统录制回放 | **本作品** |
|---|---|---|---|
| 设备侧部署 | 每个被测应用打包测试 HAP | 需注入 SDK | **零部署，只用 hdc** |
| 用例来源 | 人手写 | 人手录制 | **自动生成（探索 + 自然语言）** |
| 定位方式 | 硬编码控件属性 | 硬编码坐标 | **控件树 + 视觉双通道 + 自愈** |
| 失败处理 | 报错，人工排查 | 报错 | **自动归因 + 自动修复** |
| 跨形态 | 需人工适配 | 失效 | **一套用例跑手机/折叠/平板** |
| 回归沉淀 | 人工维护 | 手工维护 | **轨迹自动沉淀为回归集** |

**六个可演示的能力闭环**（每个都能独立演示，便于分工与答辩）：
1. 给定应用包名 → 自动探索出页面状态图
2. 给定自然语言描述 → 生成可执行用例
3. 给定用例 → 真机执行 + 失败自动归因
4. 给定失败用例 → 自动修复定位器并重跑
5. 给定应用 → 三种设备形态跑同一套用例，输出适配缺陷
6. 给定仓库 → CI 流水线质量门禁，输出结构化报告

## 二、七个技术高地（"高标准"的具体化）

不写"要做得完整"，而是列出**必须攻下、且可验收**的七个技术点。这是本项目的真正工作量，也是评审 30 分创新性、40 分难度的落点。

### 高地 1 · 定位器自愈与稳定性画像

**问题**：UI 自动化最大的痛点是定位失效。控件 id 随构建变化、文本随文案调整、坐标随布局漂移，导致"今天能跑明天挂"。

**目标**：建立定位器健康度模型，实现自动降级与自动修复。

```
定位优先级链（逐级降级）:
  控件树 id 精确匹配
   → 控件树 id 模糊 + text 组合
   → 控件树 层级路径 + 类型
   → 视觉语义定位（无标识控件）
   → 坐标兜底（记录告警）

每个定位器维护: 成功率 / 最近失败时间 / 平均耗时 / 历史降级次数
连续失败 N 次 → 触发自动修复：重新探索该页面 → 生成新定位器 → 验证 → 替换
```

**验收**：注入式测试——人为改 5 个控件的 id，系统应在不人工干预下自动恢复执行（成功率 ≥80%）。
**归属**：A ｜ 支撑：难度 40 / 创新 30 / 稳定 20

### 高地 2 · 双通道融合 + 分层成本控制

**问题**：纯控件树覆盖不到 Canvas / 图标按钮；纯视觉又慢又贵还会幻觉。

**目标**：控件树为主、视觉为辅，且**视觉只跑必要区域**。

```
分层策略:
  L1 静态候选筛选   解析控件树，按语义关键词圈定候选区域   ~50ms
  L2 局部视觉推理   只裁剪候选区域送多模态模型（小图）      ~1-2s
  L3 全屏视觉兜底   仅当 L2 失败时触发，且结果进缓存        ~3s
  缓存维度: (页面指纹, 目标描述) → 结果，跨轮次复用
```

**交叉校验**：视觉 bbox 与控件树命中做 IoU，重叠则置信度提升并采用控件树精确边界；不重叠则标记不确定、不盲点。

**验收**：无 id 无 text 的图标按钮可被点中；视觉推理平均耗时 ≤2s；缓存命中率 ≥60%。
**归属**：A ｜ 支撑：性能 20 / 创新 30

### 高地 3 · 探索覆盖率与智能引导

**问题**：朴素 BFS 探索效率低、容易陷入死循环、覆盖不全。

**目标**：把"探索"做成可度量、可引导的过程。

- **页面指纹**：用可见控件的 (类型, id, text, 尺寸) 序列做指纹，去重防重复访问
- **覆盖度指标**：`已访问可交互元素 / 控件树中全部可交互元素`，实时统计并输出报告
- **智能引导**：优先探索"未访问过且语义重要"的元素（含关键词：登录/搜索/详情/提交 等权重更高）
- **返回栈管理**：识别"返回后没回到原页"的情形并重新定位
- **安全围栏**：危险控件（删除/支付/注销/卸载）默认拦截并记录，可配置放开

**验收**：在一个 ≥3 页面示例应用上，覆盖度 ≥90%；无死循环；危险控件零误触。
**归属**：B ｜ 支撑：难度 40 / 创新 30

### 高地 4 · 生成—验证—修复闭环

**问题**：LLM 生成的用例"看起来对，跑起来挂"。直接把生成结果当真会毁掉可信度。

**目标**：生成不等同于交付，必须过验证关。

```
自然语言描述
  → LLM 生成 YAML 用例草案
  → 静态校验：定位器引用的控件在当前控件树中存在？
  → 干跑：逐步骤试执行（不产生副作用的步骤直接跑，有副作用的先判定）
  → 失败步骤自动修复：换定位策略 / 调整等待时长 / 拆分步骤
  → 通过则入库，未通过则输出"不可执行原因"报告
```

**验收**：20 条自然语言描述生成用例，**可执行率 ≥80%**（这是可量化、可对比的硬指标）；对不可执行的给出明确原因分类。
**归属**：B ｜ 支撑：难度 40 / 创新 30

### 高地 5 · 失败归因引擎

**问题**：脚本挂了，到底是脚本问题还是应用 bug？这是测试工具与"点击机器人"的分水岭。

**目标**：把失败自动分成四类，并给出证据。

| 归因类别 | 判定依据 | 输出 |
|---|---|---|
| **定位失败** | 目标控件不存在于当前控件树，且页面指纹与预期一致 | 疑似定位器失效 → 触发高地 1 自愈 |
| **时序问题** | 控件存在但未在超时内出现；重试后成功 | 建议增加等待/改用 waitFor |
| **应用缺陷** | 页面崩溃 / 白屏 / 无响应 / hilog 有异常栈 | **有效缺陷报告**，附截图 + 日志片段 |
| **用例缺陷** | 前置条件不满足（如未登录却访问订单页） | 标记用例需补前置步骤 |

**验收**：人工注入 4 类故障各 5 例，归因准确率 ≥80%；应用真崩溃必须被识别为"应用缺陷"而非"定位失败"。
**归属**：B（分类逻辑）+ C（信号采集：hilog / faultlogger / 截图比对）｜ 支撑：难度 40 / 稳定 20

### 高地 6 · 跨形态测试（鸿蒙特色）

**问题**：鸿蒙的核心优势是多形态设备，而 UI 自动化的既有方案在形态变化下基本失效。**这是最能体现"鸿蒙特色"的创新点。**

**目标**：同一套用例，在三种形态下执行，自动比对差异、输出适配缺陷。

- **形态档案**：直板机（19.5:9）/ 折叠内屏（近方形）/ 折叠外屏或平板（宽比例），含 DPR、安全区、圆角、折痕位置
- **自动切换与重采集**：形态变化后必须重新 dumpLayout（坐标体系变了，绝不复用缓存）
- **差异检测**：同一用例在三形态下的执行结果对比 → 元素缺失 / 位置越界 / 控件不可达 / 布局溢出
- **输出**：跨形态适配缺陷报告（这是"测试工具"之外新增的产品价值）

**验收**：至少 2 种形态（若有折叠屏真机则 3 种）跑同一套用例，输出差异报告；能检出至少 2 类真实适配问题。
**归属**：C（形态能力与设备）+ B（跨形态用例生成）｜ 支撑：创新 30 / 难度 40

### 高地 7 · 工程规范与 CI 质量门禁

**目标**：让"工程规范性"从软性描述变成可见证据。

- **代码规范**：类型注解全覆盖、统一格式化与 lint、命名规范、模块边界清晰
- **测试**：单测覆盖率 ≥70%（用 coverage 出报告）；真机相关测试用 skip 守卫，保证无设备也能跑 CI
- **CI**：提交即跑 lint + 单测 + 模拟设备端到端；生成报告归档
- **质量门禁**：覆盖率下降 / 单测失败 / 端到端失败 → 阻止合入
- **文档**：架构文档 + 各模块 README + API 说明（docstring）

**验收**：CI 全绿徽章可贴；覆盖率报告可展示；任何人 clone 后按 README 三步能跑起来。
**归属**：C ｜ 支撑：工程规范 10

## 四、三人分工

### 分工原则

1. **按"可独立演示的能力"切分**，而非按代码目录——每人在答辩时都能独立演示自己那块
2. **每人一个技术主战场**，避免交叉修改同一文件
3. **文档与视频全员分摊**，不堆给一个人（上一版规划的主要缺陷）
4. **集成由专人主持**，三人项目的头号死因是集成失控

### 角色 A —— 定位与感知

> **一句话**：让系统"找得到"目标，找不到时能自己想办法。

| 项 | 内容 |
|---|---|
| **负责高地** | 高地 1（定位器自愈）、高地 2（双通道融合与分层） |
| **代码模块** | `vision.py`（视觉 Provider 与融合）、`matcher.py`（高级匹配增强）、新增 `locator.py`（自愈与健康度） |
| **对外接口** | `locate(target, page) -> LocateResult`（含坐标、来源通道、置信度、健康度）；`report_locator_failure(id, reason)` 供 B 的执行器回写 |
| **KPI** | 标准控件准确率 ≥95%、无标识控件 ≥80%、视觉耗时 ≤2s、缓存命中 ≥60%、自愈成功率 ≥80% |
| **依赖** | C 提供真机截图与控件树字段结构；B 回写定位失败记录（自愈的输入） |
| **本周起步** | ① 确定多模态 API（外部依赖，最先办）② 用手机截图跑通 bbox 解析链路 ③ 把"降级链"设计写成一页纸与 B/C 对齐 |
| **文档产出** | 定位架构与算法说明（自愈策略、融合判据、成本控制） |

### 角色 B —— 探索与生成

> **一句话**：让系统"自己会逛、自己会写用例、自己判断失败原因"。

| 项 | 内容 |
|---|---|
| **负责高地** | 高地 3（探索覆盖与引导）、高地 4（生成—验证—修复）、高地 5（失败归因分类逻辑） |
| **代码模块** | `explorer.py`、`action.py`（DSL 引擎）、新增 `generator.py`（NL→用例 + 验证修复）、新增 `diagnose.py`（归因） |
| **对外接口** | `explore() -> StateGraph`；`generate(description) -> Case`；`diagnose(execution_record) -> Verdict` |
| **KPI** | 探索覆盖率 ≥90%、NL→用例可执行率 ≥80%、归因准确率 ≥80% |
| **依赖** | A 的定位能力（探索依赖定位）；C 提供执行信号（hilog / 崩溃日志 / 截图）给归因用 |
| **本周起步** | ① 给 explorer 补"返回栈回溯"单测（用 `sim.py`，今天就能做，不依赖真机）② 设计归因四分类的判定规则草案 ③ 定义"可执行率"的度量口径 |
| **文档产出** | 用例生成流程与验证机制说明、探索算法说明、归因规则表 |

### 角色 C —— 执行、质量与设备

> **一句话**：让所有东西在真机上稳定跑起来，并且把质量做成可证明的证据。

| 项 | 内容 |
|---|---|
| **负责高地** | 高地 6（跨形态测试）、高地 7（工程规范与 CI），并承担执行引擎健壮性与性能测量 |
| **代码模块** | `hdc.py`、`driver.py`（健壮性：重试/超时/幂等）、`report.py`、新增 `runner.py`（批量与并行执行）、`devices/`（形态档案）、`ci/`（流水线）、hypium 导出 |
| **对外接口** | `run(cases) -> RunReport`；`collect_signals() -> Signals`（供 B 归因）；形态切换 API |
| **KPI** | 50 步连续成功率 ≥95%、单步耗时 ≤200ms、长稳 2h、覆盖率 ≥70%、跨形态检出 ≥2 类 |
| **依赖** | 全员接口稳定（他的工作是集成） |
| **本周起步** | ① 装 DevEco、连真机、跑 `doctor.py` ② 跑 `dump_tree.py` 核对字段差异并修 `layout.py` 别名表 ③ 搭 CI 骨架（lint + 单测） |
| **文档产出** | 架构总文档（汇总）、执行与质量保障说明、跨形态适配报告、**比赛提交材料组装** + 视频剪辑 |

### 队长职责（由 C 兼任，或由团队指定）

- 主持**每周集成日**，把控接口冻结
- 对外沟通（组委会、交流群、指导教师）
- 进度把控与阻塞上报
- 决赛答辩主陈述人（配合另两人做技术答疑）

> 建议由 C 兼任队长：他掌握集成状态与质量数据，天然是信息汇聚点。

### 负载与风险对照

| 角色 | 技术难度 | 工作量 | 被阻塞风险 | 应对 |
|---|---|---|---|---|
| A | 高（模型 + 算法） | 中 | **高**（多模态 API 是外部依赖） | 先用 Mock Provider 跑通管线；Provider 可插拔，随时换源 |
| B | 高（算法 + 生成） | 中高 | 低（可全靠 `sim.py` 开发） | 无真机也能推进，是最"耐阻塞"的角色 |
| C | 中（工程 + 集成） | **高**（设备 + CI + 汇总） | **高**（真机不到位则全线停） | A/B 用模拟设备并行推进；C 的文档汇总在 W6 集中，前期不占时间 |

> **三人的最大结构性风险是 C 被卡住**。因此 A、B 的开发**必须优先在模拟设备上完成**，真机只做验证——这是 `sim.py` 存在的核心意义。

## 五、协作机制（三人项目的生死线）

### 集成节奏

| 机制 | 频率 | 内容 |
|---|---|---|
| **每日** | 随时 | 各自分支提交；CI 自动跑 lint + 单测 + 模拟端到端 |
| **每周集成日** | 每周日固定 | 三人分支合入 `main`；跑全量单测 + 真机冒烟；当场解决冲突 |
| **周会** | 每周 30 分钟 | 对照七个高地与 KPI 过进度；阻塞项当场分配责任人与时限 |
| **接口冻结** | W2 起 | 三人的对外接口（见分工表）冻结，变更需在周会提出并知会另外两人 |

### 接口契约（冻结后不得随意变更）

```python
# A → 所有人
locate(target: Target, page: LayoutNode) -> LocateResult
    # LocateResult: rect, channel('tree'|'vision'|'hybrid'), confidence, health

# B → 所有人
explore(max_pages, budget) -> StateGraph
generate(description: str) -> Case
diagnose(record: ExecutionRecord) -> Verdict   # 四分类

# C → 所有人
run(cases: list[Case], device: DeviceProfile) -> RunReport
collect_signals() -> Signals                   # hilog/崩溃/截图，喂给 diagnose
```

### 质量红线（任一项不过，不允许合入）
