## 〇、前提变化如何改写了结论

第一版分析是在"无真机"假设下做的，那时把 a26 / a24 / a16 这类"需要真机验证"的题压低了分数。**真机环境一旦具备，评价函数的三项权重全变了**：

| 维度 | 无真机时 | 有真机时 | 影响 |
|---|---|---|---|
| **硬件依赖** | 一票否决项 | 降级为"部署成本" | a24/a26/a16/a15 从"做不了"变成"可做" |
| **指标可信度** | 只能自建测试集自证 | **真机数据 = 评审最认的证据** | 有真机的题在说服力上碾压纯模拟题 |
| **创新天花板** | 受限于模拟保真度 | 可做**真实端侧闭环** | 端云协同、真机性能对比这类叙事才立得住 |

**核心洞察**：命题方给 a24/a26/a35 都埋了同一句话——"至少基于一个 OpenHarmony 示例应用完成验证"。**没有真机的队伍只能交"模拟验证"，有真机的队伍能交"真机 + 优化前后对比数据"。这在评审里是量级差异，不是程度差异。**

所以策略变了：**不要再优先选"最容易做完的"，而要选"真机能把它从 70 分抬到 95 分的"**。

### 关键提醒：真机环境 ≠ 万能的

有一个坑必须点破——**"有真机"和"能做某道题"是两件事**：

- **a16/a17/a18 具身智能**：需要的是**机器人本体 + RoboFrame 实机**，OH 手机/平板不算数。若团队没有机械臂/移动底盘，这三题依然出局。
- **a2/a8/a9 内核**：需要**能刷内核的开发板**（如 RK3568/树莓派4B 跑 OH），且要接受反复烧写、砖机、串口调试。手机真机刷不了。
- **a37/a38 DFX**：需要**OH 源码编译能力 + ROM 侧部署权限**，普通商用真机装不进去。
- **a29/a30 直播**：需要**旗舰机型 + 功耗测量设备**，且性能对标 AVPlayer。

**所以先确认一件事**：你们的"真机环境"具体是什么？

| 如果你们有… | 主攻方向 |
|---|---|
| OH 手机/平板（商用或开发板都行），能装 HAP、能连 DevEco Studio | **a26 / a24 / a35 / a10 / a36** ← 最可能的情况 |
| 能刷系统的开发板（RK3568 / 树莓派）+ 串口 | 叠加 a9 / a23 的可能 |
| 3–5 台 OH 设备（手机+平板+手表/音箱） | **a10 多 Agent 协商** 直接进入首选区 |
| 机器人本体 + RoboFrame | a15 / a16 / a19 打开 |

下面按**最可能的情况（第一行）**给结论。

## 三、首选：u-a26《北向应用基础体验分析与优化 Agent》

### 3.1 为什么真机环境下它是最优解

1. **真机是它的"刚需"而非"加分"**。题目要求"输入应用包名或工程路径，执行测试或读取测试数据"——**没有真机，这个闭环根本闭不上**。反过来说，**有真机的队伍天然比没有的多半个身位**，而这道题恰好是最适合真机的。
2. **优化前后对比数据是真机独有的"硬通货"**。命题明确要求"提交优化前后对比结果"。栈上跑出来的对比表，评审一眼就信。
3. **指标全部可采**。冷启动耗时、页面切换耗时、主线程长任务、滑动帧率、内存/CPU 变化 —— DevEco Studio Profiler + hilog + hitrace 全套都有，不需要自建测量体系。
4. **有"分析-修改-再测-对比"多轮闭环这个高分叙事**。命题的挑战目标把它列出来了，这是能把项目从"工具"抬到"Agent"的关键设计。
5. **风险可控**：不碰内核、不训模型、不做 GPU，失败模式都是"指标提升不够大"而不是"东西跑不起来"。

### 3.2 方案构想：`ABLE` — ArkUI Basics-Latency Expert

**四段式 Agent 工作流**：

```
┌──────────────────────────────────────────────────────────┐
│ ① COLLECT  采集层                                          │
│   hdc 拉起目标 HAP → 注入 hilog/hitrace 埋点               │
│   采样：冷启动(startAbility → 首帧)、页面切换、滑动帧率、    │
│         主线程长任务(>8ms 任务)、PSS/CPU                     │
│   → 产出 raw trace + 结构化指标表                           │
├──────────────────────────────────────────────────────────┤
│ ② DIAGNOSE 分析层（规则引擎 + LLM 协作）                    │
│   规则引擎：阈值判定 + trace 关键路径分析（可解释、不幻觉）    │
│   读 ArkTS 源码：AST 匹配已知劣化模式                        │
│     · 首屏同步 await 链过长                                 │
│     · aboutToAppear 里做重活                                │
│     · LazyForEach 缺 cachedCount / 未用 @Reusable           │
│     · 状态管理粒度问题（@State 大对象引发全量重绘）           │
│   LLM：把"现象 + 代码上下文"合成可读诊断                      │
│   → 产出 现象 → 关键路径 → 嫌疑代码(file:line)               │
├──────────────────────────────────────────────────────────┤
│ ③ PATCH  修复层                                            │
│   生成 diff 草案（延迟加载/任务拆分/列表优化/状态细化/资源释放）│
│   → 产出可 apply 的 patch 草案 + 预期收益说明                │
├──────────────────────────────────────────────────────────┤
│ ④ VERIFY  验证层（闭环关键）                                 │
│   自动重新编译 → 重装 → 重采样 → 与基线对比                   │
│   → 产出 优化前后差异报告（指标表 + 火焰图对比 + 结论）        │
└──────────────────────────────────────────────────────────┘
```

**三个必须做扎实的点**（这是拉开差距的地方）：

| 点 | 做法 | 为什么重要 |
|---|---|---|
| **可插拔模型接口** | 抽象 `LLMProvider`，支持本地 / 云 API / 纯规则三档，配置文件切换 | 命题挑战目标明确要求"避免强绑定单一模型"，且**纯规则档让工具在没有模型时也能跑出结果**，答辩时是很好的可信度证据 |
| **对话式问答** | "为什么这个页面启动慢" / "哪个阶段耗时最高" / "优化后提升了多少" | 命题挑战目标点名要，且演示效果极佳 |
| **反幻觉设计** | 所有结论必须挂到**真实采集数据或代码行**上，无证据不下结论 | 命题原话："工具不得仅依赖大模型生成泛化建议"。这是评审会重点拷问的点 |

### 3.3 一句话卖点

> **"把 OH 应用性能诊断从'老师傅看日志三天'变成'Agent 自动跑一轮，10 分钟给你一张带代码行号的优化清单，并证明优化有效'。"**

### 3.4 落地排期（6–8 周）

| 周 | 交付 | 验收标准 |
|---|---|---|
| W1 | 环境打通 | hdc 能拉起/卸载目标应用，Profiler + hilog 能出数据 |
| W2 | ① 采集层 | 采到 ≥3 类指标，落盘成结构化 JSON |
| W3 | ② 规则引擎 | 能判定 ≥3 类体验问题，无 LLM 也能出结论 |
| W4 | ② 代码关联 | 读 ArkTS 工程，定位到 file:line 的嫌疑点 |
| W5 | ③ 补丁生成 | 输出可 apply 的 diff，至少 2 类优化模式 |
| W6 | ④ 闭环验证 | 自动"改-编-装-测-比"跑通一轮 |
| W7 | ④ 对话式问答 + 报告 | JSON/MD/HTML 报告 + 模型可插拔 |
| W8 | 文档 + Demo 视频 | 架构文档、真机对比数据、演示 |

## 四、为什么不是 a35（我改了主意）

a35 依然是**最好的"保底选择"**——纯 PC、零硬件、指标自证，任何团队都能做完。但在有真机的前提下，它有三个劣势：

1. **真机对它增益最小**。它的验证对象是 Web 页面，跑 Chromium Headless 就够了，**真机几乎不提升说服力**。你们手里的真机资源被浪费了。
2. **它离"OpenHarmony 生态"稍远**。虽然命题在国创/鸿蒙赛道下，但交付物本质是个 Web 工具。a26/a24 是真机上的原生工具，**和赛道主线的贴合度更高**。
3. **创新空间已经被命题写死了**。a35 的挑战目标是"双引擎校验 + 准确率 90% + 单页 10s + 修复补丁"，路径非常明确，**留给团队做差异化的空间反而不如 a26**（a26 的 Agent 工作流设计自由度更大）。

**结论**：a35 降为次选，定位是"如果 a26 在 W1–W2 遇到环境阻塞时的 Plan B"。

## 五、如果要冲奖牌：u-a24《多模态智能测试系统》

如果团队的目标不是"稳妥完赛"而是"拿奖"，**a24 是创新空间最大的一题**：

- **叙事最强**：`截图/布局采集 → 页面理解 → 交互路径规划 → 脚本生成 → 自动执行 → 结果分析 → 用例沉淀`，这是一个完整的**自主探索 Agent**，比 a26 的"诊断工具"听起来更有想象力。
- **真机是它的核心资产**：需要真机跑 UI 自动化（至少一种 OH 测试框架），**没有真机根本演示不了**。你们的优势在这里会被放大到最大。
- **技术含量可展示**：多模态大模型理解截图 + 控件树 + 生成可执行脚本，这几块都能做出很漂亮的 demo。
- **代价**：工作量比 a26 大。多模态模型调用的稳定性、脚本生成的可执行率、页面状态图的构建，每个都是硬骨头。**基础目标 6 条 + 挑战目标 7 条，要求偏密。**

### a26 vs a24 的选择

| | a26 体验优化 Agent | a24 多模态测试系统 |
|---|---|---|
| 叙事 | 诊断+优化闭环 | 自主探索+脚本生成 |
| 创新天花板 | 中高 | **高** |
| 工作量 | 中 | **中高** |
| 失败风险 | 低（指标不达标也交得出东西） | 中（脚本生成率低会很难看） |
| 适合 | 求稳拿分 | **冲奖牌** |

**我的建议**：如果团队 **4 人以上且有人懂 UI 自动化**，直接打 a24；如果 **2–3 人**，打 a26。

## 六、另一个值得注意的选项：u-a10《多 Agent 自主协商系统》

如果你们手上的真机是 **3–5 台 OH 设备**（手机+平板+音箱/手表），**a10 值得认真考虑**：

- **创新性在 38 题里数一数二**：设备 Agent 通过软总线"自主开会协商"，从"设备互联"跃迁到"智能体社会"。命题背景里那个"温度传感器→空调→窗帘协商 30 秒后全帘关闭"的例子非常有画面感。
- **真机数量就是准入券**：命题要求"在 3 台以上设备上完成端到端 Demo"，**这是硬性门槛，多设备团队天然领先**。
- **有形式化建模这个技术纵深**：CSP 演算证明最终一致性/无冲突性，答辩时很有分量。
- **风险**：需要 LLM 生成谈判策略 + 形式化验证两套能力，团队要同时懂分布式和形式化方法，门槛不低。

## 八、行动建议

**第一步（本周）**：确认真机的确切能力边界——能不能装 HAP、能不能连 DevEco Studio、有几台、什么型号。这决定了是打 a26 还是 a10。

**第二步**：按下面的决策树选定：

```
真机 ≥3 台 OH 设备，且团队懂分布式？
├─ 是 → a10 多 Agent 协商（创新性最高）
└─ 否 → 团队 ≥4 人且有 UI 自动化经验？
         ├─ 是 → a24 多模态智能测试（冲奖牌）
         └─ 否 → a26 体验优化 Agent（最优性价比）★推荐
```

**第三步**：无论选哪个，**W1 先把"真机上跑起一个示例应用并采集到数据"这件事打通**——这是所有候选题的共同地基，也是最早能发现环境坑的时点。

## 九、结论摘要
