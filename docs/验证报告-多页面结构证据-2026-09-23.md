## 二、判定依据：三级证据，强度递减

**关键点：判定依据不是「截图看起来不一样」。**

只按截图判会把「同一页的滚动」误判成换页 —— 滚动前后截图不同，
但页面结构语义没变。真正硬的是**应用自己声明的路由身份**：

| 级别 | 依据 | 含义 | 强度 |
|---|---|---|---|
| **L1** | **`pagePath`** | ArkUI 路由路径，**应用自己声明的页面身份** | ★★★ |
| L2 | 结构签名 | 层级 + 类型 + bounds 的哈希（**不含文案**） | ★★ |
| L3 | 页面标题 | 排除状态栏后最靠上的短文本 | ★ |

**为什么 L1 最强**：`pagePath` 是应用在代码里注册的路由，不是我们从渲染结果
反推的。两个页面共用同一个 `pagePath` 就不该算两个页面 —— 这是应用自己的答案。

**为什么 L2 不含文案**：文案会变（时钟每分钟跳一次、电量在变），
用文案签名会把**同一页面在不同时刻**判成两个页面。

### 3.4 搜索页文案为空：是真实状态，不是采样遗漏

我最初以为这是 bug，查了树才确认：

```
搜索页所有有 text 的节点：
  Text  '没有 SIM 卡'   rect=(43,32,...)     ← 状态栏
  Text  '×'            rect=(182,32,...)    ← 状态栏
  Text  '11%'          rect=(519,32,...)    ← 状态栏
  Text  '08:41'        rect=(621,32,...)    ← 状态栏

搜索页 clickable 节点：
  Image     text_deep=''
  TextInput text_deep=''
```

**该页正文由输入型控件构成**（空 `TextInput` + 返回图标），初始状态无输入
所以无文案。产物报告里如实写成「排除状态栏后无可采文案 —— 该页正文由输入型
控件构成，不是采样遗漏」，**不粉饰**。

> 顺带：这条也暴露了我第一版的一个采样缺陷 —— 文案采样**没有排除状态栏**，
> 于是每页前 4 条永远是「没有 SIM 卡 / × / 11% / 08:40」，把真正的页面文案挤掉。
> 是**看了产物才发现**的，不是写的时候想到的。已修。

## 四、真机上踩到的四个坑（都影响可复现性）

### 4.1 🔴 `aa start` 是**复用实例**，不会回到入口页

```
第 1 轮：点 '搜索设置项' → page2 采到
第 2 轮：拉不回入口页（sig 509f... != 74b0...），停止探索
```

`com.ohos.settings` 的 `MainAbility` **会恢复上次停留的页面**。
只 `start_ability` 的话第二轮就停在搜索页 → 整个采集提前终止（只采到 2 页）。

**修法**：`aa force-stop` → `keyEvent Home` → `aa start`，三步缺一不可。

### 4.2 🔴 `pagePath` 在 `attributes` 里，不是内联文本

我第一版按「搜 `pagePath=xxx` 内联文本」写正则，结果**永远读到空串**。
真相是：

```python
node.attributes['pagePath'] == 'pages/settingList'
```

它是独立的键值对。改为直接读 `attributes` 后，5 个页面全部读出来了 ——
而且这是**比标题和结构签名都硬**的证据。

### 4.3 🟠 真机可点控件**自身 id/text/descr 全空**

`com.ohos.settings` 首页 **11 个可点控件，11/11 自身身份字段为空**：

| 层级 | 内容 |
|---|---|
| 可点容器（`Flex` / `ListItem`） | `id='' text='' descr=''` |
| 子 `Text` | `WLAN` / `已关闭` / `显示与亮度` / `蓝牙` … |

所以第一版「按 id 或自身 text 找可点控件」**一个都选不中**（只采到 1 页）。
必用 `text_deep`（自身 + 子树文案）—— 这与 `layout.py:215` 的 `text_deep`、
以及 B 的 `pick_stress_target` 是**同一个教训**，只是各自踩了一遍。

### 4.4 🟠 hdc 通道间歇不可用

真机上会间歇性回：

```
[Fail][E000004]:The communication channel is being established.
[Fail]ExecuteCommand need connect-key? please confirm a device by help info
```

**这不是命令错，是通道还没建好**，等 1–2 秒重试即可。本工装对每条设备命令
做了 4 次重试。⚠️ 另外 `Hdc.shell()` 返回的是 **`ShellResult` 对象**不是 str ——
我第一版直接对它做 `in` 判断，报 `TypeError: argument of type 'ShellResult' is not iterable`。

## 六、局限（如实列出）

1. **样本不是命题要求的「示例应用」** —— 见 §一。这是本报告最重要的局限。
2. **只走了 5 个页面**（入口 + 4 个子页），`com.ohos.settings` 还有更多路由
   （显示与亮度、声音、生物识别、应用、存储、隐私、辅助功能…）。5 个已满足
   「≥3」，没有继续扩。
3. **`pagePath` 依赖应用暴露该属性**。`etsclock` 是纯 Canvas、`id` 数为 0，
   这台设备上不少应用不暴露 `pagePath` —— 那时只能退回 L2/L3。
4. **探索策略是广度优先 + 每轮从入口页重来**，采不到「二级深度的页面」
   （例如「设置 → WLAN → 某个具体网络」）。要采深层页面得改策略。
5. **页面 #2 无文案**（§3.4）—— 页面身份完全靠 `pagePath` + 结构签名立住，
   内容证据为零。

## 七、这次验证说明了什么

**基础 #5 现在是「双口径各自闭环」**：

| 口径 | 样本类型 | 证据强度 | 数字 |
|---|---|---|---|
| 核心流程 | 示例应用 ✓ | 控件树指纹变化（动作前后） | **4/4** |
| 页面覆盖 | 系统应用 ⚠️ | ArkUI 路由 `pagePath` | **5/3** |

命题给的读法是「**或**」，任一条成立即可 —— 我们现在两条都有，
且都不靠「看起来对」：核心流程靠动作前后的树差异，页面覆盖靠应用自报的路由。

**但不要用这个掩盖样本的短板**：真正符合命题「示例应用」字样的只有核心流程
那条；页面覆盖那条的样本是系统应用，报告里必须如实标注。

## 八、附带发现（对 A/B 有用的）

1. **`pagePath` 是页面级身份的可用证据源** —— 建议 A 的 `layout.py` /
   `explorer.py` 把它纳入页面签名（目前 `build_page_signature` 用的是结构特征，
   没用到 `pagePath`）。真机上它比结构签名更稳。
2. **`attributes` 里还有 `hitTestBehavior` / `opacity` / `zIndex` /
   `origBounds`** —— 后两个 B 的 `diagnose.py` 已经在用了；
   `origBounds` 与 `bounds` 的差异可用来识别「被裁剪/被遮挡」的控件，
   目前两侧都没用。
3. **可点控件自身身份字段全空已经是第二次被踩**（B 的 `pick_stress_target`、
   我的这个工装）。建议把这条件**收敛成一条公共约定**，写进
   `layout.py` 的 `identity_hint(node)`，两侧共用，别再各踩一遍。
