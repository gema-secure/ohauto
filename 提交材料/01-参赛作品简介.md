# 参赛作品简介

## 面向 OpenHarmony 的多模态智能测试系统

**作品形态**：Python 能力包与命令行工具集
**适用平台**：OpenHarmony 应用，支持真机与模拟器

### 一、项目概述

本作品面向 OpenHarmony 应用的质量保障，是一套在宿主侧运行的 UI 自动化测试系统。系统经 hdc 通道驱动真机与模拟器，设备侧零部署，不修改被测应用代码，也无需为应用打包任何测试组件。

系统将人工测试流程转化为自动流程：采集控件树与截图，解析页面结构，生成可执行用例，执行并断言，失败后归因与修复，最终沉淀为可重放的回归集。

系统名称中的「多模态」指控件定位使用两个信息通道。控件树提供结构化布局信息，其可用性取决于应用是否设置标识；截图提供视觉语义，可覆盖 Canvas 绘制与无标识图标等控件树盲区。两路证据按统一契约融合裁决。

### 二、问题分析

**（一）控件定位依据不足。** 对 13 个真实应用采集 14 份控件树，共 1648 个节点，其中带 id 属性的 70 个，占 4.2%；可交互控件中有 69.0% 不具备任何语义标识。系统设置与纯 Canvas 绘制的时钟应用，整棵树的 id 数为零。单一控件树通道在这类应用上完全失效，多模态融合是必要条件。

**（二）失败缺乏归因。** 执行失败时，现有框架只报告步骤失败，不区分设备异常、应用缺陷与脚本缺陷。人工排查的结论不可复核，也难以转为可复用的修复机制。

**（三）生成用例可信度不足。** 语言模型生成的用例普遍存在可执行但缺乏实质验证的问题：步骤全部通过，却没有断言与有效动作，通过率被系统性抬高，反而掩盖真实质量状况。

### 三、技术方案

**（一）四源融合定位与「声明—观察」契约。**
静态源码、用例声明与设计稿提供「声明」，描述控件应当存在；运行时控件树、截图视觉与 OCR 提供「观察」，描述页面实际存在什么。融合规则只依据证据角色，不依据来源名称，新增信息源只需实现一个适配器。

裁决分三种：声明与观察一致为 confirmed；声明存在而观察缺失为 missing，按「差异即缺陷」判为疑似缺陷；声明缺失而观察存在为 undeclared，提示声明的完整性缺口。条件渲染未生效、控件被显式隐藏、控件越出屏幕三类成因均可由此稳定检出。

证据不足以支撑判定时，系统显式失败并给出原因，不以坐标兜底静默通过。系统应用上静态源码不可用，实际在线通道为二至三路，融合按可用证据降级，并在报告中标注降级事实。

**（二）失败归因与定位自愈。**
失败瞬间打包现场：截图、连续多棵控件树、崩溃日志与设备状态。归因分为定位失败、应用缺陷、环境问题、用例问题四类，多源信号交叉印证，冲突时按证据强度排序。

确认定位失败且同一位置连续失败达到阈值后，系统基于历史控件树重新生成候选定位器并换代执行，验证通过才写入账本，不通过则回滚上一代。失败按来源、代次、定位器三者幂等记账，同一失败不重复计数。

**（三）可信用例生成与导出校验。**
生成分两阶段：先由自然语言描述与页面上下文产出测试点与步骤，再由静态校验拦截缺乏实质验证的用例。校验只查两件事：该步骤是否具备失败可能，失败原因是否指向应用。等待与断言计入实质动作，无可执行步骤或断言落空的用例在导出前被拦截。通过校验的用例可导出为 hypium 测试脚本，在真机测试框架中直接运行。

### 四、系统组成

- **连接与执行**：设备通信、控件树与截图采集、输入注入、用例调度；
- **探索与生成**：页面状态图自动探索，自然语言驱动的用例生成；
- **融合与定位**：多源证据融合裁决，五级降级定位链；
- **诊断与报告**：崩溃与无窗口等信号采集，逐步归因，输出可复核报告；
- **工装与质量**：静态检查、质量门禁、离线评测、长稳编排。

### 五、验证结果

| 项目 | 结果 | 口径说明 |
|---|---|---|
| 单元测试 | 1580 项通过，1 项跳过（57 个测试文件） | 离线全绿，耗时 109 秒；真机用例按设备在场自动解除跳过 |
| 代码覆盖率 | 89%（核心包 `ohauto/`） | 门禁线 70% |
| 静态检查 | 0 error（243 warning） | 基于语法树的本地检查，不依赖外部服务 |
| 控件 id 覆盖率 | 全节点 4.2%，可交互控件 26.4% | 69.0% 的可交互控件无任何语义标识 |
| 视觉与控件树一致性 | 95.0%（19/20），扩充至 13 应用后 97.8%（45/46） | 双通道一致性（IoU@0.5），非绝对准确率 |
| 生成用例静态可执行率 | 92.3%（24/26，两轮复跑一致） | 两条固定负样本均被校验闸拦截 |
| 生成用例真机执行 | 用例级 23/24 与 22/24（两轮） | 波动一条，根因为断言目标落在控件树之外 |
| 用例墙钟耗时 | 降低 26%（取树 12 次降至 9 次） | 同一条十步用例的真机前后对比 |

验证在 DAYU200 真机（OpenHarmony 5.0.3.135）与模拟器实例上完成。视觉一致性为两个信息通道之间的一致程度，项目未建立人工真值标注集；生成用例的「可执行」指通过静态校验并可导出，不等同于执行通过。

### 六、交付与可复现

仓库交付源码、测试、真实采集数据与全部数字的复现命令。核心包附带 57 个测试文件，13 个应用的控件树与截图作为公开数据集提供，无设备环境亦可跑通测试。

一条命令跑通完整链路：

```bash
python tools/demo_full_chain.py
```

附加 `--real` 参数走真机；设备不在场时如实失败退出，不伪造运行结果。文档包括 API 手册与两个在线演示页，覆盖整链演示与应用画廊。

本作品将多源融合定位、失败归因与定位自愈、可信用例生成三项能力集成为可在 OpenHarmony 真机上完整运行的测试系统，为应用质量保障提供可复现、可扩展的工程基础。
